# Civitas-AI 实验矩阵设计

> 本文档定义一张覆盖 **非对抗面** 与 **对抗面（恶意攻击 + 环境故障）** 的实验矩阵，
> 用于系统性验证 Civitas-AI 在正常行为与受攻击/受扰动条件下的设计假设是否成立。
>
> 机器可读的单一事实源为 [`Benchmarks/experimentMatrix.json`](../../Benchmarks/experimentMatrix.json)，
> 本文所有表格与之对齐；覆盖完整性由 [`Scripts/experimentMatrix.cjs`](../../Scripts/experimentMatrix.cjs) 强制校验。

---

## 1. 矩阵模型

### 1.1 两条轴

- **行：系统面（surface）** —— 被验证的能力边界，共 12 个面（见 §1.4）。
- **列：实验类别（cls）** —— 每格标注属于以下之一：
  - `BEN` 非对抗：正确性、收敛、正常恢复、守恒等"按设计工作"的行为。
  - `ENV` 对抗·环境故障：崩溃、超时、满盘、网络分区、Provider 故障、风暴、预算耗尽、死锁等非恶意但恶劣的运行条件。
  - `SEC` 对抗·恶意攻击：注入、越权、串谋、篡改、绕过审批、数据投毒等带意图的完整性/可用性攻击。

一个实验 = 矩阵中的一个 **cell**，落在某个面 × 某个类别。

### 1.2 cell 字段

| 字段 | 含义 |
|------|------|
| `id` | 唯一标识：`BEN-*` / `ENV-*` / `SEC-*` |
| `surface` | 所属系统面 |
| `cls` | BEN / ENV / SEC |
| `family` | 对抗家族（仅 ENV/SEC），见 §1.3 |
| `objective` | 被验证的设计假设 |
| `method` | 实验方法 / 对抗手段 |
| `oracle` | 判据（成功/失败的可判定定义） |
| `module` | 锚定的真实模块 |
| `gate` | 映射到既有 Gate（G0-G13，2026-09-22 校准，见下方注）或 DUR-* |
| `status` | `existing-covered` / `new-scaffold` / `declared-only` |
| `dim` | 六维指标归属 |
| `anchor` | 可解析性锚点（见 §1.5） |

> **注（2026-09-22 校准）**：`gate` 取值上界为 **G0-G13**，非原文的 G0-G14。§3 全表逐行核对后实际出现的最高门禁为 **G13**（BEN-API 行 `G13/M2`）；**G14** 仅见于 [`Docs/14-构建与实施/项目构建顺序.md`](../14-构建与实施/项目构建顺序.md)（S14 里程碑的目标态门禁），本矩阵无任何 cell 锚定它，故不计入映射范围。

### 1.3 六类对抗家族

为保证攻击面分类无遗漏，所有对抗 cell 必须归入下列之一：

1. `injection` —— Prompt 注入、指令覆盖，篡改仲裁/审计逻辑。
2. `integrity` —— 目标/测试/产物/并发写入的完整性篡改与反博弈。
3. `availability` —— 资源耗尽、超时、崩溃、分区、熔断、死锁等可用性打击。
4. `privilege-escalation` —— 越权使用高危工具、访问私有上下文、目录/网络逃逸。
5. `governance-manipulation` —— 跳级验证、Maker-Checker 串谋、审批绕过、逃避裁决。
6. `data-poisoning` —— 低可信断言注入长期记忆、密钥泄露污染观测面。

### 1.4 系统面（12）

启动与配置 / 持久执行 / LLM 通道 / 工具层 / Loop 控制与主循环 / Token 经济 /
事件与共享记忆 / 单 Agent 端到端 / 多 Agent 编排 / 并行与隔离 / 司法与监管 / 交互与可观测。

### 1.5 status 与 anchor

- `existing-covered`：既有测试已覆盖，`anchor.kind=spec`，`ref` 为既有测试文件路径。
- `new-scaffold`：本次新增可运行用例，`anchor.kind=tag`，用 `// @matrix:<ID>` 关联 `Tests/Experiments/**`。
- `declared-only`：需真实进程/混沌环境或运行时检测点尚不存在，仅在矩阵声明方法与判据，**不产出伪断言**，`anchor.kind=none`。

## 2. 覆盖保证

### 2.1 四条硬规则（由脚本强制，违反则退出码非 0）

1. 每个系统面至少 1 个 `BEN` 且至少 1 个对抗（`ENV`/`SEC`）cell；
2. 六类对抗家族各至少被 1 个 cell 覆盖；
3. 每个 cell 必须有 `oracle`，且 `anchor` 可解析（spec 文件存在 / tag 出现 / declared-only）；
4. 汇总对抗落地率与 `declared-only` 缺口。

## 4. 实现约定

- **锚定真实契约**：SEC/ENV 断言一律使用模块返回契约（`checkPath.allowed`、`isToolAllowed`、`checkAntiGaming.passed`、`checkViolation.violated`、`interceptWrite`、`checkTimeoutApprovals.status`、`isFrozen` 等），**不引用不存在的 EventType**。注意 `security.json` 的 `INJECTION_DETECTED/FORBIDDEN_PATH_ACCESS/KEY_LEAKAGE` 是配置标签，非 `eventTypes.ts` 枚举成员。
- **Maker-Checker 有运行时点**：`verifier/llmJudge.ts` 在 `spec.payload.model === ctx.producerModel` 时返回 err（ADR-0004），SEC-COLLUSION 据此落地对照断言。
- **测试隔离**：新增用例均为纯逻辑模块，无 DB；`afterEach` 调用各模块 `reset*`/`clear*` 复位全局单例；ENV-CLOCK 用 `vi.spyOn(Date,'now')` 并 `restoreAllMocks`。
- **不触碰 Src**：本矩阵仅新增评估资产（测试/基准/脚本/文档），不改生产代码；`declared-only` cell 不写伪断言。

## 5. 已知缺口（declared-only，待后续排期）

| ID | 面 | 阻塞原因 |
|----|----|----------|
| ENV-TIMEOUT | LLM 通道 | 需真实流式时钟注入（总 60s/首字节 10s/包间 15s） |
| ENV-NETPART | LLM 通道 | 需混沌网络分区环境 |
| ENV-PDOWN | LLM 通道 | 需多 Provider 同时故障编排 |
| SEC-KEYLEAK | 交互与可观测 | `keyStore` 缺泄露扫描检测点（需实现后再补断言；模块导出面见注③） |

> **注③（2026-09-22 校准）keyStore 导出面**：原文"仅有 registerKey/resolveKey"**低估**了该模块。`Src/Infra/Security/keyStore.ts` 实导出 **9 个函数**：`registerKey:61` / `resolveKey:76` / `isKeyAvailable:114` / `getMaskedKey:123` / `resolveSingleRef:138` / `isKeyRef:156` / `clearKeyStore:163` / `getRegisteredKeyNames:171` / `scanAndRegisterRefs:181`（另导出 `KeyRef`/`ResolvedKey`/`KeyEntry` 三类型），含脱敏摘要与多引用 fallback 解析。
> **结论保留 `declared-only`**：① 仍**无密钥泄露扫描检测点**——`scanAndRegisterRefs` 只递归登记配置里的 `env:` 引用，不检测明文外泄，全 `Src/` grep `KEY_LEAKAGE|leakage|redact|maskSecret|scanSecret` **0 命中**（`KEY_LEAKAGE` 仅作为 `Configs/security.json:19` 的 `criticalSecurityEvents` 配置标签存在，见 §4）；② 整模块在 `Src/` 中 **0 生产调用者（未接线）**，唯一引用者为 `Tests/Infra/security.spec.ts`。故 SEC-KEYLEAK 不具备落地断言的条件。
>
> 另记一项**非 declared-only** 的补断言待办：ENV-DBFULL（满盘注入缺失，见 §3.2 注①）。
