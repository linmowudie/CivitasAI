# 仲裁系统设计

> 本文档定义 Civitas-AI 的仲裁系统（Arbitration Tribunal），融合动态仲裁者数量控制、上下文胶囊、律师函挂起机制和现场恢复机制的完整设计。

---

## 1. 职责边界

| 职责 | 说明 |
|------|------|
| 冲突接收 | 接收 WriteGuard 上报的语义冲突、Agent 间分歧 |
| 上下文胶囊组装 | 按需拉取证据，组装轻量级裁决上下文 |
| 裁决推理 | 3-LLM 多数决，按优先级协议推理 |
| 律师函挂起 | 立即挂起涉事 Agent，释放资源 |
| 现场恢复 | 指定恢复者，执行补偿动作 |
| 动态仲裁者管理 | 按冲突频率动态调整辅助仲裁者数量 |
| 知识沉淀 | 裁决结果提炼为长期知识 |

**不负责：** 冲突检测（由 SharedMemory/WriteGuard 负责）、Token 划扣执行（由 TokenEconomy 执行）、全局规则修改（由 Regulatory Authority 负责）。

## 3. 核心组件

### 3.1 组件定义

| 组件 | 实现（函数式模块） | 职责 |
|------|------|------|
| 冲突接收器 | `fileCase(params)`（`tribunal.ts`） | 接收冲突事件，创建仲裁案件 |
| 胶囊组装器 | `assembleCapsule(params)`（`capsuleAssembler.ts`）/ 闭环内简化版 `assembleCapsule(caseId, params)`（`tribunal.ts`） | 按需拉取证据，组装上下文胶囊 |
| 仲裁者池 | `initArbitratorPool` / `assignArbitrators` / `resizeAuxiliaryPool`（`arbitratorPool.ts`） | 管理核心层+辅助层仲裁者，动态扩缩 |
| 推理引擎 | `reasonVerdict(caseId)`（`tribunal.ts`） | 执行优先级协议，输出裁决 |
| 律师函发布器 | `issueSuspension(caseId)`（`tribunal.ts`） | 发布 `SUSPEND_AND_NOTIFY` 事件 |
| 恢复管理器 | `createPlan(params)` / `executePlan(planId)`（`restorationManager.ts`）；闭环内另有 `createRestorationPlan` / `completeRestoration`（`tribunal.ts`） | 指定恢复者，跟踪恢复进度 |
| 知识沉淀器 | `consolidateKnowledge(caseId)`（`tribunal.ts`）+ `consolidateFromTrace`（`SharedMemory/memoryConsolidator.ts`） | 提炼裁决结果为长期知识 |
| 动态扩缩器 | `evaluateScaling()` / `startAutoScaling()`（`dynamicScaling.ts`） | 按冲突监测指标调整仲裁者数量 |
| 端到端编排 | `executeFullArbitration(params)`（`tribunal.ts`） | 顺序串起 Step 1→6 |

> **2026-10-03 校准**：上表定位一律改为**文件名 + 函数名**锚点（此前"文件:行号"因 lint/类型债修复整体漂移 +1~4 行，行号锚点已废弃）。
>
> ⚠️ **裁决路径与仲裁者池当前解耦（2026-10-03 校准）**：`reasonVerdict` **不从仲裁者池取仲裁者**——在 `tribunal.ts` 内以 for 循环自造 `arbitrator-1..3`；
> `initArbitratorPool` / `assignArbitrators` / `executeVerdicts` / `releaseArbitrators` 在 Src 中**零生产调用方**，
> 池仅有 `dynamicScaling.ts` 调 `resizeAuxiliaryPool`/`getPoolStats` 与 `Interface/RestApi/loopApi.ts` 调 `getPoolStats` 两个存在点（未 `initArbitratorPool` 时统计恒 0）。§2 架构图"Pool→推理引擎"为**目标态**。

> ⚠️ 未接线（2026-09-22 校准）：`executeFullArbitration` 与 `restorationManager.ts` **互不调用**（闭环内用的是 `tribunal.ts` 自带的 `createRestorationPlan`/`completeRestoration`）；
> 案件与恢复计划均存于模块级 `Map`（`tribunal.ts` 顶部 `cases`/`restorationPlans`、`restorationManager.ts` 顶部 `plans`），**不落库**（见 Docs/Agent/09 §2.7）。

## 4. 六步治理闭环（详细流程）

### Step 1：写入拦截（由 WriteGuard 触发）

```
Agent 向全局工作区写入新记忆
    │
    ▼
WriteGuard.intercept(writeRequest)          // 目标态；实际导出为 interceptWrite(entry, currentVersion, expectedVersion)（SharedMemory/writeGuard.ts → interceptWrite）
    │
    ├── 【目标态 · ⚠️ 未实现（2026-09-22 校准）】
    │   ├── 提取新记忆的语义向量 + 元数据
    │   ├── 在向量库中检索相似度 > 0.85 的旧记忆
    │   └── 检测是否存在语义相反的旧记忆
    │
    ├── 【实际实现】interceptWrite 仅做三件事：
    │   ├── 红线 key 校验（goal / immutable_constraints / successCriteria 禁入 GlobalWorkspace）
    │   ├── 乐观锁版本号校验（不匹配 → MEMORY_VERSION_CONFLICT）
    │   └── assertion 级别标记（inferred/assumed 不入 L 分区与长期记忆）
    │
    ├── 无冲突 → 放行写入
    └── 有冲突 → 生成 CONFLICT_DETECTED 事件
        │
        ├── ⚠️ 实际发布方（2026-09-22 校准）：`Core/Decision/orchestrator/conflictPrecheck.ts` → `precheckConflicts()`
        │   —— 检测维度是"多个 Agent 修改了同一文件路径"，非语义向量；
        │   —— `Configs/memory.json → memory.conflictSimilarityThreshold` 目前无任何代码引用；
        │   —— 语义相反检测仍为目标态（见 Docs/Agent/07 §3.2）。
        │
        ├── ⚠️ 发布链尚未接入主循环（2026-10-03 校准）：`precheckConflicts()` 的唯一调用方是
        │   `mergePhase.ts → executeMergePhase()`，而 `executeMergePhase` 在 Src 中**无任何导入者**（仅 Tests/Parallel 引用）；
        │   且全仓无 CONFLICT_DETECTED→`fileCase` 的订阅桥（仲裁自动立案环节缺失）——Step 1→Step 2 目前为**手动/测试驱动**。
        │
        └── 事件内容（目标态契约）：
            {
              conflictId: string,
              newMemoryId: string,
              oldMemoryId: string,
              newMemoryAgentId: string,
              oldMemoryAgentId: string,
              similarity: number,
              conflictType: 'semantic_opposition' | 'contradiction' | 'duplication',
              timestamp: number                  // epoch ms
            }
```

### Step 2：胶囊调阅

```
Arbitrator 收到 CONFLICT_DETECTED 事件
    │
    ▼
assembleCapsule(params)                       // capsuleAssembler.ts → assembleCapsule（params = conflictId/newMemoryId/oldMemoryId/plaintiff/defendant/taskId/tokenBudget?）
    │                                        // 六步闭环内实际调用的是 tribunal.ts → assembleCapsule 简化版 (caseId, params)
    │                                        // ⚠️ 2026-09-22 校准：需先 initCapsuleAssembler(source)（capsuleAssembler.ts → initCapsuleAssembler）注入 EvidenceSource，Src 内目前无调用方
    │                                        //    未注入时回落 createSimpleCapsule（证据为 '(简化模式)'、agentHistory 为空）
    ├── [2a] 拉取证据
    │   ├── 新记忆完整内容 + 元数据（时间戳、来源 Agent、任务 ID）
    │   └── 旧记忆完整内容 + 元数据
    │
    ├── [2b] 拉取环境上下文
    │   ├── 两条记忆所属任务的"父级任务描述"
    │   └── 前置约束条件（如有）
    │
    ├── [2c] 拉取 Agent 历史记录
    │   ├── 涉事 Agent 最近 5 条操作记录（代码硬编码 limit=5，未读 `memory.capsuleRecentOpsCount`）
    │   └── 相关 trace_id 的决策历史
    │
    └── [2d] 组装胶囊
        │
        └── 输出 ContextCapsule：
            {
              capsuleId: string,
              conflictId: string,
              evidence: {
                newMemory: { content, metadata, agentId },
                oldMemory: { content, metadata, agentId },
              },
              taskContext: {
                parentTaskDescription: string,
                constraints: string[],
              },
              agentHistory: {
                plaintiffOps: OperationRecord[],
                defendantOps: OperationRecord[],
              },
              tokenBudget: number,      // 本次仲裁的 Token 预算；缺省 5000，未读 memory.capsuleBudgetTokens

            }
```

**最小信息原则：** 仲裁者绝不加载全局上下文，只看到"案卷"。

### Step 3：裁决推理

```
reasonVerdict(caseId)                         // 原写 ReasoningEngine.reason(capsule) 不存在；实为 tribunal.ts → reasonVerdict（入参是 caseId，胶囊取自案件）
    │
    ├── ⚠️ 现状（2026-09-22 校准）：Phase 0-2 为**规则裁决**，不调 LLM（tribunal.ts 头注释）；
    │   代码内以 for 循环生成 3 个结论一致的 ArbitratorVerdict（verdict 恒为 'new_wins'，confidence 0.8）
    │
    ├── 目标态：并行调用 3 个独立 LLM（仲裁者）
    │   ├── 每个 LLM 独立接收 capsule
    │   ├── 使用 Prompts/roles/arbitrator.md 提示词
    │   └── 输出结构化裁决
    │
    ▼
按优先级协议推理（每个 LLM 内部）：
    │
    ├── 优先级 1：时间戳优先（LWW）
    │   └── 如果新旧记忆描述客观事实，且新记忆时间戳更晚 → 采信新记忆
    │
    ├── 优先级 2：任务权威性优先
    │   └── 检查来源 Agent 的权限等级/任务优先级
    │
    ├── 优先级 3：证据链完整性优先
    │   └── 检查哪条记忆附带更可靠的工具调用结果
    │
    └── 优先级 4：LLM 语义推理兜底
        └── 根据任务环境上下文进行逻辑推演
    │
    ▼
单个 LLM 裁决输出（= 代码 ArbitratorVerdict，types.ts → ArbitratorVerdict）：
    {
      arbitratorId: string,
      verdict: 'new_wins' | 'old_wins' | 'both_invalid' | 'need_more_evidence',
      winnerId: string | null,
      loserId: string | null,
      reasoning: string,                // 裁决理由
      confidence: number,               // 置信度 0-1
      penalty?: {
        type: 'token_deduction' | 'warning' | 'none',
        amount?: number,
      },
      deliveredAt: number,              // epoch ms
    }
    │
    ▼
多数决汇总（tribunal.ts → reasonVerdict 内的汇总段）：
    ├── 取票数最高的裁决为 finalVerdict；3 票一致 → isUnanimous = true
    ├── 三种裁决各不相同（unique 票数 = 3）→ isDeadlocked = true → 案件 status = 'deadlocked'
    │   └── ⚠️ 现状更新（2026-10-03 校准）：**监管承接端已实现并有测试覆盖**——
    │       `Regulation/regulatoryAuthority.ts → escalateDeadlock()` 转 `Regulation/finalArbiter.ts → issueFinalVerdict()`
    │       （校验 deadlocked/reasoning 态、落 interventions Map、广播 ARBITRATION_VERDICT 且带 `isRegulatoryIntervention: true`），
    │       用例见 Tests/E2E/regulationAuditMode.spec 与 Tests/Judicial/judicialSupervision.spec；
    │       **仍缺**：仲裁侧触发——tribunal 的死锁分支（`executeFullArbitration` 内）仅提前 return，不发事件也不调用 escalateDeadlock，
    │       `ARBITRATION_DEADLOCK` 至今**全仓无任何发布方**（仅 eventTypes.ts 枚举定义）。死锁升级链路 = "下游已就绪、上游未接线"。
    └── 超时（120s）→ 判定超时死锁 → 升级至 Regulatory Authority
        └── ⚠️ 未实现：`arbitration.deadlockTimeoutSec` 无代码消费，reasonVerdict 无超时分支（2026-10-03 复核仍成立）
```

### Step 4：律师函挂起

```
issueSuspension(caseId)                       // 原写 InjunctionPublisher.publish(arbitrationCase) 不存在；实为 tribunal.ts → issueSuspension
    │
    ├── 发布时机（2026-09-22 校准，按代码）：**裁决后挂起**，而非"与 Step 3 同时"
    │   executeFullArbitration 顺序执行：fileCase → assembleCapsule → reasonVerdict
    │   → 若 isDeadlocked 提前 return，**跳过挂起** → issueSuspension
    │   "零资源浪费"的并行发布仍为目标态（⚠️ Phase 3 改造项）
    │
    ├── 防抖：同 conflictId 5 分钟内只挂一次（常量 SUSPEND_COOLDOWN_MS = 5*60*1000，suspendHistory Map，
    │   均在 tribunal.ts → issueSuspension / 模块顶部）
    │   └── ⚠️ 待人工裁定（2026-10-03 登记）：去重键口径三处不一致——
    │       ① 实现与本节：以 **conflictId** 为键（suspendHistory: conflictId → lastSuspendAt）；
    │       ② tribunal.ts 两处代码注释（防抖段与 issueSuspension docstring）：写"同 **(loopId, conflictId)**"；
    │       ③ ADR-0002 决策第 4 条：亦写"同一 **(loopId, conflictId)** 5 分钟内只挂一次"。
    │       待办：裁定去重键是否含 loopId——含则改代码实现+本文档，否则修 ADR-0002 与代码注释。
    │
    ▼
广播 SUSPEND_AND_NOTIFY 事件（priority = 'critical'）：
    {
      eventType: 'SUSPEND_AND_NOTIFY',
      targetAgentIds: string[],        // 涉事 Agent 列表 = [plaintiffAgentId, defendantAgentId]
      suspensionReason: string,        // 挂起原因
      caseId: string,                  // 关联仲裁案件 ID（代码字段名为 caseId，非 arbitrationId）
      conflictId: string,
      // ⚠️ conflictSummary / issuedAt 不在实际 payload 中（2026-09-22 校准）
    }
    │
    ▼
涉事 Agent 收到律师函后【立即执行】：
    │                                        // ⚠️ 现状更新（2026-10-03 校准）：**类型与状态机底座已就位、仅缺事件订阅与写入**——
    │                                        //    SUSPEND_AND_NOTIFY 在 Src 中仍**无任何订阅方**（业务订阅仅 progressTracker 的 TASK_*）；
    │                                        //    但承接底座已半接线：① LoopControl/loopState.ts 定义 `SuspensionRecord{reason, suspendedAt,
    │                                        //    suspendedBy, conflictId}` 与 `LoopState.suspension?` 字段（代码注释明书"Docs/Agent/05 定义"，
    │                                        //    该类型的文档归属登记见本文 §6；suspension 字段目前在 Src/Tests 中**零写入方**）；
    │                                        //    ② Core/AgentRuntime/stateMachine.ts 支持 `SUSPEND: running→suspended`，
    │                                        //    AgentStatus 'suspended' 注释即为"挂起（律师函）"。
    │                                        //    以下 [4a]-[4c] 流程仍为设计目标态（⚠️ 未实现；冻结快照落 Redis/SQLite 亦未接线）
    ├── [4a] 状态冻结（State Freeze）
    │   ├── 停止当前任务链执行
    │   ├── 将执行进度、局部变量、中间结论打包
    │   └── 存入 Redis/SQLite（冻结快照）
    │
    ├── [4b] 任务转移（Task Shifting）
    │   ├── 释放当前算力资源
    │   └── 处理任务队列中不依赖冲突上下文的低优先级任务
    │       （如无可用任务，进入空闲等待）
    │
    └── [4c] 进入等待队列
        └── 标记为 WAITING_FOR_ARBITRATION，不再推进原任务
```

**架构价值：**
- **零资源浪费** — Agent 不会因冲突而傻等（Block），而是去干别的活（Yield）
- **数据安全** — 通过"冻结状态"杜绝 Agent 在等待期间基于错误前提继续执行
- **系统韧性** — 冲突不再导致系统崩溃或死锁，而是变成一次常规的异步任务调度

## 5. 动态仲裁者数量控制

### 5.1 冲突监测指标

| 指标 | 计算方式 | 用途 |
|------|---------|------|
| 冲突发生频率 | 单位时间内冲突次数（滑动窗口） | 判断是否需要扩容 |
| 冲突持续时间 | 从冲突检测到裁决完成的时长 | 判断仲裁效率 |
| 冲突涉及 Agent 数 | 单次冲突中参与的 Agent 数量（加权平均） | 判断冲突规模 |
| 待处理冲突队列长度 | 排队等待仲裁的案件数 | 判断仲裁压力 |

> ⚠️ 未实现（2026-09-22 校准）：`dynamicScaling.ts` 只维护 `conflictWindow: number[]`（由 `recordConflict()` 追加的冲突时间戳），
> 即**仅"冲突发生频率"一项有采集代码**（窗口长度硬编码 300 秒，未读 `arbitration.frequencyWindowSec`）；
> 冲突持续时间、涉及 Agent 数、待处理队列长度三项均无实现。

### 5.2 动态调整算法

```
// 2026-09-22 校准：以下按 Src/Services/Arbitration/dynamicScaling.ts 实际实现重写。
// 原写法 targetCount = currentCount × scaleUpFactor 与 CPU/内存资源约束检查均与代码不符（代码无资源约束逻辑）。

evaluateScaling()                              // dynamicScaling.ts → evaluateScaling；由 startAutoScaling()（同文件）每 monitoringIntervalMs 触发
{
  // [0] 冷却期：距上次扩缩 < cooldownMs（默认 120_000）→ 直接返回 action='none'

  // [1] 采集指标：conflictWindow 过滤到最近 300 秒（窗口长度硬编码，未读 frequencyWindowSec）
  frequency = conflictWindow.length            // 窗口内冲突条数

  // [2] 扩容判定：频率连续 consecutiveHighCount（默认 3）个评估轮 > frequencyThreshold（默认 5）
  //     幂律公式 f = k · n^m
  scalingFactor(=k, 默认 1.5) × Math.pow(frequency, scalingExponent(=m, 默认 0.5))
  targetCount = min(ceil(上式), maxArbitrators /* 默认 15 */)
  if (targetCount > currentAux) resizeAuxiliaryPool(targetCount)      // 仅扩辅助层，核心层不参与扩缩

  // [3] 缩容判定：frequency < frequencyThreshold × 0.5 且连续 consecutiveLowCount（默认 3）轮
  targetCount = max(minArbitrators /* 默认 0 */, floor(currentAux × 0.5))   // ⚠️ 0.5 为硬编码，未读 scaleDownFactor
  if (targetCount < currentAux) resizeAuxiliaryPool(targetCount)

  // [4] 介于两者之间 → consecutiveHigh / consecutiveLow 双双清零
}

// 扩缩成功后广播 ARBITRATOR_POOL_RESIZED（source='Arbitration/dynamicScaling'）
//   payload = { action: 'scale_up' | 'scale_down', targetCount, added | removed }

⚠️ 未接线（2026-09-22 校准）：
  · initDynamicScaling(cfg) 在 Src 中无调用方 → 全部阈值取模块内 DEFAULT_CONFIG，
    Configs/arbitration.json 的 scaleUpFactor / scaleDownFactor / monitoringIntervalSec /
    frequencyWindowSec / cpuPerArbitratorCores / memoryPerArbitratorMb **均未被消费**；
  · recordConflict() 无生产调用方（案件立案/裁决路径未回采频率），故自动扩缩实际处于空转；
  · 无 CPU/内存资源约束（原"resourceLimit"分支为设计目标）。
```
