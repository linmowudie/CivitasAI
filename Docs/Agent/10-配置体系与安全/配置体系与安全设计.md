### 1.2 配置加载优先级

```
local.json  >  {env}.json  >  default.json        （配置文件三层，优先级固定）
环境变量     →  仅用于注入密钥引用，不参与配置层级竞争
```

**规则：**
- `default.json` 提供所有配置项的默认值，**空配置下系统必须可直接启动**（`default.json` 本身缺失 → `configLoader.ts` 的 `loadConfig()` 第 1 步直接返回 FATAL）；
- `{env}.json` 为环境层（`dev.json` / `prod.json`），`{env}` 由 `CIVITAS_ENV` 决定；
- `local.json` 优先级最高，覆盖本地开发环境（不提交到 git）；
- **环境变量不再凌驾于 `local.json` 之上**（v2.1 修正：原写为 `环境变量 > local > default`，与全局约定冲突）；
  环境变量的唯一作用是解析 `api_key_ref: "env:OPENAI_API_KEY"` 这类引用（`.env` 的注入时机见 §3.6）；
- 运行时可重载的配置（L2）通过 `Infra/Watcher/configWatcher.ts` 文件监听触发。
  **⚠️ 未接线（2026-09-22 校准，2026-10-03 复核仍成立）**：见 §1.3，该监听当前不存在实际行为，L2 配置只能靠**重启进程**生效。

> **⚠️ 三层优先级的落地缺陷（2026-09-22 校准 · 现状 + 代码债，不抹平；2026-10-03 复核：未修复，且破坏面扩大）**：
> 上面那条 `local.json > {env}.json > default.json` 只对 **`default.json` 内的键** 成立。
> 实际顺序是：`configLoader.ts` 的 `loadConfig()` **第 4 步**用 `deepMerge(defaultConfig, deepMerge(envConfig, localConfig))` 得到 `merged`，
> 随后 **第 6 步**再把 §1.1 白名单里的 **11 个功能 JSON** 逐个 `merged[key] = deepMerge(merged[key], fileValue)`（或直赋值）覆盖到同一个 `merged` 上
> ——**功能 JSON 永远最后写入，且不看来源层**。
> 后果：凡是被功能 JSON 定义的键（`routing.*`、`economy.*`、`loopDefaults.*`、`stopRules.*`、`hardLimits.*`、`roleOverrides.*`、`supervision.*`、`retention.*` 等），
> `local.json` / `{env}.json` 里的**同名覆盖会被无条件吃掉**，"local 优先级最高"对这些键不成立；
> 只有**仅存在于 `default.json`** 的键（`system.*` / `server.*` / `database.*` / `ui.*`）才真正遵守三层优先级。
> - **2026-10-03 校准（影响加重）**：随着 §2.7 `supervision.rateLimit*`、§2.8 `stopRules`/`hardLimits`/`loopDefaults.token_budget`、§2.9 `durable.effect.writeSynchronous`
>   等键**首次转为真实生效值**，本缺陷的受害者从"调了也没用的键"变成"**真的会改变行为、但 `local.json` 覆盖不动的键**"——
>   本地想用 `local.json` 临时放宽预算/限流/审批超时现在同样无效。`Configs/local.json` 至今不存在，`.gitignore` 已登记该路径。
> - **现状**：本地调参只能直接改 `Configs/*.json`（会污染 git 工作区）或改 `default.json`。
> - **待办（代码债 · 优先级上调）**：功能 JSON 应先合并 `default.json → {env}.json → local.json` 各自的同名文件，
>   或在 `loadConfig()` 第 6 步的循环里对 `envConfig` / `localConfig` 中已存在的同名键保留覆盖值，之后再写入 `merged`；
>   在此之前，§2 各表中"✅ 运行期消费"的键须默认附带一条限定：**"改文件生效，但 `local.json` 覆盖不生效"**。

### 1.2.1 命名与单位规范（强制 · v2.1 新增）

| 对象 | 风格 | 例 | 说明 |
|------|------|----|------|
| 配置文件键 | **camelCase** | `httpPort`、`qualityThreshold` | 例外见下方《命名豁免清单》 |
| DB 表名与列名 | **snake_case** | `timeout_ms`、`budget_used_tokens` | 与 TS 字段的对应关系必须是**机械转换**，禁止人为改名 |
| TS 接口字段 | **camelCase** | `budgetUsedTokens` ↔ 列 `budget_used_tokens` | repository 层统一做 snake↔camel 映射；`LoopConfig` 除外（见豁免清单） |
| 时长后缀 | 必带单位 | 毫秒 `_ms` / 秒 `_sec` / 分 `_min` / 时 `_hour` / 天 `_days` / 轮 `_rounds` | `busyTimeout: 5000` → **`busyTimeoutMs: 5000`**；禁止无单位后缀的时间配置 |
| 比例与阀值 | 内部一律 **0.0–1.0 浮点** | `qualityScore: 0.85` | 展示层才 ×100；禁止 0-100 与 0-1 混用；DB 对应列为 `REAL` |
| 金额 | `_usd` 后缀 + number | `hardUsd`、`budgetUsedUsd` | 与 token 计量严格分开 |
| 时间戳 | `number`（epoch **毫秒**）+ `_at` 后缀；DB 列一律 `INTEGER` | `recordedAt`、`created_at` | 禁止 ISO-8601 字符串与 epoch 整数在同一库内混用 |
| 枚举 | **三处同形**（TS / DB / 配置文件不做大小写转换） | `'awaiting_approval'` | 分两类：① 状态/阶段类用 lower snake_case；② 安全类沿用 skill 的 SCREAMING_SNAKE（见豁免清单）；禁止 UI 引入第二套拼写 |

### 1.3 可变性分级

| 级别 | 名称 | 说明 | 适用配置 |
|------|------|------|---------|
| L0 | 启动锁定 | 启动后不可更改，修改需重启 | 安全策略、数据库路径 |
| L1 | 启动时读取 | 启动时读取一次，运行期间不变 | 本地覆盖配置 |
| L2 | 运行时可重载 | 通过文件监听或 API 热更新 | 路由规则、税率、模型路由 |
| L3 | 实时可变 | 每次使用时重新读取 | 无（当前不使用此级别） |

> **⚠️ 未实现 / 未接线（2026-09-22 校准 · 2026-10-03 复核：逐条重查，结论全部仍成立）**：上表 L0/L1/L2/L3 是**目标态分级**，当前**没有任何运行期含义**——
> 全部配置都在 `loadConfig()` 一次性读入 `merged`，此后运行期不再回读文件，因此 L0/L1/L2/L3 的实际行为**完全相同（改任何键都要重启进程）**。
> 逐条现状（定位一律用"文件 + 函数/符号名"）：
> - `configWatcher.ts` 的 `detectChanges()` 仍是**注释桩**（函数体只有两行 `Phase 0-2` 注释，不扫描文件系统）；

>   `main.ts` 的 `startServer()` 第 ⑨ 步只调 `initConfigWatcher({ watchDir: 'Configs/', pollIntervalMs: 5000 })` **存下参数而不启动轮询**；

### 3.2 信任分级

> **v2.2 修订**：原 L0 包含 Prime Director，但 Prime Director 与 Partner 本质是**入口级对等协作体**（均可接收用户输入、递归派发子 Agent），不应与治理三权（Regulator/Auditor/Arbitrator）共享最高权限。修订后 L0 仅保留治理三权，L1 为入口级，L2 为执行子级。外部输入的内容隔离（`<external trust="L2">`）与角色信任分级正交，不再占用 L2 行。

| 级别 | 名称 | 适用角色 | 权限范围 | 可接收用户输入 | 可递归派发子 Agent |
|------|------|---------|---------|:---:|:---:|
| L0 | 治理级 | Regulator, Auditor, Arbitrator | 全局读写、规则修改、Agent 管理、冲突裁决 | — | — |
| L1 | 入口级 | Prime Director, Partner | 接收用户输入、需求评估、工作方式选择、递归派发子 Agent、搭建工作流 | ✅ | ✅ |
| L2 | 执行子级 | Worker, Reviewer, Assembly Node | 仅执行上级派发任务、不可接收外部输入、不可自行招募下级 | ❌ | ❌ |

**角色分类说明：**

- **治理三权（L0）**：不参与业务执行，仅在冲突、异常、违规时介入。三权独立互相制衡。
  - Regulator：检测冲突行为、强制暂停 Agent
  - Auditor：审计日志回溯、异常操作告警
  - Arbitrator：裁决分歧（如两个 Partner 意见不一）

- **入口级（L1）**：Prime Director 与 Partner 完全对等，均可独立接收用户输入、递归拆分任务给其他 Partner 或委派 Worker。Prime Director 仅是全局视角的"主领导"标识，权限不高于 Partner。

- **执行子级（L2）**：仅执行上级派发任务。Worker 完成工作后必须走 `submitForReview`，不可自行宣告完成。

### 3.6 密钥管理

> **⚠️ 2026-09-22 校准（本节多条描述不实，逐条更正）· 2026-10-03 复校：结论均不变，定位改为文件名+符号名，并补一条新事实**：

>   `process.loadEnvFile(resolve('.env'))`（Node ≥20.12），外层 `try/catch` **静默忽略**文件不存在/不可读的情形，
>   且语义上不覆盖已存在于 `process.env` 的变量（Electron 注入的 `CIVITAS_*` 目录优先）。
>   ⇒ 因此"`api_key_ref": "env:XXX`"链路自 2026-10-03 起**可仅靠 `.env` 生效**；但**缺失变量时仍是静默保留字面量**（见下条），
>   `.env.example` 只登记 `HUAWEI_MAAS_API_KEY` 一项。
> - **引用语法只有 `env:XXX` 前缀**，**不支持 `${ENV_VAR}` 占位符插值**：
>   `configLoader.ts` 的 `resolveEnvReferences()` 仅对 `value.startsWith('env:')` 的字符串做 `process.env[ref.slice(4)]` 替换；
>   `keyStore.ts` 的 `resolveSingleRef()` 对非 `env:` 前缀直接返回错误 `不支持的密钥引用格式: … （仅支持 env:XXX）`。
>   写成 `"api_key_ref": "${HUAWEI_MAAS_API_KEY}"` 会被当普通字符串存进配置。
> - **环境变量缺失时静默保留原值**：`resolveEnvReferences()` 只在 `envValue !== undefined` 时替换，否则把 `"env:XXX"` 字面量原样留在 `merged` 里，不报错不告警（源码注释原话："未设置时保留原值，由使用方检查"）；
>   唯一的兜底报错发生在构造 Provider 时（`Src/Infra/Llm/Provider/providerBase.ts` 抛 `环境变量 X 未设置`）。
>   **待办**：`resolveEnvReferences` 应记录 warn（或由 §1.2 的启动校验强制非空），否则非 Provider 路径（如嵌入、通知类密钥）会带着 `env:` 字面量继续运行。
> - **PBKDF2 派生与"加密敏感配置项"无实现**：`Src/` 内无 `pbkdf2` / `createCipheriv` / `createDecipheriv` 任何引用，`node:crypto` 只被用于 SHA-256 摘要与随机数

> - **多 Key fallback 只在未接线的模块里**：`keyStore.ts` 的 `resolveKey()` 确实按 `refs[]` 顺序尝试并标 `isFallback`，
>   但 **整个 `Src/Infra/Security/keyStore.ts` 在 `Src/` 内 0 生产调用者**（2026-10-03 复检索：`Src/` 内除本文件自身外无任何 import；只有 `Tests/Infra/security.spec.ts` 引用），
>   因此运行期**不存在轮换/回退能力**；且 `registerKey()` / `scanAndRegisterRefs()` 均无装配点调用。
> - **泄露风险（现状 + 待办）**：`resolveEnvReferences` 在加载阶段就把真实密钥**写回 `merged`**，
>   任何 dump `config.merged` 的调试/日志路径都会带出明文（当前 `startServer()` 只打印 `env` 与 `configDir`，未主动泄露）；
>   脱敏函数 `getMaskedKey()` 在未接线的 keyStore 里。

## 4. 错误处理策略

### 4.1 错误分级

| 级别 | 名称 | 处理策略 |
|------|------|---------|
| ERROR | 可恢复错误 | 记录日志 + 通知相关组件 + 尝试恢复 |
| FATAL | 不可恢复错误 | 记录日志 + 保存状态 + 终止当前轮次 + 通知用户 |
| PANIC | 系统级崩溃 | 保存快照 + 紧急终止 + 通知管理员 |

### 4.2 关键错误场景

| 场景 | 级别 | 处理 |
|------|------|------|
| LLM 调用失败 | ERROR | 按 fallback 列表尝试下一个 Provider |
| 数据库写入失败 | ERROR → FATAL | 重试一次，仍失败则 FATAL |
| Token 余额不足 | ERROR | 暂停任务 + 通知 Director |
| Agent 连续失败 | ERROR | 3 次后开除 + 重新招募 |
| 仲裁死锁 | FATAL | 升级至 Regulation |
| 数据库损坏 | PANIC | 保存快照 + 紧急终止 |
| 账本守恒异常 | FATAL | 暂停交易 + 通知 Audit |

### 6.2 工具返回格式（强制）

所有工具必须返回下列形式，与 skill `source-code.md` 一致：

```json
{
  "role": "tool",
  "tool_call_id": "{operation_id}",
  "status": "success",
  "recoverable": false,
  "content": { /* 具体业务数据 */ },
  "effects": ["file.write:/Data/Workspace/.../a.ts"],
  "artifacts": [{"path":"...","hash":"sha256:...","size":1024}]
}
```

失败时：

```json
{
  "role": "tool",
  "tool_call_id": "{operation_id}",
  "status": "error",
  "recoverable": true,
  "error": {
    "code": "FILE_PERMISSION_DENIED",
    "message": "...",
    "details": { "path": "...", "required_perm": "..." }
  }
}
```

`recoverable` 决定 Loop 控制行为：`true` → 写 FailureFeedback 后重试/换策略；`false` → 直接风险退出。

1. **头部只放热工具 + 元工具**（`tool.search` / `tool.execute`），**会话内字节恒定**。

### 8.2 审批权限：决策池按请求方层级 + 法定人数（更正 §6.3 现状）

原 §6.3 登记的【需人工裁定】现状"CRITICAL ≥2 不同角色可被同一 `prime_director` 名义满足、客户端单操作者
一次点击补齐全部角色 ⇒ 实质等于单人同意"**已被修复**，现行规则：

1. **身份级去重**：不同角色必须由**不同身份**满足（Kuhn 二分匹配），同一人换角色名不再满足多角色；
2. **层级化决策池**：L2 请求（L1 自治域）→ 用户/L1/L0 **任意两方**；L1 或 L0 自身 → 用户 + L0（剔除自身）；
3. **请求方角色永不入池**（配置亦不可突破）；
4. **法定人数 2**（不同角色 + 不同身份）；
5. **系统角色只能自动拒绝**，永不自动通过；白名单自动审批仍走 `forceApprove` 并带 `autoApproved` 标记。

配置项约定：审批人默认构成改为 **用户 + L0 治理角色**（旧默认值含 L1 的 `prime_director` ⇒ 层级自审，已移除）。
`approverRoles` 仍只存在于代码默认值（未配置化），属待办（G-09/G-12 见清单）。

### 8.3 记忆治理：写入分层 + 语义碰撞（灵感源 §1.3 / §3.3）

`SharedMemory/memoryGovernance.ts` 落地三项：

| 规则 | 说明 |
|------|------|
| **键分层** | `regulation.` / `governance.` / `verdict.` / `rule.` / `arbitration.` → **治理键**；`internal_scratchpad` / `draft.` / `private.` / `reasoning.` → **隔离键**；其余 → 共享键 |
| **分层写入权限** | 治理键**仅 L0 / 所有者可写**；隔离键**任何人不得写入共享层**（中间过程物理隔离，防污染全局记忆） |
| **语义碰撞检测** | 先剥掉"允许/禁止"等模态词比较**命题相似度**（Jaccard ≥ 0.85），再判定**极性相反** → 阻断写入并发布 `CONFLICT_DETECTED`（含新旧记忆 ID，交仲裁者） |

> 实现注意：直接对**原句**做相似度会因模态词拉低重叠（实测 0.64 < 0.85 ⇒ 真冲突漏判），
> 必须比较"命题 + 极性"两个维度。

### 8.4 广播 = 治理机构向全员**写入共享记忆**

`regulation:broadcast` 的四类广播（`rule_update` / `emergency_alert` / `system_notice` / `arbitration_deadlock`）
全部为治理来源，故 `broadcast()` 需 L0 身份；且广播会写入 `globalWorkspace`（经 `writeGuard` 红线/乐观锁），
使"广播 = 所有 Agent 可见的记忆条目"成立。**记忆写入失败不阻断广播**（借鉴"监管失效不阻断主流程"）但留痕。

### 8.5 治理留痕事件族

新增 `EventType.GOVERNANCE_ACTION_RECORDED = 'governance:action_recorded'`（含客户端镜像），
强制四类元数据（全局唯一 ID / 时间戳 / 来源 Agent / 任务标识）+ `action` / `outcome` / `reason` / `targetIds`；
**拒绝同样留痕**（越权尝试是有价值的治理事实）。留痕内建于治理守卫，全部治理入口自动覆盖。
