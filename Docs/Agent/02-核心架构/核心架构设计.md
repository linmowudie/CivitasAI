## 1. 五层架构

系统采用五层架构，**单向依赖**：上层依赖下层，下层不可引用上层。

```
┌─────────────────────────────────────────────────┐
│              Interface（交互层）                   │
│  Web UI (React) · Electron IPC Bridge · REST API │
├─────────────────────────────────────────────────┤
│              Core（引擎层）                      │
│  Loop · Middleware · Model · Decision            │
│  （含 Agent Runtime / Orchestrator / Route）     │
├─────────────────────────────────────────────────┤
│              Services（服务层）                  │
│  Context · Supervision · Pipeline · Hook         │
│  Cache · Session · Retrieval                     │
│  LoopControl · TokenEconomy · Arbitration        │
│  Regulation · Audit · SharedMemory · EventBus    │
├─────────────────────────────────────────────────┤
│              Tools（工具层）                     │
│  Registry · Factory · Traits · Builtin · Custom  │
│  Builtin: Read / Write / Execute / Search / ...  │
├─────────────────────────────────────────────────┤
│              Infra（基础设施层）                 │
│  Fs · Db · Terminal · Logging · Time · Llm       │
│  Slm · Embedding · Hook · Config · Sandbox       │
│  Security · Watcher · Workspace · Env            │
│  DurableExecution（本 v2 新增）                  │
└─────────────────────────────────────────────────┘
```

> **层名统一**（对齐 skill `source-code.md`）：只允许使用 `Interface / Core / Services / Tools / Infra` 五个名字，禁止"核心层/决策层/业务层"等曾用名。

### 1.1 各层职责

| 层 | 职责 | 可依赖的层 | 禁止依赖 |
|----|------|-----------|---------|
| **Interface** | 用户交互入口：Web UI 渲染、Electron IPC 桥接（替代原 WebSocket）、REST API 路由 | Core, Services(只读查询) | Tools, Infra |
| **Core** | 系统核心引擎：Agent 运行时、上下文管理、主循环、编排决策 | Services, Tools, Infra | Interface |
| **Services** | 业务服务：Token 经济、仲裁、监管、审计、共享记忆、事件总线 | Tools, Infra | Interface, Core |
| **Tools** | 工具实现：LLM 调用、文件操作、代码执行、外部 API | Infra | Interface, Core, Services |
| **Infra** | 基础设施：数据库、日志、配置、加密、HTTP、向量存储 | 无（最底层） | 所有上层 |

### 1.2 层间通信规则

| 规则 | 说明 |
|------|------|
| 单向依赖 | 上层可调用下层导出的函数/类，下层**绝对不可**引用上层 |
| 跨层调用 | Interface 需要读取 Services 数据时，通过 Core 暴露的查询接口间接获取 |
| 事件通信 | 同层或跨层组件间异步通信统一走事件总线（Services/EventBus） |
| 接口契约 | 每层对外暴露的类型定义写在**该层的 types.ts**（2026-10-03 校准：代码实态为"就近模块 `types.ts`"，而非层根单文件）。当前仅 `Src/Infra/types.ts` 存在层根文件；`Interface` / `Core` / `Services` / `Tools` **均无层根 types.ts**，类型分散在 `Core/AgentRuntime/types.ts`、`Core/Decision/types.ts`、`Services/LoopControl/types.ts`、`Services/TokenEconomy/types.ts`、`Services/Arbitration/types.ts`、`Tools/Traits/toolSpec.ts` 等模块内。跨层共享的中间件类型契约已下沉 `Infra/Contracts/`（ADR-0006） |

### 2.1 命名规范声明（对齐 skill）

- 目录一律 **PascalCase**（如 `LoopControl/` `DurableExecution/`）
- 文件一律 **camelCase**（如 `loopEngine.ts` `loopConfig.json`）；配置扩展名统一 `.json`
- 例外：哈希目录 `{session_key}` 不受约束；`LoopConfig` 接口字段保持 snake_case（豁免 X2，见 Docs/Agent/10 §1.2.1）
- 例外（**2026-10-03 校准** 补列）：`Src/Infra/DurableExecution/schemas/` 下的 **`Checkpoint.ts` / `EffectRecord.ts` / `RecoveryPlan.ts` 为 PascalCase**，约定为"schema 文件名与导出类型同名"，不视为违规

## 3. 主循环序列（强制 10 步）

> **本小节是 `skill:source-code.md` 强制契约的直接投影，禁止任何顺序调换**。若需适配业务必须写 ADR 并获批。

### 3.1 关键约束

1. **②与③不可合并**：监管是内置安全机制，中间件是可扩展插件，两者共存时**中间件在外层、监管在内层**，禁止互相替代（对齐 skill）。
2. **⑤不可省略**：监管对上下文的检查在装配之后、调用之前，避免修改已装配的上下文造成缓存命中失效。
3. **⑧必须包裹 `wrapToolCall`**：幂等、审批门、限流、日志都挂在此，确保任何副作用先写意图日志（Docs/Agent/12 §4）。
4. **⑩不可交给模型自判**：“完成”判定必须由验证器确定，防止失效一。

### 3.2 递归派发协作模型（v2.2 修订）

> **修订说明**：原 T6 双层循环仅描述 Director → Worker 两级。实际架构为**递归分发的对等协作网络**：Prime Director 与 Partner 完全对等，均可接收用户输入、递归派发子 Agent、搭建工作流。治理三权（Regulator/Auditor/Arbitrator）不参与业务执行，仅在冲突时介入。

```
用户 ──→ Prime Director（主 Agent，分析请求）
              │
              ├─ 简单任务 → 自己做 / 委派 Worker
              ├─ 复杂任务 → 拆分给 Partner（合作者，独立决策体）
              │                  │
              │                  ├─ 自己做 / 委派 Worker
              │                  └─ 继续拆分给下一层 Partner（递归）
              └─ 固定流程 → 搭建 Assembly Node 流水线

治理层（不参与业务执行，仅在冲突时介入）：
  Regulator ←→ 检测冲突行为
  Auditor    ←→ 审计异常操作
  Arbitrator ←→ 裁决分歧
```

**角色权限分级（详见 Docs/Agent/10 §3.2）：**

| 级别 | 角色 | 权限 |
|:---:|------|------|
| L0 治理级 | Regulator, Auditor, Arbitrator | 全局读写、规则修改、Agent 管理、冲突裁决 |
| L1 入口级 | Prime Director, Partner | 接收用户输入、递归派发、搭建工作流 |
| L2 执行子级 | Worker, Reviewer, Assembly Node | 仅执行上级派发任务 |

**递归派发特有约束**：
- `trace_id` 跨 Agent 复用，新增 `parent_agent_id` 写入日志与事件；
- Token 预算上移为**入口级全局预算**，L1 Agent 侧为总量、L2 Agent 侧为分配额度；
- **⑩ 需额外检测**：互相回传死锁（A 等 B 的结果，B 等 A 的结果），命中时直接触发风险退出；⚠️ 2026-10-03 校准 **未接入主循环**：`detectDeadlock` 已在 `Services/Supervision/loopSupervision.ts` 实现，但**零生产调用者**（仅 `Tests/Runtime/runtime.spec.ts` 引用），`runIteration` 的 ⑩ 段不含死锁检测；
- **L2 Agent 不可接收用户输入**：入口仅接受 L1 级 Agent 的请求，子 Agent 请求路径需校验角色（当前入口为 Electron IPC 桥接，原 WebSocket 入口 2026-09-28 已删除，见下方校准注）；
- **工具可见性按 `requiredRoles` 白名单裁剪**（详见 Docs/Agent/10 §3.3.1），主循环 ④ 仅将角色可见工具传给模型。

> **⚠️ 权限声明校准（2026-09-22）**：
> - 上表 L0 "全局读写、规则修改、Agent 管理、冲突裁决"为**设计意图**：`regulator` 未出现在任何注册工具的 `requiredRoles` 中（`grep -rn "regulator" Src/Tools/` 命中 0），治理操作**无工具层落地形态**（详见 Docs/Agent/10 §3.3.1 同款注）。
> - "WebSocket 入口仅接受 L1 请求"**未实现**：原 `Src/Interface/WebSocket/wsHandler.ts` 与 `RestApi/chatApi.ts` 对入口消息**无任何角色校验**（`wsHandler.ts` 已于 2026-09-28 随 WebSocket 删除，现入口为 `Src/Interface/IpcBridge/ipcBridge.ts`，同样无角色校验）。
> - "工具可见性按 requiredRoles 裁剪"**已实现但形态略有不同**：`Src/Core/Loop/runIteration.ts` 的 **④ 段调用 `getVisibleToolsForRole(ctx.agentRole)`**（2026-10-03 校准：改为符号定位，原注的 `:290` 行号已漂移）；实际规则为 **`requiredRoles` 命中 ∪ 角色为 L0（非 FORBIDDEN 全可见）**（`toolFactory.ts` 的 `getVisibleToolsForRole`）；`trustLevel × dangerLevel` 矩阵（`isToolAllowed`）仅被零生产调用者的 `getVisibleTools`/`isToolVisible` 消费，**不在主循环路径上**。

### 4.2 接口定义

```typescript
// Infra/Contracts/middlewareTypes.ts（ADR-0006：原 Core/Middleware/types.ts 已删除，契约下沉至 Infra 共享内核）
type MiddlewareHook =
  | 'beforeAgent' | 'beforeModel' | 'wrapModelCall'
  | 'wrapToolCall' | 'afterModel' | 'afterAgent';

interface AgentMiddleware {
  name: string;
  hook: MiddlewareHook;
  priority: number;                       // 同钩子内排序，小的先执行
  canShortCircuit: boolean;

  // 单一钩子函数字段：签名随 hook 类型变化（HookFunction 联合类型），
  // 非 wrap 型返回 void | { shortCircuit, result? }，wrap 型接收 next(input) 完全控制后续链路
  execute: HookFunction;
}
```

> 钩子分派不由中间件对象自持 run/wrap 双方法，而是由 `Core/Middleware/middlewareRegistry.ts` 统一执行：pre/post 钩子走 `executePrePostHooks`，wrap 钩子走 `executeWrapHooks`（洋葱式组合）。

## 5. 上下文分区（缓存感知四级）

> **v2 修订**：严格对齐 skill `source-code.md` §上下文分区。旧版描述的 S=系统约束/L=长期记忆/M=对话历史 + "预留" 分区均不合规。

**核心原则**：**不变的内容在前，变化的内容在后**，以最大化 Prompt Cache 命中。

### 5.1 四级分区与两个正交系数

| 分区 | 含义 | 内容 | **预算上限**（`partitionCeilingRatio`） | **分件系数**（`tokenCoefficient`） | 变动频率 |
|------|------|------|------|------|---------|
| **S** Static | 静态区 | 系统提示词、不可变约束、角色定义 | **≤ 15%** | **0.05**（极低） | 极低（会话内不变） |
| **L** Low-freq | 低频区 | 工具 Schema、长期记忆、Skills | **≤ 15%** | **0.5** | 低（小时级） |
| **M** Mid-freq | 中频区 | 用户对话历史、LoopState 摘要 | **≤ 15%** | **0.3** | 中（轮次级） |
| **H** High-freq | 高频区 | Agent 输出、工具结果、本轮检索片段 | **≤ 45%** | **1.0** | 高（每轮） |

两个系数属于 **不同机制、不得混用**（v2.1 澄清，旧版曾将两者当同一个量）：

- **预算上限**（skill `source-code.md` §Token 预算体系）：约束每个分区**能占多少输入预算**，四项和 = 90%，剩 10% 为余量；超限→ 按评分裁剪；
- **分件系数**（skill §评分延迟压缩机制）：进入条目压缩评分的**第四维度成本折算因子**（S 区因 Prompt Cache 命中而实际只付 5% 价格），**不是百分比**。

**预算公式**（仅用于压缩评分）：
```
条目压缩评分 = 时间衰减 + 访问频率（反向加权）+ 语义相关性 + 分件系数
```

## 6. Agent 运行时生命周期

> **枚举同形修正（v2.1）**：本节旧版用中文态名（创建/就绪/执行/挂起…）描述状态机，与 DB 列 `agents.status` 的英文枚举不同形（违反 Docs/Agent/09 §1.1 “枚举三处同形”）。
> 现以 **`agents.status` 的 6 个规范值为唯一事实源**，中文仅作括号内展示名；并明确区分**两个层级**：`awaiting_approval` 与 `failed` **不是 Agent 态**，而是 Loop 态（`loops.phase` / `loops.stopped_reason`）。

```
creating(创建) → ready(就绪) → running(执行) ⇄ suspended(挂起)
     ↑                        ↓                        ↓
     │                    destroyed(销毁) ← expelled(开除) ←──┐
     └────────── 重新招募（新 agent_id，不复用旧实例）───────────┘

Loop 级（不是 Agent 状态列，存在 loops.phase）：
  running 内嵌：planning → acting → verifying →（awaiting_approval）→ …
  终态：completed | failed（失败原因写 loops.stopped_reason）
```

| 层级 | 合法取值 | 列名 |
|------|---------|------|
| **Agent 生命周期**（6） | `creating` `ready` `running` `suspended` `expelled` `destroyed` | `agents.status` |
| **Loop 阶段**（6） | `planning` `acting` `verifying` `awaiting_approval` `completed` `failed` | `loops.phase` |
| **Loop 退出原因**（7） | `success` `limits` `budget_soft` `budget_hard` `no_progress` `risk` `human_abort` | `loops.stopped_reason` |

> **⚠️ LoopPhase 实态校准（2026-10-03）**：上表的"Loop 阶段 6 值"目前是**规范态定义**，**运行时并不由它驱动**。代码里实际存在**三套** `LoopPhase`：
> 1. 6 值规范态：`Core/AgentRuntime/types.ts` 与 `Services/LoopControl/types.ts`（两处同名导出，**无 re-export 关系**）；

> 3. `planning` 仅作为 `Services/LoopControl/loopState.ts` 中 `createInitialLoopState()` 的初始值出现；`acting` / `verifying` / `awaiting_approval` **全仓无任何赋值点**（审批门 `approvalGate.ts` 不写 phase，仅用自身超时机制）。

### 6.1 状态转换规则

> 表中“状态”列均为 **Agent 层**（`agents.status`）；写“Loop 层”的行不变 Agent 态，只变 `loops.phase`。

| 当前状态 | 触发事件 | 目标状态 | 动作 | 实现状态（2026-10-03 校准） |
|---------|---------|---------|------|------|
| `creating` | 初始化完成 | `ready` | 分配 Token 钱包、加载角色 Prompt | ⚠️ `INIT_COMPLETE` 事件**无生产派发点**：`Core/AgentRuntime/agentFactory.ts` 直接赋值 `agent.status = 'ready'` 并写透 DB，**绕过状态机校验** |

| `running` | 验证器通过 + 风险退出未命中 | `ready` | 结算 Token、写成功 Checkpoint（Loop 层 → `completed`） | ✅ `TASK_COMPLETED`（`agentRuntime.ts`）；⚠️ `loops.phase` 不落库 |
| `running` | **命中审批门** | `running`（不变） | **仅 Loop 层 → `awaiting_approval`**；写 `PendingApproval` 到 DB，Agent 状态不变 | ⚠️ 审批门**不写 phase**：`Services/LoopControl/approvalGate.ts` 全文无 `phase` 赋值，`awaiting_approval` 态在运行时不存在 |

| `suspended` | 收到 `RESTORATION_ACK` | `running` | 恢复 State，从 `last_checkpoint_id` 续接 | ⚠️ `RESTORATION_ACK` 只是 EventBus 事件（`Services/Arbitration/restorationManager.ts`），**不驱动状态机**；`RESTORE` 无派发点 |
| `running` | 验证器失败 ≥ 上限 | `ready` | Loop 层 → `failed` + 写 `DiagnosticSummary`；Agent 本体不死亡 | ⚠️ 部分：`TASK_FAILED` 转换表支持，生产未见派发 |
| `expelled` | Director 发起重新招募 | `creating` | **新建 Agent 实例**（`agent_id` 不同，旧实例入 `destroyed`） | ⚠️ `RECRUIT` 事件**无生产派发点**；仅 `EXPEL` 由 `Services/Recruitment/recruiter.ts` 派发 |
| ~~任意~~ `ready` / `running` / `suspended` / `expelled` | 任务结束 + 无后续任务 | `destroyed` | 清理资源、归档 Trace | ⚠️ **2026-10-03 校准修正**：`stateMachine.ts` 的转换表里 **`creating` 态没有 `DESTROY` 转换**，故"任意"应为 `ready/running/suspended/expelled`；且 `DESTROY` 事件本身**无生产派发点** |

| 磁盘配额超限 | 按清理优先级依次淘汰，不阻断业务 ⚠️ 2026-10-03 校准 **未实现/目标态**：`Infra/Fs/quotaManager.ts` 仅有 `setQuota` / `canWrite` / `recordUsage` / `getUsage` / `scanDirectorySize` / `syncUsage` / `clearQuotas`，**无淘汰或按优先级清理的 API**；当前实际行为是 `canWrite()` 返回 false 即**拒绝写入**（清理优先级仅存在于 `Configs/dataStorage.json` 的声明中，无执行者） |

## 10. 模型调用契约（Model Call Contract）

> **v2 新增章**：对齐 skill `source-code.md` §模型调用契约。所有对 LLM 的调用必须满足下列硬性约束；违反任何一条均为代码门禁失败项。

### 10.1 超时

| 项 | 默认 | 可调范围 | 行为 |
|----|------|---------|------|
| 单次调用总超时 | **60_000 ms** | 10s – 300s | 超时→归为网络错误重试 |
| 流式首字节 | **10_000 ms** | 3s – 60s | 超时→中止并降级 |
| 流式相邻包间隔 | **15_000 ms** | 5s – 60s | 超时→中止 |

### 10.2 错误分类与重试

| HTTP / 错误 | 分类 | 重试 | 退避 | 处理 |
|-----------|------|------|------|------|
| **401 / 403** | Auth | ❌ 禁止 | — | **FATAL**，不重试，直接终止当前轮次 |
| **429** | RateLimited | ✅ 1 次 | 5s | 仍失败→降级到备选 Provider |
| **5xx**（非 503） | ServerError | ✅ 2 次 | 1s, 2s | 耗尽→终止本轮 |
| **503** | ServiceUnavailable | ✅ 1 次 | 直接降级 | 备选 Provider |
| **网络错误**（ECONNRESET/ETIMEDOUT） | Network | ✅ 2 次 | 1s, 2s | 耗尽→终止本轮 |
| **Schema 不匹配** | FormatError | ✅ 1 次 | 直接重试 | 仍失败→上报 FATAL |
| **内容安全命中** | ContentBlocked | ❌ 禁止 | — | 直接失败，写入安全事件 |

**重试耗尽后的统一行为**：终止当前轮次，写入 `FailureFeedback(category='external')`，交给 Loop 控制的 **⑩ 迭代判定**，避免默默推进。

> **⚠️ 未实现/目标态（2026-10-03 校准）**：上述"写入 FailureFeedback"**无任何生产写入点**——`Services/LoopControl/failureFeedback.ts` 的 `buildFailureFeedback` 仅有定义与再导出，调用者只在 `Tests/`。代码实际行为：`Core/Loop/runIteration.ts` 的 ⑥ 段在 `wrapModelCall` 分支拿到失败结果后，直接以 **`exitReason: 'risk'`** 短路退出本轮（不产出 `category='external'` 的可行动反馈）。待办：把重试耗尽接到 `buildFailureFeedback` 并按本句口径退出。

### 10.3 流式与非流式

- **默认流式**：`stream: true`；非流式仅用于已知返回极短的内部控制调用；
- 流式必须支持 **中途取消**（AbortSignal），取消时也写 EffectJournal；⚠️ 2026-10-03 校准 **"取消时写 EffectJournal"的桥接未实现**：`Core/Model/abortSignal.ts` 文件头虽声明承担该桥接，但全文件**无 `recordIntent` / `updateEffectStatus` 调用**，取消仅向下游传播 abort 信号。EffectJournal 的"先写意图再执行"目前发生在 ⑧ 的 `wrapToolCall`（`Services/LoopControl/middleware/toolSafetyGate.ts`）内，与流式取消无关联。
- 流式中间不能切换 `thinking/reasoning` 模式（对齐 Anthropic Extended Thinking 约束）。

## 11. Hook 系统

> **v2 新增章**：对齐 skill `source-code.md` §Hook 系统。Hook 与 §4 中间件不同：中间件面向 Loop 内部阶段；Hook 面向 **生命周期事件**，可供外部插件注入确定性脚本。

### 11.1 事件集合

| Hook 事件 | 触发时机 | 可否拦截 | 默认 fail 行为 | 实现状态（2026-10-03 校准） |
|----------|---------|---------|---------------|---------------|
| `UserInputReceived` | ① 之前 | ✅ 可 | fail-open | ✅ **唯一有生产派发点**（`Core/Loop/runIteration.ts` ① 段调 `dispatchHook('UserInputReceived', …)`，命中拦截即短路） |
| `SessionStart` | 会话创建 | ✅ 可 | fail-closed | ⚠️ 无生产派发点（仅在 `hookRegistry.ts` 的事件枚举/语义表中定义） |
| `PreToolExecute` | ⑧ 之前 | ✅ **可取消该工具** | fail-closed | ⚠️ 无生产派发点（⑧ 走 `wrapToolCall`，见 §3 校准） |
| `PostToolExecute` | ⑧ 之后 | ❌ 仅观察 | fail-open | ⚠️ 无生产派发点 |
| `ModelCallStart` | ⑥ 之前 | ❌ 仅观察 | fail-open | ⚠️ 无生产派发点 |
| `ModelCallEnd` | ⑥ 之后 | ❌ 仅观察 | fail-open | ⚠️ 无生产派发点 |
| `VerifierExecuted` | Verifier 返回后 | ❌ 仅观察 | fail-open | ⚠️ 无生产派发点 |
| `ApprovalRequested` | 审批门入队 | ❌ 仅观察 | fail-open | ⚠️ 无生产派发点 |
| `SessionEnd` | 会话结束 | ❌ 仅观察 | fail-open | ⚠️ 无生产派发点 |

> **⚠️ 校准（2026-10-03）**：**触发时机与默认 fail 行为两列是目标态**。枚举本身与 `Services/Hook/hookRegistry.ts` 逐字一致（9 事件；`SessionStart` / `PreToolExecute` fail-closed，其余 fail-open；handler 默认超时 5s；fail-closed 命中即 `intercepted`），但**全仓生产代码只派发 `UserInputReceived` 一个事件**，其余 8 个事件即使注册了 handler 也永不被触发。上表"触发时机"列不得读作已实现行为。

### 11.2 实现位置

> **2026-10-03 校准**：职责切分按代码实况改写（原"执行引擎在 `Infra/Hook/`（统一派发 + 超时 + 重试）"与实现相反）。

- **注册 + 派发 + 超时 + fail-open/closed 语义**：均在 `Services/Hook/hookRegistry.ts` —— `registerHookHandler` / `registerHookHandlers`（handler 默认 `timeoutMs = 5000`）与 `dispatchHook`（逐 handler 竞速超时，fail-closed 命中即返回 `intercepted`，fail-open 吞异常继续）。
- **`Infra/Hook/`**：仅提供一个通用重试工具 `hookExecutor.ts` 的 `executeHookWithRetry`（默认 10s 超时 / 1 次重试）与内置系统钩子 `Hook/System/auditHook.ts`。`main.ts` ⑬ 段只调用 `initHookExecutor()` 完成其初始化，**Hook 派发路径并未经过 `executeHookWithRetry`**（`hookRegistry` 不 import 它）。
- **待办（建议写 ADR）**：是否把"统一派发 + 超时 + 重试"下沉到 `Infra/Hook/`，让 `Services/Hook/` 只保留面向业务的注册/调度 API，以恢复本文原始分层意图。

### 11.3 与中间件的选择

| 需求 | 首选 |
|------|------|
| 项目内置控制 | 中间件 |
| 外部可插拔（用户自定义） | Hook |
| 需要取消后续行为 | 仅 PreToolExecute / UserInputReceived 可 |
