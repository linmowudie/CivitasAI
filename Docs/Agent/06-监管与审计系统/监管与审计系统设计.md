## 1. 监管局（Regulatory Authority）

### 1.1 职责边界

| 职责 | 说明 |
|------|------|
| 全局规则维护 | 制定、更新、发布《智能体行为准则》 |
| 跨域协调 | 处理跨任务/跨 Agent 的重大事件 |
| 广播通道 | 允许 Agent 提交重大异常报告，全局广播通知 |
| 最终裁决 | 仲裁庭死锁时，作为最终裁决方介入 |
| 紧急干预 | 系统级异常时强制终止/重启 Agent |

### 1.2 核心组件

| 组件 | 实现（函数式模块） | 职责 |
|------|------|------|
| 行为准则管理器 | `initBehaviorCode` / `addRule` / `removeRule` / `updateVersion` / `checkViolation`（`Regulation/behaviorCode.ts:94,148,159,169,125`） | 加载/更新/发布行为准则 |
| 广播通道 | `broadcast(params)` / `acknowledge(broadcastId, agentId)`（`Regulation/broadcastChannel.ts:42,94`） | 管理全局广播消息 |
| 紧急干预器 | `emergencyIntervene({ type, reason, targetAgentIds? })`（`Regulation/regulatoryAuthority.ts:105`） | 强制执行终止/重启操作 |
| 最终裁决器 | `issueFinalVerdict({ case_, reason, overrideVerdict? })`（`Regulation/finalArbiter.ts:37`） | 仲裁死锁时的降级裁决 |
| 监管局主入口 | `initRegulatoryAuthority` + 上述能力代理（`Regulation/regulatoryAuthority.ts:48`） | 聚合四模块对外出口 |

> ⚠️ 2026-09-22 校准：原表所列 `BehaviorCodeManager` / `BroadcastChannel` / `EmergencyIntervener` / `FinalArbiter` **均为类名写法，Src 中不存在这些类**；
> `Services/Regulation/` 与仲裁一样采用**函数式模块**（且无 `index.ts` 汇总出口，调用方直接 import 单文件）。

### 1.3 行为准则

```typescript
interface BehaviorCode {
  version: string;                     // 语义化版本号
  rules: BehaviorRule[];
  effectiveAt: number;                        // epoch ms
  publishedAt: number;                        // epoch ms
}

interface BehaviorRule {
  ruleId: string;
  category: 'safety' | 'communication' | 'resource' | 'cooperation';
  description: string;                 // 人类可读规则描述
  condition: string;                   // 触发条件（结构化表达式）
  action: 'warn' | 'restrict' | 'forbid' | 'report';
  severity: 'low' | 'medium' | 'high' | 'critical';
  enforceable: boolean;                // 是否可自动执行
}
```

**默认行为准则（Phase 1 最小集）：**

| 规则 | 类别 | 动作 | 可执行 |
|------|------|------|--------|
| 禁止 Agent 越权访问其他 Agent 私有上下文 | safety | forbid | ✓ |
| 禁止通过 Prompt 注入篡改仲裁/审计逻辑 | safety | forbid | ✓ |
| Worker 连续 3 次交付失败须被开除 | cooperation | report | ✓ |
| 重大异常须上报监管局 | communication | report | ✓ |
| Token 消耗超预算须申请补充 | resource | warn | ✗ |

> **2026-09-22 校准**：第 3 行原写 `enforce`，与代码不符——`behaviorCode.ts:67-70` 的 `cooperation-001` 实际 `action: 'report'`，
> 且 `RuleAction` 联合类型只有 `'warn' | 'restrict' | 'forbid' | 'report'`（`behaviorCode.ts:17`），**无 `enforce` 取值**。
> "连续失败即开除"目前只上报、不自动执行；实际开除动作仍属目标态（Docs/Agent/02 §状态机引用 `supervision.agentConsecutiveFailuresToExpel`，该键亦无代码消费）。
> 表内规则与 `DEFAULT_RULES`（`behaviorCode.ts:44`）逐条对应；违规判定目前是 `checkViolation` 的关键词匹配（`:132-138`），非条件表达式求值。

### 1.4 广播机制

```typescript
interface BroadcastMessage {
  broadcastId: string;
  type: 'rule_update' | 'emergency_alert' | 'system_notice' | 'arbitration_deadlock';
  priority: 'normal' | 'high' | 'critical';
  
  title: string;
  content: string;
  
  // 目标范围
  targetScope: 'all' | 'specific_agents' | 'specific_role';
  targetAgentIds?: string[];
  targetRole?: string;
  
  // 要求
  requiresAck: boolean;                // 是否需要确认收到
  ackDeadline?: number;                // 确认截止时间（epoch ms）
  
  publishedAt: number;                        // epoch ms
  publishedBy: 'regulatory_authority';

  acks: Map<string, number>;           // agentId → ackTime（原表缺失，2026-10-03 校准补齐）
}
```

> **2026-10-03 校准**（`Regulation/broadcastChannel.ts`，函数 `broadcast` / `acknowledge` / `getUnacknowledged`）：
> - 代码结构体另有 **`acks: Map<string, number>`**（agentId → 确认时刻），由 `acknowledge(broadcastId, agentId)` 写入，
>   `getUnacknowledged(agentId)` 依据它筛选未确认消息；
> - `broadcast()` 的**入参是相对毫秒 `ackDeadlineMs`**，函数内换算为 `ackDeadline = Date.now() + ackDeadlineMs`，
>   即接口里的 `ackDeadline` 是派生字段而非调用方直接传入；
> - `requiresAck` 默认 `false`、`priority` 默认 `'normal'`、`targetScope` 默认 `'all'`；
>   事件 `BROADCAST_MESSAGE` 的 payload **不含 `ackDeadline`/`acks`**（ACK 状态只活在 `broadcastChannel` 的进程内 `messages` Map 里）。
> - **命名口径【需人工裁定】（2026-10-03 校准）**：仓内存在**两套 `UserRole` 枚举**——
>   `Infra/types.ts` 用 `'regulator'`（与 `Configs/security.json`、`Infra/Config/configValidator.ts` 一致），
>   `Services/LoopControl/types.ts` 用 `'regulatory_authority'`（`broadcastChannel.ts` 的 `publishedBy` 亦取该拼写）。
>   同一治理主体跨层拼写不同，字符串比对（审批角色、广播来源）时易错配。
>   **待办**：或本文长期声明"两套拼写各自归属不同子系统"，或由代码统一为单一枚举（建议后者，另开修复项）；本文按现状保留两种写法。

```
Arbitration → Regulation: escalateDeadlock(case_, reason)   // regulatoryAuthority.ts:96（原写 escalate(caseId) 不存在）

```

> **2026-10-03 校准（死锁判定口径）**：`Arbitration/tribunal.ts` 的 `reasonVerdict` 只做**多数决汇总**，
> 死锁唯一来源是 `isDeadlocked = Object.keys(verdictCounts).length === 3`（三位仲裁员给出**三种不同裁决**），
> 命中后置 `c.status = 'deadlocked'` 并在 `ARBITRATION_VERDICT` 的 payload 里带 `isDeadlocked`；
> **没有**任何"裁决超时 120 s"的计时判定——`Configs/arbitration.json` 的 `deadlockTimeoutSec`（120）在 `Src/` 中零读取点
> （仅 `Client/src/config/configSchema.ts` 作为可编辑项列出）。⚠️ 超时触发死锁属目标态。

### 1.6 紧急干预

| 干预类型 | 触发条件 | 动作 |
|---------|---------|------|
| 强制终止 Agent | Agent 行为严重违反行为准则 | 立即冻结 + 销毁 Agent |
| 暂停全局任务 | 系统级异常（如 Token 大面积异常消耗） | 暂停所有非核心 Agent |
| 强制重启 | 系统状态不可恢复 | 保存快照 → 重启核心组件 |
| 规则紧急更新 | 发现新的安全漏洞 | 立即发布新规则 + 广播 |

> **2026-09-22 校准**：入口是 `emergencyIntervene({ type, reason, targetAgentIds? })`（`regulatoryAuthority.ts:105`），
> `InterventionType` = `'force_terminate' | 'pause_all' | 'force_restart' | 'rule_emergency'`，与上表四行一一对应。
> 现状**只发布 `EMERGENCY_INTERVENTION`（critical）+ 同步广播 `emergency_alert`**，Src 中无该事件的订阅方，
> 故"立即冻结 + 销毁 Agent""保存快照 → 重启核心组件"等动作**未执行**（`record.executed` 仅表示事件发布成功）。

> **2026-10-03 现状记录 + 待办【需人工裁定】：监管局角色没有工具执行通道**
> - `regulator` 出现在 `Configs/security.json → security.trustLevels.systemRoles` 与 `Infra/types.ts` 的 `UserRole`，
>   但**全部已注册工具的 `requiredRoles` 声明中无一包含 `regulator`**（`Tools/Builtin/{Execute,Read,Write,Search}`、
>   `Tools/Builtin/Plan/todoWriter.ts`、`Tools/Custom/{agentRecruiter,submitForReview}.ts`）；
> - `Tools/Registry/toolRegistry.ts` 的 `requiredRoles` **硬校验**在 `Tools/Factory/toolFactory.ts` 的 L0 兜底**之后**仍生效
>   （L0 兜底只放开**可见性**，不放开**执行**）→ regulator 运行时调用任何工具都会拿到 `ROLE_FORBIDDEN`；
> - 唯一把 regulator 当治理角色使用的代码是 `Tools/Custom/agentRecruiter.ts` 的 `GOVERNANCE_ROLES` 常量（招募资格判定），与干预执行无关；
> - 影响：本节"冻结/销毁/暂停/重启"与 §5.3 的"冻结钱包 / 临时禁用工具 / 下发换策略指令"**都不可能经工具通道落地**。
> - **待办（二选一，需产品与安全裁定）**：① 在本文 §1.6/§5.3 正式声明"监管局不经工具通道执行，干预由内部函数与事件承担"；
>   ② 给 `toolRegistry` 执行闸补 L0 兜底对称（与 Docs/Agent/05 执行闸不对称条目同源，另开修复项）。在裁定前，上表"动作"列**全部按目标态理解**。

### 2.3 异常检测规则

#### 规则 1：滚动窗口超限

```
每 5 秒检查一次所有活跃 Agent：          // ⚠️ 未实现：无周期调度器，仅由调用方驱动（2026-10-03 校准）

for each agent:
    windowConsumption = sum(consumptions in last 5 minutes)
    budget = agent.tokenBudgetPer5Min  // 默认 10000
                         // ⚠️ 未实现：预算为**全局单值**，无按 Agent 私有预算（2026-10-03 校准）
    
    if windowConsumption > budget × 0.8:
        trigger ALERT_LEVEL_WARNING
    if windowConsumption > budget:
        trigger ALERT_LEVEL_CRITICAL → 冻结 Agent
```

> **2026-10-03 校准（规则 1 现状）**：
> - **无调度器**：`anomalyDetector.checkRollingWindow(agentId)` 只被 `resourceAuditBureau.monitorAgent()` **同步调用**，
>   而 `monitorAgent` 在 `Src/` 生产链路**零调用方**（仅 Tests）；`Configs/economyRules.json` 的 `rollingWindow.checkIntervalSec`（5）
>   在 `Src/` 中无读取点（仅 `TokenEconomy/types.ts` 的 `RollingWindowConfig` 声明）→ "每 5 秒检查一次"属目标态。
> - **按 Agent 预算未实现**：`checkRollingWindow(agentId)` **不接受预算入参**，实际预算取 `anomalyDetector.ts` 的
>   `DEFAULT_CONFIG.rollingBudgetTokens = 10000`（全局单值，所有 Agent 同额度）；
>   `economy.rollingWindow.tokens` / `.windowSec` 亦无读取点（窗口时长同样是 `DEFAULT_CONFIG.rollingWindowMs` 的 5 分钟字面量）。
> - **判定顺序**：代码先判 `> budget`（critical）再判 `> budget × 0.8`（warning）且命中即 `return`，
>   两档互斥，不会同时产出两条告警；告警还受同 Agent 同类型 30 s 冷却期抑制（见 §5.1 防风暴第 2 道）。

#### 规则 2：偏离均值

```
每完成一次 LLM 调用后检查：

if 该 Agent 的近 10 条消耗记录不足 3 条:
    return 不判定            // ⚠️ 样本守卫（2026-10-03 校准补齐）
recentAverage = average(last 10 rounds consumption)
if recentAverage == 0:
    return 不判定            // ⚠️ 均值为 0 亦跳过（同上）
currentConsumption = this round consumption

if currentConsumption > recentAverage × 3:
    trigger ALERT_LEVEL_WARNING
    
if currentConsumption > recentAverage × 5:
    trigger ALERT_LEVEL_CRITICAL → 冻结 Agent
```

> **2026-10-03 校准（规则 2 现状）**：`anomalyDetector.checkDeviation` 先取 `records.slice(-10)`，
> **`recent.length < 3` 直接 `return ok(null)`**（样本不足跳过判定），**均值为 0 同样跳过**；
> 倍数取 `DEFAULT_CONFIG.deviationWarnMultiplier = 3` / `deviationCriticalMultiplier = 5`（与伪代码同值，但不读配置）。
> 原伪代码未写这两道守卫——照原伪代码复现会在冷启动阶段误报，故补齐。判定顺序同为 critical 先于 warning、命中即返回。

#### 规则 3：循环检测

实际实现（`Audit/anomalyDetector.ts:130-155`，调用方为 `resourceAuditBureau.ts` 的 `monitorAgent(agentId, tokens, outputFingerprint?)`）：

```
每轮由调用方传入输出指纹 outputFingerprint（未传则跳过本规则）：

fingerprints = 该 Agent 保留的指纹序列（长度上限 loopConsecutiveRounds + 2，默认 7）

if fingerprints.length >= loopConsecutiveRounds:          // 默认 5
    recent = last(fingerprints, loopConsecutiveRounds)
    unique = distinct(recent)

    if unique.size <= 2:
        trigger ALERT_LEVEL_CRITICAL（loop_detected）→ 冻结 Agent
```

> **2026-09-22 校准**：上方原设计的"两两余弦相似度 > 0.85 → warning、连续 5 次 > 0.85 → critical"**未实现**：
> - 判定依据是**指纹集合基数**（`new Set(recent).size <= 2`，阈值硬编码于 `anomalyDetector.ts:147`），Src 中无任何相似度计算；
> - 循环检测**只有 critical 一档**，无 warning；"连续 5 次"在代码里是窗口长度 `loopConsecutiveRounds = 5`，不是计数累加；
> - `audit.loopSimilarityThreshold`（0.85）仅被当作 `createAlert()` 的 `threshold` **实参**传入，
>   最终落在告警对象 `AnomalyAlert.threshold` 字段上作为展示值，**不参与判定**；
>   **2026-10-03 校准更正**：原文"塞进 payload"不准确——发布的 `ANOMALY_DETECTED` 事件 payload 只有
>   `{alertId, agentId, type, level, detail}`，**并不携带 threshold**，该值只存在于进程内告警对象里（`getAlerts()` 可见）；
> - 指纹相等即视为重复（精确匹配），因此"高度相似但不同"的输出不会被识别为循环。
>
> ⚠️ 余弦相似度分档属目标态，未实现（2026-09-22 校准）。

## 6. v3 补丁：治理层分层与权限（2026-10-04 新增）

> 本节由 AI 编码代理新增（2026-10-04），落地产品裁定 **"治理层只由 L0 承担，L1/L2 只做事"**；
> 实现细节与验收证据见 `Docs/Dev/治理层完善清单.md`（该目录为开发过程文档，不具规范效力）。

### 6.1 四类"审查"的职责边界（不可混淆）

| 职能 | 审什么 | 归属层级 | 是否治理动作 | 实现 |
|------|--------|---------|-------------|------|
| **reviewer 内容审查** | **生成内容**（产出质量/正确性） | L2（L1 编排域内） | ❌ 不是治理 | `Services/ReviewerAgent` |
| **audit 副作用审计** | **副作用行为**（写了什么/改了什么/花了多少） | L0 `auditor` | ✅ 是 | `Services/Audit` |
| **regulation 行为监管** | **行为正确性**（守不守规范、违规判定与执法） | L0 `regulatory_authority`(=`regulator`) | ✅ 是 | `Services/Regulation` |
| **arbitration 冲突裁决** | **冲突事实与责任** | L0 `arbitrator` | ✅ 是 | `Services/Arbitration` |

已核实 `Services/ReviewerAgent` 中不存在 `freeze / penalt* / behaviorCode / violation / audit / budget / sideEffect`
等治理动作引用 —— 内容审查与副作用/行为治理相互独立。

### 6.2 治理动作的角色门（`Services/Governance/governanceGuard.ts`）

凡治理动作入口一律接收显式 `actorRole`，并经 `requireGovernanceRole(actorRole, action)` 校验：

| 域 | 入口 | 需 L0 |
|----|------|-------|
| 审批 | `approvalGate.decideApproval` | 见 6.3（按请求方层级） |
| 审计 | `freezeAgent` / `unfreezeAgent` / `investigate` / `runPatrol` | ✅ |
| 仲裁 | `reasonVerdict` / `issueSuspension` / `consolidateKnowledge` | ✅ |
| 监管 | `emergencyIntervene` / `escalateDeadlock` / `addBehaviorRule` / `removeBehaviorRule` | ✅ |
| 广播 | `broadcastChannel.broadcast` / `regulatoryAuthority.broadcastMessage` | ✅ |

例外（刻意保留、非治理动作）：
- **系统到期自动解冻**（`freezeManager.checkAutoUnfreeze` → 内部 `applyUnfreeze`）—— 属 fail-safe 解除限制；
- **自动干预**（阈值驱动的检测，如 `validateBehavior` / `checkViolation` 判据查询）—— 监管的"检测"面可自动运行；
- **系统角色只能自动拒绝、永不自动通过**（`decideApproval`）。

### 6.3 审批决策池按**请求方层级**构造（层级相对规则）

| 请求方 | 决策池 | 法定人数 |
|--------|--------|---------|
| **L2**（worker/reviewer/assembly_node） | 用户 + L1 + L0（**L2 是 L1 自治域**，L1 有权参与） | **任意两方** |
| **L1**（prime_director/partner）自身 | 用户 + L0（剔除 L1） | 两方 |
| **L0** 自身 | 用户 + 另一 L0（剔除自身） | 两方 |

红线：**请求方角色永不进入决策池**（配置亦不可突破）；不同角色须由**不同身份**满足（Kuhn 二分匹配）。

### 6.4 知识沉淀 = 仲裁者的"史官"职责

依据灵感源《一些思考2》§4.5：裁决完成后由**仲裁者**清理全局上下文、提炼静态知识写入长期记忆。
故 `consolidateKnowledge()` 属治理动作，仅 L0（arbitrator）/ user 可执行。

### 6.5 治理动作统一留痕

依据灵感源 §1.2「全链路可追溯」，所有治理动作（**含被拒绝的越权尝试**）统一写入台账并发布
`governance:action_recorded` 事件，强制携带四类元数据：**全局唯一 ID / 时间戳 / 来源 Agent / 任务标识**。

### 6.6 监管理念（借鉴 `MongoTerminalAgent v2.0` supervisor 系统）

- 监管 = **干预/纠偏**，不是阻断；**监管失效绝不阻断主流程**；
- **全局开关 + 逐项开关**（本项目对应 `Configs/supervision.json`）；
- **阈值化可配置**，不硬编码布尔权限；
- **分层各管一类行为**（工具层循环 / 推理层停滞 / 路径错误 / 读去重 / 意图强化 / 终答自检）。
