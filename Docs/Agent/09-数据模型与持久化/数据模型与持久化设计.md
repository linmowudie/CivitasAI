# 数据模型与持久化设计

> 本文档定义 Civitas-AI 的 SQLite 数据库 Schema、数据生命周期和存储策略。
>
> **本文档 §2–§4 与 §8.2 是全部 DDL 的唯一事实源（Single Source of Truth）**。其他设计文档（含 Docs/Agent/11、Docs/Agent/12）**禁止内联 `CREATE TABLE`**，只能引用本文件的表名与列名；
> 表结构变更一律先改本文件，再回写引用方。开发速查入口见 `Docs/Agent/14-参数总典与接口契约/参数总典.md`。
>
> **可执行事实源**：本文件为**设计权威**，`Src/Infra/Db/migrations.ts` 为**可执行注册点**（唯一建表入口），两者必须逐表同步；不一致时以迁移代码为准并回写本文件（2026-09-22 校准）。
>
> **适用范围边界（2026-10-03 校准）**：本文**仅覆盖端侧三个 SQLite 库**（`civitas_main.db` / `civitas_events.db` / `civitas_memory.db`）及其"单进程内 `registerMigration` + `_migrations`"迁移体系（§6）。
> **服务端另有独立迁移体系与库表，不在本文 SSOT 范围内**：`Server/src/db/migrate.ts` 以 `Server/migrations/NNN_name.sql` **按文件名升序**执行，并对每条迁移记录 **sha256 checksum**（已应用文件内容被改动即拒绝启动）；`Server/migrations/001–005` 建 `users`/`refresh_tokens`/`user_settings`/`usage_events`/`memories`/`audit_log`/`verification_codes`/`user_devices`/`rate_limit_buckets`/`user_tasks`。端云由 `Src/Interface/RestApi/syncApi.ts` 对齐（`effect_journal.tool_call_id` 配对、`long_term_memory ↔ memories`、`chat_sessions ↔ user_tasks` 归档态）。
> - **现状记录**：端侧属主列 `owner_user_id` 与服务端 `userId` 的映射关系目前**无任何文档登记**。
> - **待办（需人工裁定）**：① 本文是否升格为"全栈 DDL SSOT"；② 若否，服务端表结构与端云字段映射须另立 `Docs/Server/*` 文档并在此处补链接。**未裁决前不得在本文内联服务端 DDL。**

### 1.1 DDL 全局约定（强制 · v2.1 新增）

| 约定 | 规则 | 反例（已修正） |
|------|------|---------------|
| **时间列类型** | 所有 `*_at` 列一律 `INTEGER`，存 **epoch 毫秒**；禁止 `TEXT` ISO-8601 与 `INTEGER` 混用 | v1 表 `created_at TEXT` / v2 表 `created_at INTEGER` 双标 |
| **时长列** | `*_ms` 后缀 + `INTEGER`；审批超时长用 `timeout_sec` + `INTEGER`（秒） | `time_limit_ms` 与 `timeout_ms` 两名并存 → 统一为 **`timeout_ms`** |
| **比例/评分列** | `REAL`，取值域 **0.0–1.0**，与 `Configs/**` 标度一致 | `quality_score INTEGER`（0–100）→ **`quality_score REAL`** |
| **金额列** | `REAL` + `_usd` 或明确语义名（`calculated_cost`/`tax_amount`/`net_deduction`） | — |
| **枚举列** | `TEXT`，存值与 TS 联合类型**完全同形**（不做大写化/小写化转换），取值写在行内注释中 | `phase` 存 `'awaiting_approval'` 而 TS 写 `AwaitingApproval` |
| **JSON 列** | 列名以 `_json` 结尾（数组/对象皆然）；TS 侧为已解析的结构体 | `decided_by TEXT` → **`decided_by_json TEXT`** |
| **布尔列** | `INTEGER` 0/1，命名 `is_*` 或 `*_enabled` | — |
| **外键** | 子表必须声明 `FOREIGN KEY ... ON DELETE CASCADE`；`PRAGMA foreign_keys = ON` 在连接初始化时开启 | `verifier_results`/`failure_feedbacks` 已有；`action_fingerprints` 原缺 → **仍未补**（2026-09-22 校准：`create_action_fingerprints` 该表无任何 `FOREIGN KEY`，且其在 **events** 库、`loops` 在 **main** 库，跨库外键 SQLite 不支持 → 改为应用层校验，列为待办）。⚠️ **例外见下条** |
| **外键例外（2026-10-03 校准）** | **运行期无写入方的父表不得作 FK**——FK 会让子表写入直接被约束拒绝 | `pending_approvals.loop_id` 的 `REFERENCES loops(loop_id) ON DELETE CASCADE` **已被 v24 `rebuild_pending_approvals_for_persistence` 主动移除**（重建 `pending_approvals_v24` 无 FK 子句后 RENAME，实测 `PRAGMA foreign_key_list(pending_approvals)` 为空）；动因：`loops` 运行期零 INSERT（仅 `recoveryScanner.ts` 读），保留 FK 会让审批 write-through 落库必然失败。<br>**现状记录 + 待办（需人工裁定）**：① 在 `loops` 真正落库前，审批与 Loop 的强绑定仅由内存队列保证；② 二选一裁决——把 `loops` 接入写入方并恢复级联 FK，或把本例外固化为长期约定。**未裁决前不得按"必须级联 FK"评审 `pending_approvals`** |
| **属主列（2026-10-03 校准新增）** | 个人数据表统一带 `owner_user_id TEXT NOT NULL DEFAULT 'local'`（未登录 `'local'`，登录后为服务端 `userId`），读写一律按当前属主过滤（`Src/Services/AccountScope/activeAccount.ts`） | v22 `add_owner_scope_to_personal_data`（10 表）、v21 `add_long_term_memory_owner`、v23 `ai_events`、v27 `session_todos`、v28 `add_agents_owner_scope` |
| **复合主键 / 表重建式迁移（2026-10-03 校准新增）** | SQLite 不支持修改主键，主键变更一律走"**建新表 → `INSERT ... SELECT` 迁移既有数据 → `DROP` 旧表 → `RENAME`**"，并在 `up` 开头用 `CREATE TABLE IF NOT EXISTS`（旧形状）兜底，以保证 `down` 之后 `up` 仍可重放（Gate G1） | v21 `add_long_term_memory_owner`：`long_term_memory_v21` → `long_term_memory`，既有行归入 `'local'` |
| **机械映射** | TS `camelCase` ↔ DB `snake_case` 由 repository 统一转换，**禁止人为改名** | `timeoutMs` ↔ `timeout_ms` |

> **历史豁免清单（2026-10-03 校准新增；豁免仅限下表已存在列，新增列一律不得豁免）**
>
> | 偏差 | 现存列 | 登记处理 |
> |------|--------|---------|
> | JSON 内容未以 `_json` 结尾 | `token_transactions.metadata`、`subtasks.input_context`/`output_schema`/`depends_on`/`required_tools`/`result`、`agents.allowed_tools`/`denied_tools`、`tasks.required_domains` | v1–v6 建表遗留；改名需表重建式迁移（见上"复合主键/表重建"约定），列为待办 |
> | 布尔列非 `is_*` | `verifier_results.pass`（v12 `create_verifier_results`）、`pending_approvals.auto_approved`（v24 `rebuild_pending_approvals_for_persistence` 新增，**新列亦未守约定，自 2026-10-03 起登记为偏差**） | 改名同为待办；此后新增布尔列一律用 `is_*` / `*_enabled` |
> | 时间列非 `*_at` | `ai_events.ts`（v23 `persist_ai_components`），另有序号列 `seq` | 新增偏差（2026-10-03 记录）：`ai_events` 为高写入事件流表，`ts` 为**外部约定（前端回放/IPC 契约）**列名；改名须与 `Src/Interface/EventStore/aiEventStore.ts` 同步，列为待裁决 |
>
> `domain_events.published_at`（§3.2）符合 `*_at` 约定，仅命名语义不同，不算豁免项。

## 2. 主数据库 Schema

### 2.1 任务表（tasks）

```sql
CREATE TABLE tasks (
    task_id TEXT PRIMARY KEY,              -- UUID
    session_key TEXT NOT NULL,             -- 会话标识
    trace_id TEXT NOT NULL,                -- 运行追踪 ID
    
    -- 任务信息
    user_request TEXT NOT NULL,            -- 用户原始需求
    route_mode TEXT NOT NULL,              -- 路由模式：DIRECT/DELEGATION/CONSORTIUM/ASSEMBLY_LINE
    status TEXT NOT NULL DEFAULT 'pending',-- pending/running/completed/failed/cancelled
    
    -- 复杂度评估
    estimated_tokens INTEGER,
    required_domains TEXT,                 -- JSON 数组
    coupling_score REAL,
    
    -- 结果
    final_result TEXT,
    quality_score REAL,                      -- 0.0–1.0；禁止 0–100 百分制
    
    -- 时间
    created_at INTEGER NOT NULL,
    started_at INTEGER,
    completed_at INTEGER,
    
    owner_user_id TEXT NOT NULL DEFAULT 'local',  -- 属主（2026-10-03 校准：v22 `add_owner_scope_to_personal_data` 补列，现共 14 列）
    
    FOREIGN KEY (session_key) REFERENCES sessions(session_key)
);

CREATE INDEX idx_tasks_status ON tasks(status);
CREATE INDEX idx_tasks_trace ON tasks(trace_id);
CREATE INDEX idx_tasks_owner ON tasks(owner_user_id);                  -- v22 已建
CREATE INDEX idx_tasks_session ON tasks(session_key);   --（迁移未建，待办：v3 `create_tasks` 仅建 status/trace 两个索引）
```

### 2.2 子任务表（subtasks）

```sql

    subtask_id TEXT PRIMARY KEY,           -- UUID (assignmentId)
    task_id TEXT NOT NULL,
    trace_id TEXT NOT NULL,
    
    -- 任务定义

    input_context TEXT,                    -- JSON
    output_schema TEXT,                    -- JSON Schema
    assigned_agent_id TEXT,
    
    -- 约束
    max_iterations INTEGER NOT NULL DEFAULT 30,   -- 同上：仅作 fallback，实际由 loopConfig 注入
    timeout_ms INTEGER,
    token_budget INTEGER,
    
    -- 状态
    status TEXT NOT NULL DEFAULT 'pending',-- pending/assigned/running/completed/failed
    result TEXT,                           -- JSON
    quality_score REAL,                      -- 0.0–1.0；禁止 0–100 百分制
    failure_count INTEGER DEFAULT 0,
    failure_reason TEXT,
    
    -- 依赖
    depends_on TEXT,                       -- JSON 数组
    required_tools TEXT,                   -- JSON 数组
    
    -- 时间
    created_at INTEGER NOT NULL,
    started_at INTEGER,
    completed_at INTEGER,
    
    owner_user_id TEXT NOT NULL DEFAULT 'local',  -- 属主（2026-10-03 校准：v22 `add_owner_scope_to_personal_data` 补列，现共 19 列）
```

### 2.3 Agent 表（agents）

```sql
CREATE TABLE agents (
    agent_id TEXT PRIMARY KEY,             -- 格式：{role}-{uuid8}
    trace_id TEXT NOT NULL,
    parent_agent_id TEXT,                  -- 招募者 ID
    
    -- 角色配置
    role TEXT NOT NULL,                    -- prime_director/partner/worker/reviewer/assembly_node/arbitrator/auditor/regulator（与 loopConfig.roleOverrides 键一一对应，Docs/Agent/10 §2.8）

    task_prompt TEXT,

    max_iterations INTEGER DEFAULT 30,     -- 仅作 fallback；实际值由 `loopConfig.roleOverrides[role].max_iterations` 在创建时写入
    timeout_ms INTEGER,
    
    -- 安全配置
    trust_level TEXT NOT NULL DEFAULT 'L1',-- L0/L1/L2
    sandbox_enabled INTEGER DEFAULT 1,
    
    -- 状态
    status TEXT NOT NULL DEFAULT 'creating',-- creating/ready/running/suspended/expelled/destroyed
    failure_count INTEGER DEFAULT 0,
    
    -- 时间
    created_at INTEGER NOT NULL,
    destroyed_at INTEGER,
    
    owner_user_id TEXT NOT NULL DEFAULT 'local',  -- 属主（2026-10-03 校准：v28 `add_agents_owner_scope` 补列，现共 17 列）
```

## 6. 迁移策略

> **2026-09-22 校准**：本节原写"单 `version: 1` 全量建表 + 失败自动回滚"，与 `Src/Infra/Db/migrations.ts` 实际契约不符，现按代码更正。
> **2026-10-03 校准**：接口字段与 API 集合**复核后仍逐字一致**；本节全部 `migrations.ts:行号` 锚点改为**按符号名 / 迁移 `name` 锚定**（v20–v28 插入使行号整体漂移 2–318 行），并补 §6.1 版本号冲突门禁、更正 §6.2 回滚语义与失败处理。

**契约（`migrations.ts` 的 `export interface Migration`）：**

```typescript
export interface Migration {
  readonly version: number;
  readonly name: string;                   // 如 'create_sessions'（非 description）
  readonly up: string;                     // SQL 语句（可多语句：建表 + 建索引）
  readonly down: string;                   // 回滚 SQL —— 必填，非可选
  readonly database?: 'main' | 'events' | 'memory';  // 省略时默认 main（`getDbForMigration()`：`migration.database ?? 'main'`）
}
```

**登记方式：按表逐版本注册**，不存在"一次性全量建表"的 version 1：

```typescript
registerMigration({ version: 1, name: 'create_sessions', database: 'main',
  up: `CREATE TABLE IF NOT EXISTS sessions (...);`,
  down: `DROP TABLE IF EXISTS sessions;` });
// 每张表一条：main v1–v28、events v1–v3、memory v1；
// registerMigration() 入栈后按 version 升序排序（即“物理位置 ≠ 执行顺序”，见 §3.2 注）
```

- `registerDefaultMigrations()` 幂等：模块级 `defaultsRegistered` 标志保证重复调用只注册一次。
- `initMigrations()` 在 **main / events / memory 三库各建一份 `_migrations`**（`version INTEGER PRIMARY KEY, name TEXT NOT NULL, applied_at TEXT NOT NULL DEFAULT (datetime('now'))`）。
  → **版本号按库独立**：`main` 的 v1 是 `create_sessions`，`events` 的 v1 是 `create_events`，`memory` 的 v1 是 `create_memory_entries`，三者互不冲突（但同号带来 §6.2 的回滚歧义风险）。
- `migrateUp()`：遍历全部迁移 → 按 `database` 经 `getDbForMigration()` 解析目标连接 → `isApplied(db, version)` 未应用则 `db.exec(up)` 并写入该库 `_migrations`，返回本次应用条数。
- `migrateDown()`：仅从 **main** 库 `_migrations` 取 `MAX(version)` 那一条 → `migrations.find(m => m.version === lastMigration.version)` → 目标库执行 `down` → 删除该库版本记录。
  ⚠️ **风险面（2026-10-03 校准扩大）**：`find` **只按 version 匹配、不区分库**，而 main / events / memory 三库**各自都存在同号版本**（main v1 `create_sessions` ↔ events v1 `create_events` ↔ memory v1 `create_memory_entries`；main v2 `create_agents` ↔ events v2 `create_action_fingerprints`；main v3 `create_tasks` ↔ events v3 `create_domain_events`），因 `migrations` 数组按 version 升序稳定排序，命中者为**先注册的那一条**，跨库回滚可能命中错误迁移。建议改为按 `name` 或 `database + version` 双键匹配 —— 列为待办加固项。
- 查询 API：`getAppliedMigrations(db)` / `getCurrentVersion(db)`（参数默认 `'main'`）；测试用 `clearMigrations()` 重置内部数组与幂等标志。

### 6.1 版本号冲突门禁（2026-10-03 校准新增）

`initMigrations()` 在 `registerDefaultMigrations()` 之后、建 `_migrations` 之前，用 `` `${database ?? 'main'}:${version}` `` 作键构建 `Map` 做**同库版本号冲突检测**：

- 命中冲突 → 返回 `err('迁移版本号冲突：<key> 同时被 "<prev>" 与 "<name>" 使用（后者将被静默跳过）。请改用新的版本号。', 'FATAL')`；
- 该错误经 `Src/main.ts` 转成 `throw new Error(...)` **终止启动**（见"迁移执行"）；
- 回归测试锚点：`Tests/Infra/db.spec.ts` 的 "迁移版本号冲突必须报错" 用例。

**门禁存在的理由**：若不加检测，后注册的同版本迁移会被 `isApplied()` 判为"已应用"而**静默跳过**——迁移没跑、schema 仍是旧版，是最难察觉的一类故障（历史上 FE-027 的 v25 险些撞 FE-004 已占用的 v24，`migrations.ts` 的 v25 段注释自证）。

**登记规则（强制）**：① 新迁移必须取该库**未占用**的号；② 版本号**按库独立计数**，main/events/memory 各自递增；③ 加迁移前先核对 §1 的登记表与 `_migrations` 实测；④ 破坏性 `down` 须在 §6.2 分级表登记。

### 6.2 down 的破坏性分级（2026-10-03 校准新增）

Gate G1 的"可上可下（up/down 幂等）"只保证**可重放**，**不保证无损**。现网登记的 `down` 分三类：

| 级别 | 语义 | 实例（按迁移 `name` 锚定） |
|------|------|--------------------------|
| 无损 | `DROP COLUMN` / `DROP INDEX` / `DROP TABLE`（表内本无生产数据） | v22 `add_owner_scope_to_personal_data`、v24 `rebuild_pending_approvals_for_persistence`（down 重建**含 FK** 的 v22 形态，列齐全时可正常回退，但期间新增的 `tool_call_id`/`tool_name`/`session_id`/`auto_approved` 值会丢失）、v25、v26、v27、v28 |
| **有损（删数据）** | `DROP TABLE` 直接吞掉已落库的业务数据 | **v21 `add_long_term_memory_owner`：`down: DROP TABLE IF EXISTS long_term_memory` —— 回滚即删除全部长时记忆**；v17 `create_long_term_memory`、v15 `create_pending_approvals`、v16 `create_global_workspace` 同理 |
| 需备份 | 有损类回滚前必须先复制 .db | 上述有损项；但 §5.3 备份能力**当前未实现**，故实际不可安全回滚 |

> **现状记录 + 待办（需人工裁定）**：v21 的 `down` 是"删表"而非"反向重建回单列主键"，与 §8.2/§6 的幂等表述在语义上冲突（长时记忆自 2026-10-02 起已有真实数据）。须裁决：① 把 v21 `down` 改写为**反向表重建**（`INSERT ... SELECT` 回旧形状），还是 ② 明确"v21 之后禁止 down、只允许前滚"。**裁决前，运维口径一律按"有损、需备份、默认禁止执行 `migrateDown()`"处理。**

**迁移执行：**
- 系统启动 ⑥ 步调用 `initDatabase()` → `initMigrations()` → `migrateUp()`（`Src/main.ts` 的 ⑥ 数据库初始化段）；
- 失败语义（2026-10-03 校准更正）：`initMigrations()` / `migrateUp()` 在 Infra 层**返回 `err(..., 'FATAL')` 的 Result**；由 `Src/main.ts` 检查 `!ok` 后 **`throw new Error('迁移系统初始化失败: ...')` / `throw new Error('数据库迁移失败: ...')` 终止启动**——原文"返回 `err(...,'FATAL')` 即终止启动"表述不准确，两层职责现分开记述；
- **不会自动回滚**：`up` 未包裹事务（`migrateUp()` 直接 `db.exec(migration.up)`），失败时已执行的前序语句保留原样，需人工介入或显式调用 `migrateDown()`（原"迁移失败 → 回滚"表述作废）。
  ⚠️ 补充（2026-10-03 校准）：`Src/Infra/Db/transaction.ts` 已提供 `transaction()` / `eventsTransaction()` / `memoryTransaction()` 三个事务包装函数（含 SAVEPOINT 嵌套语义），但**除 `Src/Infra/Db/index.ts` 的再导出外无任何调用方**——包括 `checkpointStore.createCheckpoint()` 在内的写路径仍各自用 `db.transaction()`，迁移亦未使用。统一经此模块包装列为待办。

### 8.5 事务与持久化约束

- `effect_journal` 写入使用 `PRAGMA synchronous = FULL`；
- 其他表默认 `NORMAL`；
- `loops + loop_checkpoints + effect_journal` 写入 **必须同事务**，否则恢复时状态不一致；
- 写入失败重试 1 次，仍失败 → **上报 FATAL 并中止 Loop**（不允许默默丢）。

> **实现状态（2026-09-22 校准 · 2026-10-03 校准更新，前两条不再是同一步伐）**
>
> | 约束 | 实态 |
> |------|------|
> | ① `effect_journal` 写入 `synchronous = FULL` | ✅ **已生效（但粒度是"整库/连接级"而非"表级"）**：`Src/Infra/Db/database.ts` `initDatabase()` 取 `config.writeSynchronous ?? 'FULL'` 打开 **main** 库，events / memory 固定 `'NORMAL'`，`openDatabase()` 逐连接执行 `PRAGMA synchronous = <mode>`；配置源 `Configs/durable.json → durable.effect.writeSynchronous = "FULL"`，读取点 `Src/main.ts`（⑥ 数据库初始化）。SQLite **没有表级 synchronous PRAGMA**，故本文语义须按"含 `effect_journal` 的 main 库整库 FULL"理解。⚠️ 副作用：main 库全部写入（含 `ai_events` 这类高频流）都吃了 FULL 的 fsync 代价，性能取舍列为待评估项 |
> | ② 其他表默认 `NORMAL` | ✅ 已按库生效：events / memory 两库 NORMAL；main 库其余表随整库 FULL（同上，无表级开关） |
> | ③ `loops + loop_checkpoints + effect_journal` 同事务 | ❌ **未实现**：`Src/Infra/DurableExecution/checkpointStore.ts` `createCheckpoint()` 的 `db.transaction()` **只包裹 `loop_checkpoints` 单表插入**，未与 `loops` / `effect_journal` 同事务；且 `loops` 运行期零写入（§8.1），三表同事务在现形态下无从成立。仍列为待办加固项，语义要求见 Docs/Agent/12 |
> | ④ 写入失败重试 1 次、否则上报 FATAL | ⚠️ 部分相符：`effectJournal.recordIntent()` 满盘（`database disk image` / `disk full`）时返回 `err(..., 'FATAL')` 拒绝新副作用（DUR-006），但**无统一的"重试 1 次"包装**，各写路径自行返回 ERROR/throw；`Src/Infra/Db/transaction.ts` 的统一事务包装器**至今无人调用**（§6 末注）。统一重试/FATAL 上报策略列为待办 |
