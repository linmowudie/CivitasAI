# Agent/12 · 持久执行与恢复设计（Durable Execution & Recovery）

> **本文档定位**：补齐 Loop Engineering 第五阶段"持久编排循环"的基础设施缺口。让 Civitas-AI 的 Agent Loop **能在进程崩溃、部署重启、机器断电后从上一个成功步骤续接**，而不是从头开始。
>
> **审查依据**：`Docs/99-审查记录/设计审查报告-Loop与Harness工程.md` §4.2 / §5.13。
>
> **业界对标**：Matt Van Horn "第五阶段循环"、Temporal / AWS Step Functions Durable Execution 模式、LangGraph Checkpointer。

---

## 1. 为什么必须做

**当前设计的致命缺口**（详见审查报告 §4.2）：

- 进程重启 → 运行中 Agent 状态全丢
- 长时间任务（>1 小时）跨部署 → 从头再来
- 已经发出外部副作用（写文件、调 API、发消息）后崩溃 → 重启后**重复执行**
- 只在容器里运行 ≠ correctness，只是 uptime

**判定标准**：**如果 Agent 循环会调用非幂等外部工具，那么没有 Durable Execution = 没有生产可用性**。

Civitas-AI 的 Worker 会写文件、执行命令、跨 Agent 通信 —— 完全命中此判定。

## 2. 设计原则

| # | 原则 | 说明 |
|---|------|------|
| D1 | **Every Effect is Logged Before It Happens** | 副作用发生前必须先写意图日志；崩溃后可根据日志判断"是否已发生" |
| D2 | **Idempotency by Design** | 所有可重试步骤必须携带幂等键；相同键第二次执行返回首次结果 |
| D3 | **Checkpoint After Every Successful Step** | 每个 iteration 末尾原子写入 `LoopState` + `artifact_manifest` |
| D4 | **Resume ≠ Replay** | 恢复时从 `lastCheckpointId` 加载 State，不重放消息历史 |
| D5 | **Recovery Must Be Explicit** | 系统重启后不自动 resume，必须经"恢复决策"确认（防雪崩） |
| D6 | **Durable ≠ Fast** | Checkpoint 落盘走 fsync；不接受 fire-and-forget |

> **⚠️ 未实现（2026-09-22 校准 · 2026-10-03 校准更新）**：D6 的 **fsync 分支全未落地** —— `Src/Infra/DurableExecution/` 目录下无任何 `fsync`/`fdatasync` 调用（全仓 fsync 仅存在于 `Src/Infra/Fs/atomicWrite.ts` 的 `atomicWrite()` 内 `fsyncSync` 调用处，而 DurableExecution 从不 import 它）。**但 PRAGMA 级持久性结论已反转（2026-10-03 校准）**：原"`effectJournal.ts` 头注释声称 synchronous = FULL、实为全局 NORMAL"不再成立 —— `Src/main.ts` 启动 ⑥ 步现读取 `durable.effect.writeSynchronous`（默认 FULL）并注入 `initDatabase()`；`Src/Infra/Db/database.ts` 的 `openDatabase()` 对 **main 库（effect_journal 所在库）设 FULL**，events/memory 库仍 NORMAL。显式 `wal_checkpoint`/fsync 仍缺，但其语义已由 synchronous=FULL 覆盖（详见 §5.3 ⑥ / §10 注）。本文其余各处"写 + fsync"在**显式刷盘**层面按此口径理解为**目标态**。

## 3. 三层持久化架构

```
┌──────────────────────────────────────────────┐
│  L3 Checkpoint Layer（每轮末尾快照）         │  ← 恢复入口
│      loop_checkpoints 表                     │
├──────────────────────────────────────────────┤
│  L2 Intent Log Layer（副作用前写意图）       │  ← 判定"是否已执行"
│      effect_journal 表                       │
├──────────────────────────────────────────────┤
│  L1 Event Sourcing Layer（全量事件流）       │  ← 审计与回放
│      Events 库（Agent/07 号文档定义）              │
└──────────────────────────────────────────────┘
```

**三层职责严格分离**：
- **L1 事件流**只写不删不改，是审计真源，性能可慢；
- **L2 意图日志**是"崩溃后到底做没做"的判定依据，必须强一致；
- **L3 快照**是恢复入口，允许丢弃，从 L2 重建。

> **⚠️ 库归属与 L1 真源现状（2026-10-03 校准）**：
> - **库归属（事实）**：`loops` / `loop_checkpoints` / `effect_journal` / `idempotency_cache` 四表均在 **`civitas_main.db`**（`Src/Infra/Db/migrations.ts` v9–v11，`database: 'main'`）。但 `Src/Infra/Db/database.ts` 头注释仍写"civitas_events.db：事件溯源 + effect_journal（仅追加）"，与 DDL/PRAGMA 实现自相矛盾 —— **待办：更正代码注释；后续严禁按该注释把 journal 迁库**（会破坏 §5.3"②③④ 同事务"前提）。
> - **L1 真源【需人工裁定·登记】**：`events` 与 `domain_events` 两表的 DDL 均声明在 events 库，但 `Src/` 内**无任何写入方**（`INSERT INTO events` / `INSERT INTO domain_events` 零命中）。实际事件持久化落在 **main 库 `ai_events`**（migrations v23 建表 + `Src/Interface/EventStore/aiEventStore.ts` 写入 + `Src/main.ts` 订阅）；工具调用同时出现在 `ai_events.agent:tool_call_result` 与 `effect_journal`，由 `Src/Interface/RestApi/syncApi.ts` 按 `tool_call_id` 配对去重（L1/L2 双写现况，见 §8.1 注）。上图"L1 = Events 库"与"审计真源"的所指（events 库 vs `ai_events`）**待裁定**，裁定前本图按**目标态**理解。

## 4. 副作用意图日志（Effect Journal）

### 4.1 数据模型

```typescript
// Infra/DurableExecution/EffectJournal.ts
interface EffectRecord {
  effectId: string;              // = {operation_id} 复用全局 ID（`Docs/Agent/10 §1.2.1` 之外的全局契约）
  loopId: string;
  iteration: number;
  kind: 'tool_execute' | 'file_write' | 'http_call' | 'db_write'
      | 'agent_message_send' | 'token_debit' | 'external_api';   // 与 effect_journal.kind 注释同集合
  idempotencyKey: string;         // 由调用方提供或本层生成（算法见 §7.2）
  payloadHash: string;            // SHA-256(payload)
  status: 'INTENT' | 'EXECUTING' | 'SUCCEEDED' | 'FAILED' | 'UNKNOWN';
  result?: unknown;
  startedAt: number;               // epoch ms
  timeoutMs: number;               // 生效超时快照；默认 = `durable.effect.defaultTimeoutMs`（30000）
  completedAt?: number;            // epoch ms
  errorClass?: 'retryable' | 'non_retryable' | 'unknown';
  toolCallId?: string;             // 触发该副作用的工具调用 ID（FE-027，2026-10-03 校准补登）
}
```

> **`timeoutMs` 补登（v2.1）**：原 §4.3 的判定式 `startedAt < now - timeout` 引用了一个 `EffectRecord` 上不存在的字段。现明确：
> 超时时长是 EffectRecord 的**第 9 个字段**，写入时从 `durable.effect.defaultTimeoutMs` 取默认值（工具可在 `ToolSpec` 声明更长值），**作为快照固定下来**，后续配置热更新不得改变存量记录的判定基准。
> 对应列：`effect_journal.started_at` + `effect_journal.timeout_ms`（DDL 见 Docs/Agent/09 §8.2，v2.1 补列）。

> **`toolCallId` 补登（2026-10-03 校准）**：代码实际多出可选字段 `toolCallId?`（`Src/Infra/DurableExecution/schemas/EffectRecord.ts` 的 `EffectRecord`/`CreateEffectInput`，位于上文清单末尾、`errorClass` 之后）；对应列 `effect_journal.tool_call_id` 由 migrations **v25** 新增（含 `idx_effect_tool_call`），并被 `recordIntent()` 真实写入、被 `syncApi` 消费（与 `ai_events` 精确配对防重复计数，见 §3 / §13 注）。
> **属主维度【需人工裁定·登记】**：migrations **v22** 已给 `loops` / `effect_journal` / `pending_approvals` 等表加 `owner_user_id DEFAULT 'local'` 列，但 `EffectRecord` 类型**无此字段**、`recordIntent()` 的 INSERT **不写该列**（恒落默认值 `'local'`）；而 `syncApi` 读 journal 时**按 owner 过滤** —— 登录态下副作用记录将**读不到**。`recoveryScanner` 扫描不按 owner 过滤（跨账号生成 RecoveryPlan）；`loop_checkpoints` 则无 owner 列。持久执行域是否纳入账号隔离待裁定，详见 §13 注待办。DDL 归属仍指 Docs/Agent/09 §8.2，需同步 v22/v25 两列。

### 4.2 生命周期

```
调用副作用工具
   ↓
[1] INSERT EffectRecord(status=INTENT) ── fsync 落盘   ⚠️ fsync 未实现
   ↓
[2] UPDATE EffectRecord(status=EXECUTING)
   ↓
[3] 实际执行工具
   ↓
[4a] 成功 → UPDATE(status=SUCCEEDED, result=hash(result))   ⚠️ 实存原文（2026-10-03 校准，见下注）
[4b] 失败明确 → UPDATE(status=FAILED, errorClass=...)
[4c] 崩溃/超时 → 保持 EXECUTING（恢复扫描按 §4.3 判据将其改写为 UNKNOWN）
```

> **⚠️ 接线现状（2026-09-22 校准 · 2026-10-03 校准更新）**：
> - **实际链路（以代码为准）**：`Src/Services/LoopControl/middleware/toolSafetyGate.ts` 的 `createToolSafetyGateMiddleware()`（wrapToolCall 钩子）内，非 SAFE 分支走 `recordIntent()` → `updateEffectStatus({status:'EXECUTING'})` → `next()` 执行工具 → `updateEffectStatus({status:'SUCCEEDED'|'FAILED', result, errorClass})`。`effectJournal.ts` 的 `markExecuting()` / `markSucceeded()` / `markFailed()` 只是 `updateEffectStatus()` 的薄封装，在 `Src/` 中**零生产调用者**（仅测试自测）。上图 [2]/[4a]/[4b] 的"mark*"应读作 `updateEffectStatus` 直调（另见 §13 表首行）。
> - **审批时序**：DANGEROUS + IRREVERSIBLE 工具的真实顺序是 **审批门阻塞（人工确认/自动审批白名单通过）→ 写 INTENT → EXECUTING → 终态**，即 [1] 之前还有一道阻塞式审批，与文档四步图示不同（2026-10-03 校准）。
> - **fail-open → fail-closed 已闭合（2026-10-03 校准，原待办清偿）**：`recordIntent()` 返回失败时，安全门记 `logger.error` 后**直接返回 `status:'error'`、`recoverable:false` 并拒绝执行工具**，代码注释显式引用本文 §4"副作用必须先写 INTENT"。⚠️ **该 fail-closed 分支目前无任何测试覆盖**（见 §12 注）。
> - **[4a] 声明更正（2026-10-03 校准）**：代码把 `result_json` 存为**工具输出原文**（`updateEffectStatus()` 对 `input.result` 直接 `JSON.stringify` 入库），**不是 `hash(result)`**。存在磁盘体积风险；hash 化列为待办（与 §11 指标/磁盘增长一起权衡）。
> - **⚠️ 待裁定叠加（登记）**：`effect_journal` 有 `UNIQUE(loop_id, idempotency_key)`（migrations v10），而 `recordIntent()` 是普通 `INSERT`；幂等键为**整 args 哈希**（见 §7.2 注）且无 attempt/iteration 分量 ⇒ 同一 Loop 内**同工具同参的第二次调用**（含失败重试、以及 `idempotency:'NO'` 的 `fileWriter`/`fileEditor`/`shellRunner`/`agentRecruiter`——缓存检查对其不生效）必然 UNIQUE 冲突，叠加本轮 fail-closed 后该工具会被**直接拒绝执行**。§4.2/§7.4 的"每次副作用前后强一致"在裁定前**不能签核**（详见 §7.2 注【需人工裁定】）。

### 4.3 崩溃后的 UNKNOWN 处理

启动扫描时的**唯一判据**（v2.1 统一：原文一处按时间、一处按 iteration，现只保留时间判据）：

```
status == 'EXECUTING'  AND  startedAt + timeoutMs < now
  → UPDATE status = 'UNKNOWN'（一次性、幂等改写）
```

> `iteration` **不参与超时判定**，只用于定位归属 Loop 与对应 checkpoint；禁止用"最后一个已 checkpoint 轮次"倒推超时。

对已改写为 `UNKNOWN` 的记录，按副作用类型尝试自动裁决：

| 副作用类型 | 处理策略 |
|-----------|---------|
| **tool_execute** | 按其内部包装的**实际底层 effect 类型**下钻判定（一个工具可产生多个 effect，每个子 effect 独立一行记录） |
| **file_write** | 用 `path + mtime + content_hash` 与预期对比；匹配则视 SUCCEEDED，否则 UNKNOWN |
| **http_call** | 通过幂等键回查（若目标 API 支持）；无回查能力则**必须升级人工** |
| **external_api** | 等同 `http_call`；若目标提供异步任务查询接口，先查再定 |
| **db_write** | 事务保护，一般无 UNKNOWN；有则查事务日志 |
| **agent_message_send** | 查目标 Agent 的收件箱；无则重发（因接收端也需幂等） |
| **token_debit** | 通过 **`token_transactions`** 表回查（SQLite 事务保证；表名以 Docs/Agent/09 §2.5 为准，原写 `wallet_transaction` 为不存在的表） |

**红线**：**UNKNOWN 且无法自动判定的副作用禁止盲目重放**，必须挂起 Loop 并升级。

## 5. Checkpoint 机制

### 5.1 触发时机

| 触发 | 是否必须 | 配置键（`durable.checkpoint.*`，Docs/Agent/10 §2.9） |
|------|---------|------|
| 每轮 iteration 末尾（**无论成功或失败轮**） | ✅ 强制 | `everyIteration: true` |
| 每次外部副作用完成后 | ✅ 强制 | `afterEachEffect: true` |
| 上下文压缩前 | ✅ 强制 | `beforeCompression: true` |
| 每 `fallbackIntervalSec` 秒（若无前述触发） | ✅ 兜底 | `fallbackIntervalSec: 60` |
| 用户显式暂停 | ✅ 强制 | `onExplicitPause: true` |

### 5.2 Checkpoint 内容

**代码实态形状**（`Src/Infra/DurableExecution/schemas/Checkpoint.ts` 的 `Checkpoint` 接口，2026-10-03 校准对齐）：

```typescript
interface Checkpoint {
  checkpointId: string;            // = {loopId}#{iteration}#{ts}（makeCheckpointId()）
  loopId: string;
  iteration: number;
  stateSnapshot: LoopStateSnapshot; // 简化快照：iteration/phase/completedSteps/failedAttempts + 索引签名
  artifactManifest: Array<{
    path: string;
    hash: string;                  // 注释写 SHA-256；⚠️ 运行期实写空串，见下注
    sizeBytes: number;
  }>;                              // 产出文件的指纹清单
  pendingEffects: string[];        // ⚠️ 未完成副作用的 ID 列表（EffectRecord 需由 effect_journal 反查）
  nextStepHint?: string;           // Agent 自评下一步（辅助恢复）
  createdAt: number;
}
```

> **⚠️ 形状差异与目标态（2026-10-03 校准）**：原设计（v2.1 及以前）为 `stateSnapshot: LoopState`（完整 LoopState，见 §12 §4.2）与 `pendingEffects: EffectRecord[]`；代码实际是**简化 `LoopStateSnapshot`** 与 **ID 字符串列表**（middleware 侧 `checkpointWriter.ts` 的 `CheckpointRecord` 同形，其 `stateSnapshot` 更是 `JSON.stringify` 后的字符串）。是否把代码升级为完整形状需先裁定（跨 Docs/Agent/09 §8.2 DDL，`loop_checkpoints.pending_effects_json` 列名按 ID 列表口径）。在裁定前，"完整 LoopState 快照 + 内嵌 EffectRecord[]"保留为**⚠️ 目标态**。
>
> **⚠️ hash 字段【需人工裁定·登记】（2026-10-03 校准）**：`artifactManifest[].hash` 注释口径为 SHA-256，但运行期唯一写入方 `checkpointWriter.ts`（`createCheckpointWriterMiddleware()`）对每个 `artifactPaths` 条目写 **`hash: ''`、`sizeBytes: 0`**（注释自标"Phase 0 不计算文件 hash"）——即**空指纹**；恢复侧 `recoveryExecutor.ts` 又只做结构校验（见 §6.3 注）。且本子系统内真正的 SHA-256 只有 `effectJournal.ts` 的 `hashPayload()` 与 `idempotencyStore.ts` 的 `result_hash`/`idem_key`；**指纹类哈希实为 DJB2**（`actionFingerprint.ts` 头注释写 SHA-256 而实现是双链 DJB2；`loopState.ts` 的 `hashGoal()` 亦 DJB2，被 `checkpointWriter` 写入 `ctx.data['goalHash']`）。待裁定：统一接 `createHash('sha256')`，或把注释/文档中的 SHA-256 降级为"非加密指纹"口径。本文其余各处"SHA-256"在指纹域按**目标态**理解。

### 5.3 原子写入流程

## 6. 恢复流程（Recovery）

### 6.1 启动扫描

（对齐 skill 启动序列，在"工作空间"一步之后扩展一步，见 §10）

```typescript
// Infra/DurableExecution/RecoveryScanner.ts
type RecoveryStrategy =
  | 'AUTO_RESUME'                // 无 UNKNOWN + 有可用 checkpoint + 预算未超阈
  | 'REQUIRE_HUMAN'              // 有不可自动裁决的 UNKNOWN，或命中任一降级阈值
  | 'RESTART_FROM_SCRATCH'       // 无任何 checkpoint（首轮崩溃），只能从 loops.goal_json 重建
  | 'REBUILD_FROM_JOURNAL';      // checkpoint 损坏，从 effect_journal + events 流重建
  // ↑ 4 个值构成 RecoveryStrategy 的**全集与唯一定义处**，与 §6.2 矩阵一一对应

interface RecoveryPlan {
  loopId: string;
  strategy: RecoveryStrategy;
  lastCheckpointId?: string;
  unknownEffects: EffectRecord[];
  estimatedWastedTokens: number;
  reason: string;                // 升级人工时必须可读
}

async function scanAndProposeRecovery(): Promise<RecoveryPlan[]> {
  const unfinished = await db.query(`
    SELECT * FROM loops WHERE phase NOT IN ('completed', 'failed')
  `);
  return unfinished.map(loop => {
    const lastCkpt = loadLatestCheckpoint(loop.loop_id);
    const orphans = findTimedOutExecutingEffects(loop.loop_id);   // 按 §4.3 时间判据，不按 iteration
    const unknowns = orphans.filter(e => !canAutoResolve(e));
    return {
      loopId: loop.loop_id,
      strategy: classify(loop, lastCkpt, unknowns),   // 四分支裁决，见 §6.2
      lastCheckpointId: lastCkpt?.checkpoint_id,
      unknownEffects: unknowns,
      estimatedWastedTokens: estimateWaste(lastCkpt),
      reason: buildReason(loop, lastCkpt, unknowns),
    };
  });
}
```

> 字段名口径：`db.query` 返回 DB 行（snake_case，如 `loop.loop_id`）；repository 出口统一转 camelCase，上面 `return` 对象已是转换后形状。禁止在业务层继续直读 snake_case 行。**限定（2026-10-03 校准）**：loop 侧 repository 尚未建立（`Src/Infra/Db/Repositories/` 现仅有 agentRepository / sessionRepository），`recoveryScanner.ts` 直读 snake_case 行、`rowToEffect()` 等转换散落在 DurableExecution 各模块内，本口径**待 loop repository 建立后落实**。

### 6.2 恢复决策矩阵

| 情况 | `RecoveryPlan.strategy` | 自动执行？ |
|------|------------------------|------------|
| 无 UNKNOWN 副作用 + 有可用 checkpoint + 预算已用 < `recovery.autoResumeMaxBudgetUsedRatio` | `AUTO_RESUME` | ✅ 自动（需同时满足下方四前置） |
| 有 UNKNOWN 副作用（不可自动裁决） | `REQUIRE_HUMAN` | ❌ 挂起 → 升级人工 |
| UNKNOWN 副作用数 > `recovery.autoResumeMaxUnknownEffects`（默认 **0**） | `REQUIRE_HUMAN` | ❌ |
| 无 checkpoint（首轮崩溃） | `RESTART_FROM_SCRATCH` | ❌ 升级人工（已花 Token 不自动重试） |
| checkpoint 数据损坏（hash 不匹配） | `REBUILD_FROM_JOURNAL` | ⚠️ 可自动，但完成后强制一轮只读验证 |
| 崩溃前预算已用 ≥ 80%（`autoResumeMaxBudgetUsedRatio`） | `REQUIRE_HUMAN` | ❌ 不自动恢复（可能反复崩溃浪费预算） |
| `recovery.requireHumanOnArtifactDrift = true` 且产出文件 hash 漂移 | `REQUIRE_HUMAN` | ❌ |

> **AUTO_RESUME 的四个并联前置条件**（缺一即降级为 `REQUIRE_HUMAN`）：
> `unknownEffects.length === 0` **且** `lastCheckpointId != null` **且** `budgetUsedRatio < autoResumeMaxBudgetUsedRatio` **且** 无产物漂移。
> 原 §6.1 代码只判第一条（`unknowns.length === 0 ? AUTO_RESUME : REQUIRE_HUMAN`），属真实缺陷：首轮崩溃的 Loop 会被误判为 `AUTO_RESUME` 却无 checkpoint 可回，v2.1 修正。

> **⚠️ 未实现/目标态（2026-09-22 校准 · 2026-10-03 校准复核，符号锚点）**：上述四前置在代码中**实际只满足 2/4**。`Src/Infra/DurableExecution/recoveryScanner.ts` 的 `classify()`（由 `classifyLoop()` 调用）：
> - ✅ 前置 1（UNKNOWN 数）——真判，**但口径不是 `=== 0`**（见下【需人工裁定】）；
> - ✅ 前置 2（有 checkpoint）——`classify()` 内 `if (!lastCkpt) return 'RESTART_FROM_SCRATCH'` 真判；

### 6.3 恢复执行

```typescript
async function resume(loopId: string, checkpointId: string) {
  const ckpt = loadCheckpoint(checkpointId);
  const state = ckv3.verify(ckpt.state_snapshot_json);
  // ① 验证产出文件完整性
  for (const art of ckpt.artifact_manifest) {
    if (!fs.existsSync(art.path) || hash(fs.readFileSync(art.path)) !== art.hash) {
      throw new RecoveryError('ARTIFACT_CORRUPTED', art);
    }
  }
  // ② 装载 State（不装载消息历史）
  ctx.loopState = state;
  // ③ 从 iteration+1 继续
  ctx.iteration = state.iteration + 1;
  // ④ 事件上报
  eventBus.publish({ type: 'LOOP_RESUMED', loopId, fromCheckpoint: checkpointId });
}
```

**关键**：恢复时**不重放历史消息给模型**。只把 `LoopState` 中的 `completed_steps / failed_attempts` 摘要作为 Context 装配的输入。这既是效率优化，也是防"错误传播"红利的做法。

> **⚠️ 未实现（2026-09-22 校准 · 2026-10-03 校准复核，符号锚点）**：上面代码块第 ① 步的"真实文件校验"（`fs.existsSync` + 重算 hash 比对）在 `recoveryExecutor.ts` 的 `resume()` 内**只做指纹结构校验**（判 `art.path` / `art.hash` 非空、`sizeBytes >= 0`），源码注释自标"注：S2 阶段仅做结构验证，实际文件校验待 S4 工具层完善"。⇒ 文件被外部篡改时 `ARTIFACT_CORRUPTED` **不会触发**（此即 §6.2 前置 4 缺失的落点）。
> **2026-10-03 叠加**：① 即便结构校验存在，运行期 manifest 本身是**空指纹**（`checkpointWriter` 写 `hash: ''`/`sizeBytes: 0`，见 §5.2 注），且该 middleware 未挂载（§5.1 注）——校验的输入数据在真实进程里根本不存在；SHA-256 口径【需人工裁定】见 §5.2 注。② `resume()` 末尾无 `eventBus.publish({ type: 'LOOP_RESUMED' })`，只返回 `ResumeResult`，事件上报交由调用方；而 `EventType.LOOP_RESUMED`（`Src/Services/EventBus/eventTypes.ts`）在 `Src/` 中**零发布点**（见 §11 注）。③ `executeRecovery()` / `resume()` / `validateRecoveryPlan()` 三者**无任何生产调用者**（仅测试自测），⑭.5 执行步不存在（见 §10 注）。§6.3 代码块整体为**目标态**。

## 8. 与 SharedMemory / Event Bus 的边界

### 8.1 三者职责分离

| 组件 | 存放 | 一致性 | 允许丢失 |
|------|------|-------|---------|
| **Event Bus（07）** | 事实发生的事件流 | at-least-once | ❌ 不允许丢 |
| **SharedMemory（07）** | 跨 Agent 共享上下文 | 最终一致 | ⚠️ 可从 Event 重建 |
| **Durable Execution（本文）** | 单 Loop 的执行状态与副作用 | **强一致** | ❌ 不允许丢 |

> **⚠️ L1/L2 双写现况（2026-10-03 校准）**：工具调用目前**同时**记录在 main 库 `ai_events`（`agent:tool_call_result`，由 `aiEventStore` 落库）与 `effect_journal`（非 SAFE 工具，由 `toolSafetyGate` 落库），两者由 `Src/Interface/RestApi/syncApi.ts` 按 `tool_call_id` 精确配对去重后同步上报（FE-027）。"三层职责严格分离"在 tool 调用这一面上**并未分离**；L1 真源归属待裁定（见 §3 注）。

### 8.2 关系图

```
                    ┌─────────────┐
                    │  Event Bus  │  ← 全系统事件（广播）
                    └──────┬──────┘
                           │ publish
                           ▼
   ┌───────────────┐   ┌──────────────┐   ┌────────────────┐
   │ SharedMemory  │◀──│  Loop State  │──▶│ Effect Journal │
   │ (跨 Agent)    │   │  (单 Loop)   │   │ (副作用溯源)   │
   └───────────────┘   └──────┬───────┘   └────────────────┘
                              │ checkpoint
                              ▼
                      ┌───────────────┐
                      │  Checkpoints  │
                      └───────────────┘
```

**读写规则**：
- SharedMemory 允许最终一致（可容忍秒级延迟）；
- Loop State 每次 iteration 强一致；
  > ⚠️ **未成立（2026-09-22 校准 · 2026-10-03 校准再降级）**：原表述"每轮 checkpoint 落在 checkpointWriter 内存 Map、不进 SQLite"现在**连内存态都不存在** —— 该 middleware 无注册点、`afterAgent` 钩子无执行点，运行期 0 个 checkpoint 触发器（见 §5.1 注）。进程重启即丢的结论不变（实际是"从未写过"）。
- Effect Journal 每次副作用前后强一致（fsync 落盘）。
  > ⚠️ **部分成立（2026-09-22 校准 · 2026-10-03 校准更新）**：显式 fsync 仍缺（目标态）；但原"三库统一 `synchronous = NORMAL`、WAL-NORMAL 掉电可丢最近事务"结论**已反转** —— main 库（journal 所在库）现按 `durable.effect.writeSynchronous`（默认 FULL）设 `synchronous = FULL`（`main.ts` ⑥ 步 → `initDatabase()` → `openDatabase()`，见 §2 D6 / §10 注）。工具路径上 INTENT 写失败已 fail-closed（§4.2 注）；"前后强一致"仍受 §4.2/§7.2 的 UNIQUE 同键冲突【待裁定】牵制。

## 14. 迭代落地

**Phase 0（必做最小集）**：
- ⚠️ Effect Journal（写 + fsync）—— **写已落、显式 fsync 未落；PRAGMA 级已闭合**（2026-10-03 校准更新）：`recordIntent()` 仍为普通 INSERT、无显式 fsync，但 main 库 `synchronous = FULL` 已读取 `durable.effect.writeSynchronous` 生效（原"全局 NORMAL"结论作废）；INTENT 写失败已 **fail-closed**；仅工具调用接入。详见 §2 D6 / §4.2 / §10 注。
- ⚠️ LoopState checkpoint —— **比 2026-09-22 记录更弱（2026-10-03 校准）**：DB store（`createCheckpoint()`）已建但零 importer；运行期连"落在 `checkpointWriter.ts` 内存 Map"也**不存在**——该 middleware 未注册、`afterAgent` 钩子无执行点，**运行期 0 个 checkpoint 触发器**；`loops` 表亦无生产写入方；事务只含 `loop_checkpoints` 单表插入，缺 §5.3 第 ②④⑥⑦ 步。详见 §5.1 / §5.3 注。
- ⚠️ 启动扫描 + AUTO_RESUME —— **仅"扫描"半侧接线，且无数据源（2026-10-03 校准加重）**：`main.ts` ⑦.5 丢弃返回的 `RecoveryPlan[]`，无待恢复队列、无 WARN 上报；⑭.5 执行步整体缺失，`executeRecovery()`/`resume()` 无生产调用者；又因 `loops` 表零写入，扫描**恒返回空数组**，恢复链路在真实进程里空转 ⇒ **实际无任何 Loop 会被自动恢复**。四前置仅满足 2/4。详见 §6.2 / §10 注。
- ⚠️ 幂等键 + idempotency_cache —— **表与读写路径已通**（`toolSafetyGate.ts` 幂等检查分支命中即跳过执行），但键生成对**整个 args** 哈希、未按 `idempotencyKeyFields` 投影，且嵌套参数可**塌缩成同键（假命中）**；与 Docs/Agent/14 §6 的另一套公式并存待裁定；与 `UNIQUE(loop_id, idempotency_key)` 叠加后同键二次 INTENT 被拒待裁定；`purgeExpired()` 已挂关闭序列（仅关闭时执行，缺周期调度，§7.3 注）。详见 §7.2 / §7.3 注。
