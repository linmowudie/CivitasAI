# 共享记忆与上下文系统设计

> 本文档定义 Civitas-AI 的共享记忆系统（Shared Memory）与上下文管理，包括事件总线、共享/隔离双层存储、写入守卫、上下文胶囊和知识沉淀机制。

---

## 1. 职责边界

| 职责 | 说明 |
|------|------|
| 全局工作区管理 | 维护所有 Agent 可读写的共享状态 |
| 私有上下文隔离 | 每个 Agent 的中间推理过程物理隔离 |
| 写入守卫 | 拦截异常写入，检测语义冲突 |
| 上下文胶囊 | 按需为 Agent 组装轻量级上下文片段 |
| 知识沉淀 | 将临时事实提炼为长期知识 |
| 事件溯源 | 所有状态变更转化为不可变事件 |

**不负责：** 仲裁裁决（由 Arbitration 负责）、Token 扣减（由 TokenEconomy 负责）。

> ⚠️ **2026-09-22 校准**：上表为职责目标态。现态中「写入守卫」只做到**拦截异常写入**（红线 key / 乐观锁版本 / assertion），
> 「检测语义冲突」**未实现**（见 §3.2）；「上下文胶囊」在 `Src/` 中**无对应类**，实际由 `Services/Context`
> 四级分区装配承担（见 §3.3）；「事件溯源」已实现（`EventBus`），但状态本身**未落库**（见 §2.1）。
>
> ⚠️ **2026-10-03 校准**：上条末句"状态本身未落库"**已半侧失效**，现只对 **GlobalWorkspace 半侧成立**——

## 3. 核心组件

### 3.1 全局工作区（GlobalWorkspace）

```typescript
// ⚠️ 2026-09-22 校准：实际实现为 Services/SharedMemory/globalWorkspace.ts 的**模块级函数**（非 class），
//    全部**同步**返回 Result/数组（无 Promise）；write 入参为 **params 对象**而非 (entry, agentId)。
interface GlobalWorkspace {
  // 读写操作（受 WriteGuard 保护）
  write(entry: WorkspaceEntry, agentId: string): Promise<WriteResult>;
  // ✅ 实为 write(params: { key, content, contentType, assertion, traceId, agentId,
  //    taskId?, taskAuthority?, evidenceChain?, expectedVersion?, conflictStrategy? }): Result<WriteResult>
  //    （globalWorkspace.ts → `write()`）
  read(query: WorkspaceQuery): Promise<WorkspaceEntry[]>;   // ✅ 实为 read(query): WorkspaceEntry[]（globalWorkspace.ts → `read()`，同步）
  delete(entryId: string, agentId: string): Promise<void>;
  // ⚠️ 无 delete：实为 discardEntry(entryId, _agentId): Result<void>（globalWorkspace.ts → `discardEntry()`），仅置 status='discarded'
  
  // 语义检索
  searchBySemantic(query: string, topK: number): Promise<WorkspaceEntry[]>;
  // ⚠️ 未实现（2026-09-22 校准）：Src 内不存在 searchBySemantic / searchByVector；
  //    read() 仅支持 key / traceId / agentId / taskId / contentType / status / assertion / limit 过滤
  
  // 按 trace 查询
  getByTrace(traceId: string): Promise<WorkspaceEntry[]>;   // ✅ 实为 getByTrace(traceId): WorkspaceEntry[]（globalWorkspace.ts → `getByTrace()`，同步复用 read({traceId})）
}

// ⚠️ 持久化未接线（2026-10-03 校准，结论未变）：条目只存内存 `const entries: Map<string, WorkspaceEntry>`
//    （globalWorkspace.ts 模块级 `entries` / `keyIndex` / `entryCounter`），不写 `global_workspace` 表
//    （表已由迁移 v16 建好、v22 补 owner_user_id 列）——全仓无该表的读写方，进程重启即丢失，
//    且 write() **不接收/不写入属主**，故 GlobalWorkspace 现态**无跨账号隔离**；见 §2.1 校准注。
//    注：与长期记忆不同——LTM 已于 2026-10-02 落库并回灌，勿把两层的结论互抄。

interface WorkspaceEntry {
  entryId: string;                     // 全局唯一 ID
  traceId: string;                     // 关联运行会话
  agentId: string;                     // 写入者 Agent ID
  taskId?: string;                     // 关联任务 ID
  
  // 内容
  content: string;                     // 记忆内容
  contentType: 'fact' | 'decision' | 'verdict' | 'contract' | 'status';
  
  // 元数据（强制携带）
  metadata: {
    timestamp: number;                       // epoch ms
    sourceAgentId: string;             // 来源 Agent
    taskAuthority: number;             // 任务权威性（**0.0–1.0**，与 Docs/Agent/10 §1.2.1 标度一致；展示层才 ×100）
    evidenceChain?: string[];          // 证据链（关联的 operation_id 列表）
  };
  
  // 向量（用于语义冲突检测）
  semanticVector?: number[];           // ⚠️ 未实现（2026-09-22 校准，2026-10-03 复核仍成立）：
                                       //    `versionedEntry.ts → WorkspaceEntry` 接口无此字段，
                                       //    迁移 v16 亦无对应列；语义冲突检测见 §3.2 校准注
  
  // 状态
  status: 'active' | 'superseded' | 'discarded';
  supersededBy?: string;               // 被哪条新记忆取代
  
  createdAt: number;                        // epoch ms
  updatedAt: number;                        // epoch ms
}
```

> **代码实际字段（2026-09-22 校准 → 2026-10-03 复核，结论未变）**：`versionedEntry.ts → WorkspaceEntry` 除上述字段外还强制携带

```typescript
class WriteGuard {
  // 拦截写入请求                        // ⚠️ 目标态签名（2026-09-22 校准），实际见上方校准注
  async intercept(entry: WorkspaceEntry): Promise<InterceptResult> {
    // [1] 生成/验证语义向量              // ⚠️ 未实现（2026-09-22 校准）
    const vector = entry.semanticVector ?? await this.generateVector(entry.content);
    
    // [2] 相似度碰撞检测                 // ⚠️ 未实现（2026-09-22 校准）：无 searchByVector
    const similarEntries = await this.workspace.searchByVector(vector, 5);
    
    // [3] 冲突判定                        // ⚠️ 未实现（2026-09-22 校准）：0.85 阈值与语义相反判定均无代码
    for (const existing of similarEntries) {
      const similarity = cosineSimilarity(vector, existing.semanticVector);
      
      if (similarity > 0.85) {
        // 高相似度 → 检查是否语义相反
        const isOpposite = await this.checkSemanticOpposition(entry.content, existing.content);
        
        if (isOpposite) {
          // 语义冲突 → 阻断并上报         // ⚠️ 未实现：实际由 conflictPrecheck.ts → precheckConflicts() 按文件冲突发布 CONFLICT_DETECTED
          return {
            allowed: false,
            conflict: {
              conflictId: generateId(),
              newMemoryId: entry.entryId,
              oldMemoryId: existing.entryId,
              similarity,
              conflictType: 'semantic_opposition',
            }
          };
        }
        
        // 高相似 + 非相反 → 可能是重复 → 警告但放行
        return { allowed: true, warning: 'potential_duplicate' };
      }
    }
    
    // 无冲突 → 放行                      // ✅ 现状等价行为：红线 + 版本 + assertion 三项通过后放行
    return { allowed: true };
  }
}
```

  // 为指定 Agent 构建上下文胶囊
  async buildForAgent(agentId: string, taskContext: TaskContext): Promise<Capsule> {
    const capsule: Capsule = {
      capsuleId: generateId(),
      agentId,
      sections: [],
      totalTokens: 0,
    };
    
    // [1] 任务描述（必选）
    capsule.sections.push({
      type: 'task_description',
      content: taskContext.description,
      tokenCount: await this.countTokens(taskContext.description),
    });
    
    // [2] 相关共享记忆（语义检索 Top-K）
    const relevantMemories = await this.workspace.searchBySemantic(
      taskContext.description,
      taskContext.memoryTopK ?? 5
    );
    capsule.sections.push({
      type: 'relevant_memories',
      content: relevantMemories.map(m => m.content).join('\n---\n'),
      tokenCount: await this.countTokens(relevantMemories.map(m => m.content).join('\n')),
    });
    
    // [3] 最近对话历史（按时间倒序，直到预算用尽）
    const recentMessages = await this.getRecentMessages(taskContext.traceId, taskContext.messageBudget);
    capsule.sections.push({
      type: 'recent_messages',
      content: recentMessages.map(m => formatMessage(m)).join('\n'),
      tokenCount: await this.countTokens(recentMessages.map(m => formatMessage(m)).join('\n')),
    });
    
    // [4] 约束条件
    if (taskContext.constraints?.length) {
      capsule.sections.push({
        type: 'constraints',
        content: taskContext.constraints.join('\n'),
        tokenCount: await this.countTokens(taskContext.constraints.join('\n')),
      });
    }
    
    // [5] 预算检查
    const totalTokens = capsule.sections.reduce((sum, s) => sum + s.tokenCount, 0);
    if (totalTokens > taskContext.capsuleBudget) {
      // 超预算 → 按优先级裁剪（constraints > task > memories > messages）
      await this.trimToBudget(capsule, taskContext.capsuleBudget);
    }
    
    return capsule;
  }
}

## 4. 事件总线（EventBus）

### 4.1 设计原则

| 原则 | 说明 |
|------|------|
| 事件溯源 | 所有状态变更转化为不可变事件 |
| 发布-订阅 | 组件仅订阅关心的事件类型，极致解耦 |
| 异步通信 | 事件处理不阻塞发布者 |
| 有序性 | 同一 trace 下的事件保证顺序 |

### 4.2 实现方案

**Phase 0-2：** 内存事件总线（进程内 EventEmitter 模式）

```typescript
interface EventBus {
  // 发布事件
  publish(event: DomainEvent): void;
  
  // 订阅事件
  subscribe(eventType: EventType, handler: EventHandler): Subscription;
  
  // 订阅多个事件
  subscribeMany(eventTypes: EventType[], handler: EventHandler): Subscription;
  
  // 等待特定事件（Promise 化）
  waitFor(eventType: EventType, filter?: (event: DomainEvent) => boolean, timeoutMs?: number): Promise<DomainEvent>;
}

interface DomainEvent {
  eventId: string;                     // UUID
  eventType: EventType;                // 🔴 必须是 §4.3 注册表成员，禁止自由字符串
  traceId?: string;                    // 关联 trace
  loopId?: string;                     // v2.1 补：Loop 级事件必填（供 §8.5 与 Docs/Agent/11 回放对齐）
  timestamp: number;                   // epoch **毫秒**（与 Docs/Agent/09 §1.1 时间列统一）
  priority: 'low' | 'normal' | 'high' | 'critical';
  payload: Record<string, unknown>;     // 事件数据
  source: string;                      // 发布者标识（组件名，如 'SharedMemory/WriteGuard'）
}
```

## 8. v2 补丁：Context ≠ State 拆分与并行隔离

> **修订依据**：`Docs/99-审查记录/设计审查报告-Loop与Harness工程.md` §3 失效三、§4.3、§4.4。

### 8.1 SharedMemory 职责边界重新定义（红线）

旧版中 `GlobalWorkspace` 同时充当了【跨 Agent 共享上下文】与【任务事实】两个角色，导致：
- 上下文压缩会意外修改任务事实；
- 不同 Agent 看到不同时间点的 workspace 无版本号；
- 一个 Agent 错误写入会污染其他 Agent 下一轮上下文。

**v2 红线**：

| 存放 | 内容 | 写入时机 | 允许丢失 |
|------|------|---------|---------|
| **LoopState**（Docs/Agent/11 §4） | 任务事实 | 每轮末尾强一致 | ❌ |
| **GlobalWorkspace** | 跨 Agent 可共享的观察 | 事件到达 | ⚠️ 可从 Event 重建 |
| **LongTermMemory** | 知识沉淀 | 任务完成后 | ⚠️ |
| **Context（本轮装配）** | 从上面三者临时拼装 | ⑥ 之前 | 不适用 |

**禁止**：任何将 `goal / immutable_constraints / successCriteria` 写入 GlobalWorkspace 的行为——必须写入 LoopState。

> **2026-10-03 校准（属主分区现状）**：本红线在代码中双向有落点——`LoopControl/loopState.ts` 的不可变区
> （`goal{originalRequirement, successCriteria, immutableConstraints}` + `setGoalImmutable` 二次修改拒绝 +
> goal hash 校验）与 `writeGuard.ts → FORBIDDEN_KEYS` 一一对应；持久化真源为 `loops.goal_json / state_json`。
> ⚠️ **跨账号隔离仅半边成立**：**LongTermMemory 已按属主分区**（`long_term_memory` / `memory_entries` 复合主键带
> `owner_user_id`，属主真源 `Services/AccountScope/activeAccount.ts`）；**GlobalWorkspace 未接入属主**——
