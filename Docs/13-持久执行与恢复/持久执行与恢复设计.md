# 13 · 持久执行与恢复设计（Durable Execution & Recovery）

> **本文档定位**：补齐 Loop Engineering 第五阶段"持久编排循环"的基础设施缺口。让 Civitas-AI 的 Agent Loop **能在进程崩溃、部署重启、机器断电后从上一个成功步骤续接**，而不是从头开始。
>
> **审查依据**：`Docs/99-审查记录/设计审查报告-Loop与Harness工程.md` §4.2 / §5.13。
>
> **业界对标**：Matt Van Horn "第五阶段循环"、Temporal / AWS Step Functions Durable Execution 模式、LangGraph Checkpointer。

---

## 1. 为什么必须做

**当前设计的致命缺口**（详见审查报告 §4.2）：

- 进程重启 → 运行中 Agent 状态全丢
- 长时间任务（>1 小时）跨部署 → 从头再来
- 已经发出外部副作用（写文件、调 API、发消息）后崩溃 → 重启后**重复执行**
- 只在容器里运行 ≠ correctness，只是 uptime

**判定标准**：**如果 Agent 循环会调用非幂等外部工具，那么没有 Durable Execution = 没有生产可用性**。

Civitas-AI 的 Worker 会写文件、执行命令、跨 Agent 通信 —— 完全命中此判定。

## 2. 设计原则

| # | 原则 | 说明 |
|---|------|------|
| D1 | **Every Effect is Logged Before It Happens** | 副作用发生前必须先写意图日志；崩溃后可根据日志判断"是否已发生" |
| D2 | **Idempotency by Design** | 所有可重试步骤必须携带幂等键；相同键第二次执行返回首次结果 |
| D3 | **Checkpoint After Every Successful Step** | 每个 iteration 末尾原子写入 `LoopState` + `artifact_manifest` |
| D4 | **Resume ≠ Replay** | 恢复时从 `lastCheckpointId` 加载 State，不重放消息历史 |
| D5 | **Recovery Must Be Explicit** | 系统重启后不自动 resume，必须经"恢复决策"确认（防雪崩） |
| D6 | **Durable ≠ Fast** | Checkpoint 落盘走 fsync；不接受 fire-and-forget |

> **⚠️ 未实现（2026-09-22 校准）**：D6 的 fsync 分支全未落地。`Src/Infra/DurableExecution/` 目录下 **无任何 `fsync`/`fdatasync` 调用**（`grep` 结果：fsync 只存在于 `Src/Infra/Fs/atomicWrite.ts:13,71,114`，而 DurableExecution 从不 import 它）；`effectJournal.ts:7` 仅在文件头注释里声称"effect_journal 表使用 PRAGMA synchronous = FULL"，实际见 §5.3 / §7.2 注与 §10 说明。本文其余各处"写 + fsync"均按此口径理解为**目标态**。

## 3. 三层持久化架构

```
┌──────────────────────────────────────────────┐
│  L3 Checkpoint Layer（每轮末尾快照）         │  ← 恢复入口
│      loop_checkpoints 表                     │
├──────────────────────────────────────────────┤
│  L2 Intent Log Layer（副作用前写意图）       │  ← 判定"是否已执行"
│      effect_journal 表                       │
├──────────────────────────────────────────────┤
│  L1 Event Sourcing Layer（全量事件流）       │  ← 审计与回放
│      Events 库（07 号文档定义）              │
└──────────────────────────────────────────────┘
```

**三层职责严格分离**：
- **L1 事件流**只写不删不改，是审计真源，性能可慢；
- **L2 意图日志**是"崩溃后到底做没做"的判定依据，必须强一致；
- **L3 快照**是恢复入口，允许丢弃，从 L2 重建。

## 4. 副作用意图日志（Effect Journal）

### 4.1 数据模型

```typescript
// Infra/DurableExecution/EffectJournal.ts
interface EffectRecord {
  effectId: string;              // = {operation_id} 复用全局 ID（`Docs/11 §1.2.1` 之外的全局契约）
  loopId: string;
  iteration: number;
  kind: 'tool_execute' | 'file_write' | 'http_call' | 'db_write'
      | 'agent_message_send' | 'token_debit' | 'external_api';   // 与 effect_journal.kind 注释同集合
  idempotencyKey: string;         // 由调用方提供或本层生成（算法见 §7.2）
  payloadHash: string;            // SHA-256(payload)
  status: 'INTENT' | 'EXECUTING' | 'SUCCEEDED' | 'FAILED' | 'UNKNOWN';
  result?: unknown;
  startedAt: number;               // epoch ms
  timeoutMs: number;               // 生效超时快照；默认 = `durable.effect.defaultTimeoutMs`（30000）
  completedAt?: number;            // epoch ms
  errorClass?: 'retryable' | 'non_retryable' | 'unknown';
}
```

> **`timeoutMs` 补登（v2.1）**：原 §4.3 的判定式 `startedAt < now - timeout` 引用了一个 `EffectRecord` 上不存在的字段。现明确：
> 超时时长是 EffectRecord 的**第 9 个字段**，写入时从 `durable.effect.defaultTimeoutMs` 取默认值（工具可在 `ToolSpec` 声明更长值），**作为快照固定下来**，后续配置热更新不得改变存量记录的判定基准。
> 对应列：`effect_journal.started_at` + `effect_journal.timeout_ms`（DDL 见 Docs/10 §8.2，v2.1 补列）。

### 4.2 生命周期

```
调用副作用工具
   ↓
[1] INSERT EffectRecord(status=INTENT) ── fsync 落盘   ⚠️ fsync 未实现
   ↓
[2] UPDATE EffectRecord(status=EXECUTING)
   ↓
[3] 实际执行工具
   ↓
[4a] 成功 → UPDATE(status=SUCCEEDED, result=hash(result))
[4b] 失败明确 → UPDATE(status=FAILED, errorClass=...)
[4c] 崩溃/超时 → 保持 EXECUTING（恢复扫描按 §4.3 判据将其改写为 UNKNOWN）
```

> **⚠️ 未实现/接线不全（2026-09-22 校准）**：上述四步在代码中由 `effectJournal.ts` 的 `recordIntent()` / `markExecuting()` / `markSucceeded()` / `markFailed()`（+ 底层 `updateEffectStatus()`）承载，**没有 fsync**（`:67-76` 为普通 prepared INSERT）。唯一生产调用点在 `Src/Services/LoopControl/middleware/toolSafetyGate.ts:136`，且该处 `:145-149` 对 INTENT 写入失败采取 **fail-open**（仅 `logger.error` 后仍允许工具执行），与本节"必须先写意图日志"的强一致语义相悖 —— **待办：须代码侧改为 fail-closed**（见 §13 现状说明）。

### 4.3 崩溃后的 UNKNOWN 处理

启动扫描时的**唯一判据**（v2.1 统一：原文一处按时间、一处按 iteration，现只保留时间判据）：

```
status == 'EXECUTING'  AND  startedAt + timeoutMs < now
  → UPDATE status = 'UNKNOWN'（一次性、幂等改写）
```

> `iteration` **不参与超时判定**，只用于定位归属 Loop 与对应 checkpoint；禁止用"最后一个已 checkpoint 轮次"倒推超时。

对已改写为 `UNKNOWN` 的记录，按副作用类型尝试自动裁决：

| 副作用类型 | 处理策略 |
|-----------|---------|
| **tool_execute** | 按其内部包装的**实际底层 effect 类型**下钻判定（一个工具可产生多个 effect，每个子 effect 独立一行记录） |
| **file_write** | 用 `path + mtime + content_hash` 与预期对比；匹配则视 SUCCEEDED，否则 UNKNOWN |
| **http_call** | 通过幂等键回查（若目标 API 支持）；无回查能力则**必须升级人工** |
| **external_api** | 等同 `http_call`；若目标提供异步任务查询接口，先查再定 |
| **db_write** | 事务保护，一般无 UNKNOWN；有则查事务日志 |
| **agent_message_send** | 查目标 Agent 的收件箱；无则重发（因接收端也需幂等） |
| **token_debit** | 通过 **`token_transactions`** 表回查（SQLite 事务保证；表名以 Docs/10 §2.5 为准，原写 `wallet_transaction` 为不存在的表） |

**红线**：**UNKNOWN 且无法自动判定的副作用禁止盲目重放**，必须挂起 Loop 并升级。

## 5. Checkpoint 机制

### 5.1 触发时机

| 触发 | 是否必须 | 配置键（`durable.checkpoint.*`，Docs/11 §2.9） |
|------|---------|------|
| 每轮 iteration 末尾（**无论成功或失败轮**） | ✅ 强制 | `everyIteration: true` |
| 每次外部副作用完成后 | ✅ 强制 | `afterEachEffect: true` |
| 上下文压缩前 | ✅ 强制 | `beforeCompression: true` |
| 每 `fallbackIntervalSec` 秒（若无前述触发） | ✅ 兜底 | `fallbackIntervalSec: 60` |

> **⚠️ 未接线（2026-09-22 校准）**：表中 5 个触发器与 `durable.checkpoint.*` 8 个配置键 **后端零消费**。`Src/` 下 `grep` 这 8 键（`everyIteration` / `afterEachEffect` / `beforeCompression` / `onExplicitPause` / `fallbackIntervalSec` / `keepLastCount` / `milestoneKeep` / `compactIntervalSec`）无一处命中；仅 `Configs/durable.json:3-12` 定义、其中 5 键在 `Client/src/config/configSchema.ts:197-201` 作 UI Schema。**现状只有"每轮 iteration 末尾"一个触发器真实存在**，实现体为 `Src/Services/LoopControl/middleware/checkpointWriter.ts:37-82`（`afterAgent` 钩子，priority 50）；副作用后 / 压缩前 / 兜底定时 / 显式暂停 4 个触发器均未实现。其余 4 键与对应触发器列为目标态 + 待办（须代码侧接线）。

## 6. 恢复流程（Recovery）

### 6.1 启动扫描

（对齐 skill 启动序列，在"工作空间"一步之后扩展一步，见 §10）

```typescript
// Infra/DurableExecution/RecoveryScanner.ts
type RecoveryStrategy =
  | 'AUTO_RESUME'                // 无 UNKNOWN + 有可用 checkpoint + 预算未超阈
  | 'REQUIRE_HUMAN'              // 有不可自动裁决的 UNKNOWN，或命中任一降级阈值
  | 'RESTART_FROM_SCRATCH'       // 无任何 checkpoint（首轮崩溃），只能从 loops.goal_json 重建
  | 'REBUILD_FROM_JOURNAL';      // checkpoint 损坏，从 effect_journal + events 流重建
  // ↑ 4 个值构成 RecoveryStrategy 的**全集与唯一定义处**，与 §6.2 矩阵一一对应

interface RecoveryPlan {
  loopId: string;
  strategy: RecoveryStrategy;
  lastCheckpointId?: string;
  unknownEffects: EffectRecord[];
  estimatedWastedTokens: number;
  reason: string;                // 升级人工时必须可读
}

async function scanAndProposeRecovery(): Promise<RecoveryPlan[]> {
  const unfinished = await db.query(`
    SELECT * FROM loops WHERE phase NOT IN ('completed', 'failed')
  `);
  return unfinished.map(loop => {
    const lastCkpt = loadLatestCheckpoint(loop.loop_id);
    const orphans = findTimedOutExecutingEffects(loop.loop_id);   // 按 §4.3 时间判据，不按 iteration
    const unknowns = orphans.filter(e => !canAutoResolve(e));
    return {
      loopId: loop.loop_id,
      strategy: classify(loop, lastCkpt, unknowns),   // 四分支裁决，见 §6.2
      lastCheckpointId: lastCkpt?.checkpoint_id,
      unknownEffects: unknowns,
      estimatedWastedTokens: estimateWaste(lastCkpt),
      reason: buildReason(loop, lastCkpt, unknowns),
    };
  });
}
```

> 字段名口径：`db.query` 返回 DB 行（snake_case，如 `loop.loop_id`）；repository 出口统一转 camelCase，上面 `return` 对象已是转换后形状。禁止在业务层继续直读 snake_case 行。

### 6.2 恢复决策矩阵

| 情况 | `RecoveryPlan.strategy` | 自动执行？ |
|------|------------------------|------------|
| 无 UNKNOWN 副作用 + 有可用 checkpoint + 预算已用 < `recovery.autoResumeMaxBudgetUsedRatio` | `AUTO_RESUME` | ✅ 自动（需同时满足下方四前置） |
| 有 UNKNOWN 副作用（不可自动裁决） | `REQUIRE_HUMAN` | ❌ 挂起 → 升级人工 |
| UNKNOWN 副作用数 > `recovery.autoResumeMaxUnknownEffects`（默认 **0**） | `REQUIRE_HUMAN` | ❌ |
| 无 checkpoint（首轮崩溃） | `RESTART_FROM_SCRATCH` | ❌ 升级人工（已花 Token 不自动重试） |
| checkpoint 数据损坏（hash 不匹配） | `REBUILD_FROM_JOURNAL` | ⚠️ 可自动，但完成后强制一轮只读验证 |
| 崩溃前预算已用 ≥ 80%（`autoResumeMaxBudgetUsedRatio`） | `REQUIRE_HUMAN` | ❌ 不自动恢复（可能反复崩溃浪费预算） |
| `recovery.requireHumanOnArtifactDrift = true` 且产出文件 hash 漂移 | `REQUIRE_HUMAN` | ❌ |

> **AUTO_RESUME 的四个并联前置条件**（缺一即降级为 `REQUIRE_HUMAN`）：
> `unknownEffects.length === 0` **且** `lastCheckpointId != null` **且** `budgetUsedRatio < autoResumeMaxBudgetUsedRatio` **且** 无产物漂移。
> 原 §6.1 代码只判第一条（`unknowns.length === 0 ? AUTO_RESUME : REQUIRE_HUMAN`），属真实缺陷：首轮崩溃的 Loop 会被误判为 `AUTO_RESUME` 却无 checkpoint 可回，v2.1 修正。

> **⚠️ 未实现/目标态（2026-09-22 校准）**：上述四前置在代码中**实际只满足 2/4**。`Src/Infra/DurableExecution/recoveryScanner.ts:139-164` 的 `classify()`：
> - ✅ 前置 1（UNKNOWN 数）——`:145-147` 真判；
> - ✅ 前置 2（有 checkpoint）——`:150-152` 真判；
> - ⚠️ 前置 3（预算比）——**形式在、实质为桩**：`:157-160` 调 `estimateBudgetUsedRatio()`，而该函数 `:169-173` 体为 `return 0`（注释自标"简化：当前阶段无法精确估算"）。0 恒 `< 0.8` ⇒ **该分支永不触发**，矩阵"预算已用 ≥ 80% → REQUIRE_HUMAN"一行不可达；

### 6.3 恢复执行

```typescript
async function resume(loopId: string, checkpointId: string) {
  const ckpt = loadCheckpoint(checkpointId);
  const state = ckv3.verify(ckpt.state_snapshot_json);
  // ① 验证产出文件完整性
  for (const art of ckpt.artifact_manifest) {
    if (!fs.existsSync(art.path) || hash(fs.readFileSync(art.path)) !== art.hash) {
      throw new RecoveryError('ARTIFACT_CORRUPTED', art);
    }
  }
  // ② 装载 State（不装载消息历史）
  ctx.loopState = state;
  // ③ 从 iteration+1 继续
  ctx.iteration = state.iteration + 1;
  // ④ 事件上报
  eventBus.publish({ type: 'LOOP_RESUMED', loopId, fromCheckpoint: checkpointId });
}
```

**关键**：恢复时**不重放历史消息给模型**。只把 `LoopState` 中的 `completed_steps / failed_attempts` 摘要作为 Context 装配的输入。这既是效率优化，也是防"错误传播"红利的做法。

> **⚠️ 未实现（2026-09-22 校准）**：上面代码块第 ① 步的"真实文件校验"（`fs.existsSync` + 重算 hash 比对）在 `recoveryExecutor.ts:70-76` **只做指纹结构校验**（判 `art.path` / `art.hash` 非空、`sizeBytes >= 0`），源码注释自标"注：S2 阶段仅做结构验证，实际文件校验待 S4 工具层完善"。⇒ 文件被外部篡改时 `ARTIFACT_CORRUPTED` **不会触发**（此即 §6.2 前置 4 缺失的落点）。另 `resume()` 末尾无 `eventBus.publish({ type: 'LOOP_RESUMED' })`，它只返回 `ResumeResult`，事件上报交由调用方；§6.3 代码块整体为**目标态**。

## 8. 与 SharedMemory / Event Bus 的边界

### 8.1 三者职责分离

| 组件 | 存放 | 一致性 | 允许丢失 |
|------|------|-------|---------|
| **Event Bus（07）** | 事实发生的事件流 | at-least-once | ❌ 不允许丢 |
| **SharedMemory（07）** | 跨 Agent 共享上下文 | 最终一致 | ⚠️ 可从 Event 重建 |
| **Durable Execution（本文）** | 单 Loop 的执行状态与副作用 | **强一致** | ❌ 不允许丢 |

### 8.2 关系图

```
                    ┌─────────────┐
                    │  Event Bus  │  ← 全系统事件（广播）
                    └──────┬──────┘
                           │ publish
                           ▼
   ┌───────────────┐   ┌──────────────┐   ┌────────────────┐
   │ SharedMemory  │◀──│  Loop State  │──▶│ Effect Journal │
   │ (跨 Agent)    │   │  (单 Loop)   │   │ (副作用溯源)   │
   └───────────────┘   └──────┬───────┘   └────────────────┘
                              │ checkpoint
                              ▼
                      ┌───────────────┐
                      │  Checkpoints  │
                      └───────────────┘
```

**读写规则**：
- SharedMemory 允许最终一致（可容忍秒级延迟）；
- Loop State 每次 iteration 强一致；
  > ⚠️ **未成立（2026-09-22 校准）**：运行期每轮 checkpoint 落在 `LoopControl/middleware/checkpointWriter.ts:34` 的**内存 Map**，不进 SQLite ⇒ 进程重启即丢。详见 §5.3 注。
- Effect Journal 每次副作用前后强一致（fsync 落盘）。
  > ⚠️ **目标态（2026-09-22 校准）**：三条"强一致"中本条**未成立** —— 无 fsync、且 `Src/Infra/Db/database.ts:140` 对三库统一设 `synchronous = NORMAL`，实际是 WAL-NORMAL 级持久性（掉电可丢最近事务）。见 §2 D6 注与 §10 注。
