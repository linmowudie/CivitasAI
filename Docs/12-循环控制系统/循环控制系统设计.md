# 12 · 循环控制系统设计（Loop Control System）

> **本文档定位**：补齐 Loop Engineering 的"受控闭环"层，是 Civitas-AI 从 **L1 工具循环** 升级到 **L2 受控闭环** 的核心子系统。
>
> **审查依据**：见 `Docs/99-审查记录/设计审查报告-Loop与Harness工程.md`。
>
> **所属层级**：Services（服务层）。与 `Supervision/`（六模块监管）、`Context/`（分区装配）**并列且互补**，禁止互相替代。

---

## 1. 设计目标与原则

### 1.1 目标

为 Civitas-AI 每一个 Agent Loop 提供 **7 部件完整闭环**：

```
Trigger ─▶ Goal ─▶ Policy/Agent ─▶ Tools ─▶ Verifier ─▶ State ─▶ StopRules
   ▲                                                              │
   └──────────── Feedback (Actionable Failure Info) ◀────────────┘
```

### 1.2 五条不可违背原则

| # | 原则 | 说明 | 违反后果 |
|---|------|------|---------|
| P1 | **Deterministic-First** | 验证优先使用确定性硬约束（编译/测试/Schema），LLM Judge 只做兜底 | 命中失效二 |
| P2 | **Maker ≠ Checker** | 产出者与验证者必须使用不同模型 + 不同提示 + 不共享上下文 | 命中失效二 |
| P3 | **State ≠ Context** | 长期事实持久化到 `LoopState`，每轮从 State 重建 Context | 命中失效三 |
| P4 | **Every Loop Has Exactly 5 Exits** | 成功 / 上限 / 预算 / 无进展 / 风险，**五类**独立出口必须全部定义 | 命中失效一 |
| P5 | **Failure Must Be Actionable** | 反馈必须是"具体失败证据+已试策略+剩余预算"，禁止"再试一次"式反馈 | 命中失效四 |

## 2. Stop Rules：五类独立退出条件

### 2.1 规范定义

每个 Loop 启动时必须实例化一个 `StopRuleSet`：

```typescript
// Services/LoopControl/StopRules.ts
/**
 * 默认值均由 `Configs/loopConfig.json` 提供（唯一事实源，见 Docs/11 §2.8）；
 * 本 schema 中的注释只标数值含义，不重复定义默认值。
 */
interface StopRuleSet {
  /** ① 成功退出：验证器通过 */
  successCriteria: VerifierSpec[];          // 至少 1 条硬验证 + 可选规则/Rubric

  /** ② 上限退出：轮次/时间/工具调用次数（防失控） */
  limits: {
    maxIterations: number;                   // ← stopRules.limits.maxIterations
    maxWallClockMs: number;                  // ← 同上 maxWallClockMs（毫秒）
    maxToolCalls: number;                    // ← 同上 maxToolCalls
    maxConsecutiveErrors: number;            // ← 同上 maxConsecutiveErrors（与 supervision.agentConsecutiveFailuresToExpel 无关）
  };

  /** ③ 预算退出：Token/金钱，双档 */
  budget: {
    softTokens: number;                      // = token_budget × stopRules.budget.softRatio（默认 0.6）
    hardTokens: number;                      // = token_budget × stopRules.budget.hardRatio（默认 1.0）
    warmTokens: number;                      // = token_budget × warmRatio（默认 0.36）→ 预热，仅记日志
    expandRequestTokens: number;             // = token_budget × expandRequestRatio（默认 0.8）→ 申请扩预算审批
    softUsd?: number;                        // 默认由 hardUsd × softRatio 推导
    hardUsd?: number;                        // 默认 = token_budget 对应金额上限；未配置时不参与判定
  };

  /** ④ 无进展退出：连续 K 轮"信息增益指标"未改善 */
  noProgress: {
    metric: 'failed_tests' | 'validation_score' | 'goal_distance' | 'custom';
    stagnationWindow: number;                // 轮；← stopRules.noProgress.stagnationWindowRounds
    minDelta: number;                        // 相对比例 0.0–1.0；← minDeltaRatio
    action: 'switch_strategy' | 'escalate_human' | 'abort';
  };

  /** ⑤ 风险退出：命中红线立即停止（安全、合规、权限） */
  riskTriggers: Array<{
    condition: string;                        // DSL，例：'tool.dangerLevel == "DANGEROUS" || tool.dangerLevel == "FORBIDDEN"'
    action: 'pause_and_request_approval' | 'abort' | 'rollback_and_abort';
  }>;
}
```

> **DSL 约束（v2.1 修正）**：`condition` 中的 `dangerLevel` 取值**必须**是 `ToolSpec.dangerLevel` 枚举成员（`SAFE` / `CONTROLLED` / `DANGEROUS` / `FORBIDDEN`），不得使用 `DANGER` 等自造简写；解析器在实例化 `StopRuleSet` 时校验，非法字面量直接抛错。
> 判定比较一律用 `==` + 字符串枚举（`dangerLevel` 无序，不支持 `>=` 语义比较）。

### 2.2 判定优先级（每轮迭代末尾）

编号与 §2.1 的五类退出定义**严格一致**（v2.1 修正：原文出现两个"①"）：

```
⑤风险 → ②上限 → ③预算 → ④无进展 → ①成功 → 继续下一轮
```

**说明**：风险最高优先级；成功判定必须**放在所有失败判定之后**——只有"没触发任何失败/停止条件 + Verifier 通过"才算真成功。这是防"Agent 自称完成"红利的核心机制。

### 2.3 每类退出的必须动作

| 退出类型 | 必须动作 |
|---------|---------|
| ①成功 | 最终验证产物 → 归档 Trace → 触发 `KNOWLEDGE_CONSOLIDATION` 事件 |
| ②上限 | 生成 `DiagnosticSummary`（做过什么/最佳假设/下一步建议）→ 升级 |
| ③预热（warmRatio） | 仅记录 `BUDGET_WARMING` 事件，**不阻断** |
| ③软预算（softRatio） | 记录 `BUDGET_SOFT_REACHED` → `reasoningSandwich.fallbackOnBudgetSoft` 模型降级 → 并行度 ÷2 → 写审计日志 → **继续执行** |
| ③扩展审批（expandRequestRatio） | 发 `PendingApproval(kind='budget_expand')`，超时 `supervision.approvalTimeoutSec` → **默认拒绝并命中硬预算** |
| ③硬预算（hardRatio） | 强制终止 → 回滚到 `lastCheckpointId` → 升级人工 → 记 `BUDGET_HARD_REACHED` |
| ④无进展 | 依 `action` 分支：换策略 / 升级人工 / 放弃 |
| ⑤风险 | 立即冻结现场 + 挂起 Agent（律师函）+ 通知监管局 |

> **口径统一（v2.1）**：软预算动作固定为"降级 + 减并行 + 继续"三项组合，不存在"仅记录"与"阻断"两种版本；`Docs/04 §5.2.1` 与 `Docs/06 §5.4` 的事件-动作映射以本表为准。比例数值统一由 `Configs/loopConfig.json → stopRules.budget.*Ratio` 提供，**禁止**其他文档另写百分比。

## 3. Verifier 四级分层协议

### 3.1 分层定义

（严格对应 Loop Engineering 权威分层，禁止跨层调用高层代替低层）

```
L4  Human Gate        ── 人类审批门：不可逆 / 高风险 / 大额
       ▲
L3  Independent Judge ── 独立 LLM 评分：语义质量 / 需求一致性
       ▲                    （必须使用与产出者不同的模型 + 校准过）
L2  Rule Verifier     ── 规则 / 参考答案：清单覆盖 / 关键词 / 结构约束
       ▲
L1  Hard Verifier     ── 确定性：编译 / 单测 / Schema / 数值阈值 / HTTP 状态码
```

**约束**：
- **L1 未通过禁止跳到 L3**（省 Token + 防绕过）
- **L3 输出必须结构化**：`{pass, evidence[], defectCategory}`，禁止返回自然语言评分
- **每个 Loop 至少使用 L1 + 一层更高层**（禁止只用 L3 打分）

### 3.2 VerifierSpec 数据结构

```typescript
// Services/LoopControl/Verifier.ts
type VerifierSpec =
  | { level: 'L1', kind: 'test', payload: { command: string; expectExit: 0 } }
  | { level: 'L1', kind: 'schema', payload: { jsonSchema: object } }
  | { level: 'L1', kind: 'numeric', payload: { metric: string; op: '<='|'>='|'=='; threshold: number } }
  | { level: 'L1', kind: 'http', payload: { url: string; expectStatus: number } }
  | { level: 'L1', kind: 'file_exists', payload: { pathGlob: string; minSize?: number } }
  | { level: 'L2', kind: 'rule', payload: { expression: string /* CEL/JsonLogic */ } }
  | { level: 'L2', kind: 'golden', payload: { referenceArtifactId: string; tolerance: number } }
  | { level: 'L3', kind: 'llm_judge', payload: {
      model: string;                         // 必须 ≠ producerModel（由运行期从模型调用结果注入，不是配置键）
      rubric: RubricItem[];                  // 定义见 03 号文档 §7.4 Rubric 模板
      minScore: number;                      // 0.0–1.0（强制浮点比例，禁百分制）
      requireEvidence: true;
    } }
  | { level: 'L4', kind: 'human_gate', payload: {
      reason: string;                        // 为什么必须人类判
      reviewerRoles: UserRole[];              // 谁能批；映射为 PendingApproval.deciders 的 role 集合
      timeoutSec: number;                     // 超时视为拒绝；默认 = supervision.approvalTimeoutSec（60）
    } };

interface VerifierResult {
  pass: boolean;
  level: 'L1' | 'L2' | 'L3' | 'L4';
  kind: string;                              // 与 VerifierSpec.kind 同名，落库列 verifier_results.verifier_kind
  evidence: Array<{ kind: string; data: unknown }>;   // 必填，供失败反馈用
  defectCategory?: 'spec_missing' | 'logic_error' | 'quality_low' | 'risk_violation';
  costTokens: number;
  durationMs: number;
}
```

> **落库字段来源约定（v2.1）**：`verifier_results` 的 `result_id` / `loop_id` / `iteration` / `created_at` **不属于 `VerifierResult` 接口**，由 repository 在写入时从 `LoopState` 注入；同理 `failure_feedbacks`、`action_fingerprints` 的同类列。禁止为了对齐表结构而往接口里加无关字段。
> `VerifierSpec.kind` 为必落库字段（用于回放时定位具体验证器），对应列 `verifier_results.verifier_kind`。

### 3.3 Rubric 校准要求

L3 的 LLM Judge 上线前必须通过**人工标注集**校准（对齐 skill 的 benchmark.md）。数值均由 `Configs/loopConfig.json → verifier.*` 提供：

- 至少 `verifier.l3CalibrationDataset` 指向的 **50** 条"通过 / 不通过"人工标注样本
- Judge 判定与人工一致率 ≥ `verifier.l3MinAgreementWithHuman`（**0.85**）
- 每 `verifier.l3RecalibrateIntervalDay`（**90 天**）重新校准，一致性下降触发 Judge 提示词重训

### 3.4 Reward Hacking 防御

（对应 Loop Engineering §4.2 Goodhart 定律）

每个 VerifierSpec 声明时**必须同时声明 anti-gaming 补充信号**：

```typescript
interface VerifierSpecWithAntiGaming {
  primary: VerifierSpec;
  antiGaming: VerifierSpec[];   // 至少 verifier.antiGamingMinRules（默认 1）条反向检查
  // 例：primary = "所有测试通过" → antiGaming = "测试文件未被修改/删除" + "变更文件数 ≤ verifier.antiGamingMaxChangedFiles（默认 8）"
}
```

## 4. State / Context 分离：GoalReanchor 机制

### 4.1 概念切分

| | **LoopState** | **Context** |
|---|---|---|
| 定义 | 任务事实的**权威副本**，跨轮/跨会话持久 | 当前轮**动态挑选**给模型看的视图 |
| 存放 | **SQLite `civitas_main.loops.state_json`（唯一真源）** + `loop_checkpoints.state_snapshot_json`（历史快照） | 内存，每次装配生成，不持久 |
| 人读副本 | `Data/Loops/{session_key}/state.json` 为**只导出副本**（供 `LoopDebugger` 与人工排查），**禁止作为恢复入口** | — |
| 内容 | `goal` / `immutableConstraints` / `phase` / `iteration` / `completedSteps` / `failedAttempts` / `actionFingerprints` / `latestVerification` / `artifactPaths` / `budgetUsed` / `lastCheckpointId` / `pendingApprovals` / `suspension` | 从 State 挑相关切片 + 从 SharedMemory 拉胶囊 + 从 Skills 拉规范 |
| 修改时机 | 每轮 iteration 末尾（**无论成功或失败轮均写**，对应 `Docs/13 §5.1` 的每轮 checkpoint） | 每轮开头**重新装配** |
| 压缩影响 | **禁止被摘要压缩触及** | 允许被压缩 |

> **单一真源裁决（v2.1）**：原 §4.1 与本节 §10 并存"文件 `state.json`"与"DB `loops.state_json`"两处写入路径，属双真源冲突。现裁决：
> 1. **持久化真源唯一为 SQLite**；
> 2. 文件副本在 checkpoint 写入成功后同步导出（异步、失败仅 WARN，不影响主流程）；
> 3. 恢复扫描（`Docs/13 §6`）只读 SQLite，禁止读文件。

**核心红线**：**任何压缩/摘要机制不得修改 `LoopState` 的 `goal` 与 `immutableConstraints` 字段**。

### 4.2 LoopState Schema

```typescript
// Services/LoopControl/LoopState.ts
interface LoopState {
  schemaVersion: 1;
  loopId: string;                // = {session_key}#{iteration_anchor}
  traceId: string;               // 全局 UUID
  parentAgentId?: string;

  // ─── 不可变区（禁止任何自动机制修改） ───
  goal: {
    originalRequirement: string;   // 用户/上游 Agent 的原始表述，逐字保留
    successCriteria: VerifierSpec[];   // 见 §3
    immutableConstraints: string[];    // "不允许修改 X" "必须保持 Y"
  };
  createdAt: number;

  // ─── 可变区 ───
  phase: 'planning' | 'acting' | 'verifying' | 'awaiting_approval' | 'completed' | 'failed';
  iteration: number;
  completedSteps: Array<{ stepId: string; artifact?: string; verifiedAt: number }>;
  failedAttempts: FailedAttempt[];             // 见 §5
  actionFingerprints: FingerprintRecord[];      // 含 iteration 维度，支撑 §5.2 的窗口计数
  latestVerification?: VerifierResult;
  artifactPaths: string[];                      // 已产出文件路径（checkpoint 清单的轻量镜像）
  budgetUsed: { tokens: number; usd: number };
  lastCheckpointId: string;                     // 见 13 号文档「持久执行与恢复」

  // ─── 挂起区 ───
  pendingApprovals: PendingApproval[];          // §6 人工审批门
  suspension?: SuspensionRecord;                // 律师函挂起（05 号文档定义）
}

interface FailedAttempt {
  attemptId: string;
  iteration: number;
  strategy: string;                // 用了什么方案（≤ 30 字，同 TurnStrategy 字数上限）
  failureCategory: FailureCategory;   // 见 §7.2，与 FailureFeedback 共用同一枚举
  evidence: unknown;               // 具体失败证据（错误栈、失败测试名、工具输出等）
  costTokens: number;
}

/** 动作指纹记录：支撑 §5.2 的窗口计数（原 string[] 无法表达 iteration 维度） */
interface FingerprintRecord {
  fingerprint: string;             // SHA-256(toolName + canonicalJson(args))
  toolName: string;
  iteration: number;
  countInIteration: number;        // 同一 iteration 内重复次数
  recordedAt: number;              // epoch ms
}
```

> **枚举统一（v2.1）**：`FailureCategory` 全集以 §7.2 `FailureFeedback.failureCategory` 为准（8 个成员），`FailedAttempt` 与 `failure_feedbacks.category` 均引用同一结合；禁止再维护 6 成员的第二套枚举。

### 4.3 GoalReanchorMiddleware

新增中间件（挂载在 `wrapModelCall` 前钩子）：

```typescript
// Services/LoopControl/middleware/GoalReanchorMiddleware.ts
class GoalReanchorMiddleware implements AgentMiddleware {
  hook = 'beforeModel';

  async run(ctx: LoopContext) {
    const state = await ctx.loopState.load();
    // 每 K 轮（默认 K=5）或每次上下文压缩后，强制重新锚定
    if (ctx.iteration % this.reanchorEvery === 0 || ctx.justCompressed) {
      ctx.messages.unshift({
        role: 'system',
        content: [
          '【任务原始目标（不可修改，仅可参考）】',
          state.goal.originalRequirement,
          '【不可违背约束】',
          ...state.goal.immutableConstraints.map(c => `- ${c}`),
          '【已尝试且失败的策略】',
          ...state.failedAttempts.slice(-5).map(f =>
            `- 迭代 ${f.iteration}：${f.strategy} → ${f.failureCategory}（避免重复）`),
        ].join('\n'),
        isReanchor: true,   // 标记为注入项，不参与压缩
      });
    }
  }
}
```

**默认参数**：`goalReanchor.reanchorEveryRounds`（=5）与 `goalReanchor.alwaysOnAfterCompression`（=true）；注入失败策略条数 = `goalReanchor.injectRecentFailedStrategiesCount`（=5）。均来自 `Configs/loopConfig.json`。

## 5. 重复动作与局部循环：ActionFingerprint + Strategy Ledger

### 5.1 Action Fingerprint 定义

```
fingerprint = SHA-256( toolName + canonicalJson(toolArgs) )
```

**规范化 JSON**：字典序排序键、去除 optional 空字段、数字统一 float 表示。

### 5.2 检测规则

阀值均自 `Configs/loopConfig.json → fingerprint.*`（数值不在本文重复定义）：

| 触发条件 | 配置项 | 动作 |
|---------|-------|------|
| 单次迭代内 fingerprint 相同 ≥ `singleIterationWarnThreshold`(2) | `fingerprint.singleIterationWarnThreshold` | WARN，注入提示"你刚做过这个" |
| 连续 `consecutiveDuplicateRounds`(3) 次相同 fingerprint | `fingerprint.consecutiveDuplicateRounds` | 强制进入 `noProgress.action = 'switch_strategy'` 分支 |
| `windowRounds`(5) 轮内相同 fingerprint 累计 ≥ `windowHitThreshold`(3) | `fingerprint.windowRounds` + `windowHitThreshold` | 触发 `ACTION_FINGERPRINT_DUPLICATE` 事件到监管局 |
| 两个 Agent 相同 fingerprint 交叉出现 ≥ `crossAgentDuplicateThreshold`(2) | `fingerprint.crossAgentDuplicateThreshold` | 触发死锁保护（见 03 §路由） |

**重叠仲裁规则（v2.1 新增，原缺）**：
1. 多条件同一轮命中时，按**动作强度升序**只执行最强一个：`WARN < switch_strategy < 事件上报 < 死锁保护`；
2. 已进入 `switch_strategy` 后，同一 `fingerprint` 在当前策略周期内**不得重复上报** `ACTION_FINGERPRINT_DUPLICATE`（以 `(loopId, fingerprint, strategyEpoch)` 为去重键）；
3. fingerprint 检测属于**④无进展退出的前置信号**，不独立构成退出；它只能触发 `noProgress` 分支或事件上报，禁止直接终止 Loop；
4. 上述优先级必须纳入 §2.2 判定链的 `④无进展` 分支内部，不改动五类退出的主链次序。

> **事件名修正**：原写为 `LOOP_DETECTED`，该名称未在事件注册表登记；统一使用 `ACTION_FINGERPRINT_DUPLICATE`（已登记于 07 号文档 §3，v2.1 补全）。

### 5.3 Strategy Ledger（策略账本）

每轮结束时，Agent 必须**结构化输出**本轮策略摘要（不是自由文本）：

```typescript
interface TurnStrategy {
  iteration: number;
  strategy: string;          // ≤ 30 字（强制字数上限，防灌水）
  expectedOutcome: string;   // 本轮想达到什么
  actualOutcome?: string;    // 下轮回填
  failureReason?: string;    // 下轮回填
}
```

**存储位置（v2.1 修正）**：**`civitas_main.strategies_ledger` 表为唯一真源**（DDL 见 Docs/10 §8.2）。`TurnStrategy` **不再**写入 `LoopState.failedAttempts`（原设计矛盾：`FailedAttempt` 无 `expectedOutcome`/`actualOutcome`/`failureReason` 三字段）；`LoopState` 仅在 `failedAttempts[].strategy` 保留 ≤ 30 字的策略摘要文本以供 reanchor 注入。
人读副本 `Data/Loops/{session_key}/strategies.jsonl` 为异步导出件，禁止作为数据源。

### 5.4 "换策略"具体动作

当 `noProgress.action = 'switch_strategy'` 触发时：

1. **禁止**简单重跑；
2. 从 `Skills/strategies/{taskType}/` 加载候选策略集（见 §11 Intent Debt）；
3. 排除 `LoopState.failedAttempts.map(a => a.strategy)`；
4. 若无可用策略 → 自动升级为 `escalate_human`；
5. 若有可用策略 → 注入下一轮 Context 的 reanchor 段：`"上一策略失败原因：X；本次尝试替代策略：Y"`。

## 6. Human Gate：审批门与挂起队列

### 6.1 何时触发（对齐 skill 的"操作不可逆性"原则）

| 条件 | 触发审批 | 审批人角色 | 对应审批 `kind` |
|------|---------|----------|----------------|
| 工具危险级 = `DANGEROUS` | ✅ 强制 | 用户 + Prime Director | `tool_execute` |
| 工具危险级 = `CONTROLLED` 且首次使用 | ✅ 一次授权，会话内免审 | 用户 | `tool_execute` |
| 预算使用 ≥ `stopRules.budget.expandRequestRatio`(0.8) × token_budget | ✅ | 用户 | `budget_expand` |
| 不可逆副作用（`reversibility='IRREVERSIBLE'` 或 `sideEffectScope='external'`） | ✅ | 用户 + Prime Director | `irreversible_action` |
| 涉及 `~/.ssh/` `Data/Auth/` 等硬禁路径 / 工具危险级 = `FORBIDDEN` | ❌ **直接拒绝，不进入审批** | — | — |
| 生产环境部署类工具（如 `shell.exec` 命中 `deploy/` `prod/`） | ✅ | 用户 | `irreversible_action` |
| 开除 Agent / 冻结其他 Agent | ✅ | Regulatory Authority | `irreversible_action` |
| Verifier L4 显式声明 | ✅ | 声明中的 `reviewerRoles` | `judge_override` |

> **预算触发修正（v2.1）**：原写"单笔 Token 支出 > 用户预算 20%"，与硬预算 100% 中止矛盾（达到 120% 时硬预算已早先触发）。现统一为**累计使用 ≥ `expandRequestRatio`（默认 0.8）** 即申请扩容审批，与 §2.3 退出动作表完全一致。
> **`FORBIDDEN` 语义裁决**：硬禁项**不产生审批记录**（避免"刷审批通过"路径），直接写 `operation_history` 失败 + `WARN` 安全事件；只有 `DANGEROUS` / `IRREVERSIBLE` 才进入审批队列。

### 6.2 审批队列实现

```typescript
// Services/LoopControl/ApprovalGate.ts
interface PendingApproval {
  approvalId: string;             // = {timestamp_ms}-{4位hex}（复用全局 operation_id 格式）
  loopId: string;
  iteration: number;              // 发起时的轮次（对应表列 iteration，v2.1 补）
  requestedAt: number;            // epoch ms
  requestedBy: string;            // agentId
  kind: 'tool_execute' | 'budget_expand' | 'irreversible_action' | 'judge_override';
  payload: unknown;
  riskLevel: RiskLevel;           // 'LOW' | 'MEDIUM' | 'HIGH' | 'CRITICAL'
  timeoutSec: number;             // 默认 supervision.approvalTimeoutSec（60）；落库为 expires_at = requestedAt + timeoutSec
  defaultOnTimeout: 'reject' | 'abort_loop';   // 默认 'reject'；禁止默认通过
  deciders: ApprovalDecider[];    // 审批人与权重
  decisionPolicy: 'majority' | 'unanimous';    // 默认 majority；riskLevel='CRITICAL' 强制 unanimous
  status: 'PENDING' | 'APPROVED' | 'REJECTED' | 'TIMEOUT';
  decidedBy?: string[];
  decidedAt?: number;
  decisionReason?: string;
}

interface ApprovalDecider {
  role: UserRole;
  weight: number;                 // 默认 1.0；CRITICAL 级至少 2 个不同角色（supervision.criticalApprovalRoles）
}
```

> **单位统一（v2.1）**：原 `timeout: number // 默认 60_000 ms` 与正文"60s"两处单位不一致。现统一为 **`timeoutSec`（秒）**，接口层一律 `_sec` 后缀。
> 落库同时保存两列：`pending_approvals.timeout_sec`（**生效时长快照**，秒）与 `pending_approvals.expires_at`（**绝对时间点**，epoch ms，= `requested_at + timeout_sec × 1000`）；前者供审计回放，后者供超时扫描，**不得只存其一**。
> **与 L4 `human_gate.timeoutSec` 的关系**：L4 声明的 `timeoutSec` 为**覆盖值**；未声明时继承 `supervision.approvalTimeoutSec`。生效值写入 `timeout_sec` 快照，防配置热更新导致存量审批语义突变。
> **审批人单一口径**：`reviewerRoles`（L4 声明）→ `deciders[].role`（运行时实例）→ `deciders_json`（落库）为同一名单的三个形态，禁止引入第四套命名。
> **枚举三处同形**：`riskLevel` / `status` / `kind` / `decisionPolicy` 在 TS、`pending_approvals` 表、UI 三处**字面量完全相同**（不做大小写转换），详见 `Docs/11 §1.2.1 豁免 X3`。

**存储**：SQLite 表 `civitas_main.pending_approvals`（DDL 唯一事实源见 **Docs/10 §8.2**）。

### 6.3 审批期间的 Loop 处理

- **禁止**继续执行触发审批的那一步；
- **允许**其他并行步骤继续（若无依赖）；
- Agent 状态置 `AWAITING_APPROVAL`（枚举名，**与 `LoopState.phase = 'awaiting_approval'` 是同一语义的两个平面**：前者为 Agent 状态机状态（`Docs/02 §6`，PascalCase 枚举），后者为 Loop 阶段字符串（DB 存储，snake_case）；映射关系固定，禁止第三套写法）；
- 超时（`supervision.approvalTimeoutSec`，默认 60 秒）→ **默认拒绝 + 记录 `APPROVAL_TIMEOUT_REJECTED`**；同一 Agent 1 小时内累计 ≥ 3 次超时拒绝→上报监管局。

### 6.4 与"不可中断"红线的关系

（对齐 skill：LLM 循环中只有暂停符和停止符可以阻断）

**审批门 = 停止符的合法来源之一**，通过显式 `LoopConfig.pauseSignal` 触发，不违反"不可中断"红线。**必须写入 ADR-0001**（见 §12）。

## 7. Failure Feedback 协议：可行动的失败信息

### 7.1 禁止的反馈形式

- ❌ "验证失败，请重试"
- ❌ "质量不达标"
- ❌ "再试一次"
- ❌ 只返回 `score: 45`

### 7.2 强制的反馈形式

```typescript
// Services/LoopControl/FailureFeedback.ts
type FailureCategory =
  | 'schema' | 'logic' | 'external' | 'timeout'
  | 'risk' | 'no_progress' | 'budget_soft' | 'budget_hard';   // 8 成员，唯一定义处

interface FailureFeedback {
  iteration: number;
  failureCategory: FailureCategory;      // 与 FailedAttempt.failureCategory 同一结合
  evidence: {
    kind: 'test_output' | 'error_stack' | 'diff_from_expected' | 'tool_error' | 'rule_violation' | 'judge_rubric';
    data: unknown;              // 原始可机器解析
    excerpt?: string;           // ≤ failureFeedback.evidenceExcerptMaxChars（默认 500）字人类可读片段
  }[];
  comparedWithLastAttempt?: {   // 与上一轮的差异
    improvement: number;        // 相对指标改善（0.0–1.0，可负 = 恶化）
    newFailures: string[];
    resolvedFailures: string[];
  };
  triedStrategies: string[];    // 已试过的策略摘要（防重复）
  remainingBudget: { tokens: number; iterations: number; seconds: number };
  recommendedNextAction?: NextAction;
}

type NextAction = 'switch_strategy' | 'request_approval' | 'abort' | 'escalate_human' | 'rollback_and_abort';
```

> **枚举打通（v2.1）**：原先 `noProgress.action`（3 值）、`riskTriggers.action`（3 值）、`recommendedNextAction`（4 值）三套动作枚举互不包含，实现时易出现无法表达的指令。现裁决：
> - `NextAction` 为**动作全集**（5 值，含 `rollback_and_abort`），供 `recommendedNextAction` 使用；
> - `noProgress.action` 取值域为 `NextAction` 的**子集** `'switch_strategy' | 'escalate_human' | 'abort'`（配置校验器拒其他值：无进展时无意义请求审批）；
> - `riskTriggers.action` 取值域为 `'pause_and_request_approval' | 'abort' | 'rollback_and_abort'`（风险时不允许自行换策略）；
> - 两个子集与全集的映射由 `Services/LoopControl/actionSchema.ts` 集中心维护，禁止就地硬编码。

### 7.3 注入位置

`FailureFeedback` 序列化后作为 **tool_result** 回传给模型（不占用 reanchor 段），格式：

```json
{
  "role": "tool",
  "tool_call_id": "verify-{iteration}",
  "status": "error",
  "recoverable": true,
  "content": { /* FailureFeedback */ }
}
```

## 8. Trigger 防风暴

### 8.1 规范

每个入口必须实现（数值均自 `Configs/supervision.json` §2.7，本文不重复定义）：

| 机制 | 说明 | 配置项 |
|------|------|--------|
| **去重键（dedupKey）** | `hash(source + intent + target)`，窗口内相同键直接返回旧结果 | `triggerDedupWindowSec`(300) |
| **冷却期（cooldown）** | 同一 Agent 被连续触发时最小间隔 | `triggerCooldownSec`(30) |
| **幂等 ID（idempotencyId）** | 客户端传入，服务端保留 | `triggerIdempotencyTtlHour`(24) |
| **优先级队列 + 并发上限** | 全局 / 单用户并发 Loop | `maxConcurrentLoopsGlobal`(20) / `maxConcurrentLoopsPerUser`(5) |
| **任务风暴断路器** | 每分钟触发数超阈即熔断 | `stormBreakerThresholdPerMin`(100) → `stormBreakerOpenSec`(60) |

> **两种幂等键不得混用（v2.1）**：本节的 `dedupKey`/`idempotencyId` 是**入口风暴防护**（`hash(source+intent+target)`，窗口 5 分钟 / 24 小时）；`Docs/13 §7` 的 `idempotencyKey`（`SHA-256(toolName + canonicalJson(pick(args, keyFields)) + loopId)`）是**工具副作用重放防护**。两者参与量、算法、作用域均不同，实现时禁止复用同一字段或同一缓存。

### 8.2 实现位置

- Interface 层：`InputDeduplicationMiddleware`
- Services 层：`LoopScheduler`（含并发上限与优先级）
- Infra 层：`IdempotencyStore`（**SQLite，表 `idempotency_cache`**）

> **介质裁决（v2.1）**：原写"Redis / SQLite"两可。现确定：**Phase 0–2 一律 SQLite**（`durable.idempotency.store = "sqlite"`），Redis 仅作为 Phase 3 水平扩展的可选升级，不得提前引入。
