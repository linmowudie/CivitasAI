## 1. 背景与目标

### 1.1 问题

Civitas-AI 是**桌面应用**（Electron 壳 + 进程内本地服务 `:3000` + SQLite 三库）。
所有用户数据都落在客户端本机：

- 设置：`Configs/*.json` 与 `system_config` 表
- 记忆：`long_term_memory` 表
- 统计与账本：`token_wallets` / `token_transactions` / `events`
- 会话与消息：`chat_sessions` / `chat_messages`

一旦用户**卸载软件、换机、重装系统**，这些数据即随之消失，且没有任何找回途径。
这是产品层面的硬缺口：**用户投入的使用积累（偏好、记忆、统计）与软件安装状态强耦合**。

### 1.2 目标与非目标

| 类型 | 内容 |
|---|---|
| **目标** | ① 账户体系（注册/登录/登出/改密/注销/设备管理）；② 设置云端权威存储与拉取；③ 个人统计上报与聚合；④ 记忆云端存储与检索；⑤ **一键备份/恢复**（重装重建）；⑥ 自托管、可本地跑、可上服务器；**⑦ 任务（会话）元数据同步**（标题 + 归档状态，见 §4.10）；**⑧ 验证码登录与设备自助管理**（见 §10.5） |

### 1.4 术语

| 术语 | 含义 |
|---|---|
| **端侧 / 客户端** | Electron 应用（`Client/` + `Src/` 进程内服务） |
| **服务端** | 本文对象，`Server/` 独立 Node 进程 |
| **访问令牌** | JWT（HS256，默认 900s），业务声明只含 `sub`/`sid`/`typ`（另带标准 `iss`/`aud`/`iat`/`exp`，见 `security/tokens.ts` 的 `signAccessToken()`）；**2026-10-03 校准**：原文写"只含 `sub`/`sid`"，实际签发时还写入 `typ: 'access'` 与签发方/受众/时间声明。每次请求由守卫按 `sid` 回查会话状态（SV-002 即时吊销） |
| **刷新令牌** | 不透明随机串，服务端只存 sha256；用于换取新访问令牌 |
| **令牌家族（family）** | 一次登录产生的刷新令牌轮换链；重用检测以其为吊销单位 |
| **`clientMemoryId`** | 端侧 `memory_id`，上传后用于幂等对齐 |
| **revision** | 设置版本号，单调递增，用于乐观并发 |
| **备份包** | `format=civitas.backup` 的自包含 JSON |
| **任务元数据** | **2026-10-03 校准（新增）**：客户端会话的"标题 + 归档状态 + 本机时间戳"，以 `clientSessionId` 为幂等键存于 `user_tasks`；**不含消息正文** |
| **设备凭据（deviceCredential）** | **2026-10-03 校准（新增）**：客户端安装期生成的随机串，服务端只存 `sha256`（`user_devices.credential_hash`），取代易变硬件指纹 |

## 2. 总体架构

### 2.1 在系统中的位置

```
┌───────────────────────── 用户机器 ─────────────────────────┐
│                                                            │
│  ┌── Electron 应用（桌面端）───────────────────────────┐   │
│  │  渲染进程 Client/（React）                          │   │
│  │        │ IPC / backend-event                       │   │
│  │  主进程 + 进程内本地服务 Src/（HTTP :3000, SQLite） │   │
│  └────────┬───────────────────────────────────────────┘   │
│           │  HTTPS + Bearer <accessToken>                  │
└───────────┼────────────────────────────────────────────────┘
            │
            ▼
┌──────────────────── 服务端 Server/（自托管）────────────────────┐
│  Fastify 5（:8787）                                              │
│   ├─ 中间件链：安全响应头 → 限流(onRequest) → 路由 → 写限流      │
│   ├─ routes/  ── 鉴权守卫 + Zod 校验 + 统一响应                  │
│   ├─ services/ ── 业务规则（鉴权/设置/统计/记忆/任务元数据/备份） │
│   ├─ repositories/ ── 参数化 SQL                                 │
│   └─ db/pool ── 连接池（statement_timeout / 池上限）             │
│                              │                                   │
│                              ▼                                   │
│                 PostgreSQL（10 张业务表 + 迁移记录）             │
└──────────────────────────────────────────────────────────────────┘
```

> **2026-10-03 校准（S01-D01）**：架构图原写"7 张表 + 迁移记录"。按 `Server/migrations/001–005` 实际统计为
> **10 张业务表**（`001_init.sql` 6 张：`users`/`refresh_tokens`/`user_settings`/`usage_events`/`memories`/`audit_log`；
> `002` 增 `verification_codes`/`user_devices`；`004` 增 `rate_limit_buckets`；`005` 增 `user_tasks`）
> **+ `schema_migrations`**（迁移器创建，不计入业务表）。表定义见 §3.2。

**与进程内本地服务（`:3000`）的关系**：两者互不依赖。本地服务继续负责本机的 Agent 循环、工具执行、
事件流与本地库；服务端只负责"需要跨设备/跨重装存活"的数据。`Server/` 是**独立 npm 包**，
其依赖（fastify/pg/jose/argon2）**不进入 Electron 打包**（见根 `package.json` 的 `build.files` 未包含 `Server/`）。

### 2.2 分层结构

| 层 | 目录 | 职责 | 约束 |
|---|---|---|---|
| 路由层 | `Server/src/routes/` | HTTP 语义、鉴权守卫、入参校验、响应包装 | 不含业务规则，不直接写 SQL |
| 服务层 | `Server/src/services/` | 业务规则与编排（事务、策略、DTO 映射） | 不感知 Fastify |
| 仓储层 | `Server/src/repositories/` | 参数化 SQL、行↔对象映射 | 不含业务判断 |
| 基础设施 | `Server/src/db/`、`src/http/`、`src/security/` | 连接池、迁移、错误/响应/校验/限流、密码与令牌 | 被上层复用 |

依赖方向单向向下（routes → services → repositories → db），横向能力（http/security）按需注入，
依赖通过 `AppContext` 显式组装（`Server/src/app.ts` 的 `buildApp()`），因此测试可直接用
`fastify.inject()` 构建应用而不监听端口。

### 2.3 设计原则

| # | 原则 | 落地方式 |
|---|---|---|
| S1 | **服务端权威** | 设置/记忆以服务端为唯一真源；客户端登录后拉取，写入上行；`revision` 提供并发保护 |
| S2 | **幂等优先** | 记忆按 `clientMemoryId` upsert；统计按 `clientEventId` 去重；重装重传不产生重复 |
| S3 | **失败即拒绝** | 生产缺密钥拒绝启动；迁移 checksum 不符拒绝执行；超限直接 4xx；5xx 不外泄细节 |
| S4 | **最小暴露** | 令牌不含 PII；审计保留但注销账号即级联清除业务数据；日志脱敏 |
| S5 | **可自托管** | 单个 PostgreSQL + 单进程即可；无外部强制依赖（无 Redis/消息队列/对象存储） |
| S6 | **测试可复现** | 集成测试跑真 PostgreSQL；无库环境自动跳过；E2E 脚本可重跑 |

### 2.4 技术选型与理由

| 维度 | 选择 | 备选 | 理由 |
|---|---|---|---|
| 运行时 | Node 20+ / ESM | — | 与现有工程一致（根 `package.json` `"type": "module"`） |
| Web 框架 | **Fastify 5** | Express、Koa、原生 `node:http` | 内置 schema 校验/日志/生命周期钩子；`app.inject()` 便于无端口测试；生态成熟 |
| 数据库 | **PostgreSQL 16** | SQLite、MySQL | 多用户与并发写；`jsonb`、部分唯一索引、GIN 全文索引、`timestamptz` 时区运算均为刚需 |
| 驱动 | `pg` | postgres.js | 生态最广、`Pool` 语义清晰；显式参数化查询 |
| 密码哈希 | **Argon2id**（`@node-rs/argon2`） | bcrypt、scrypt | OWASP 首选；`@node-rs` 提供预编译二进制，**免除 node-gyp**（本项目在 better-sqlite3 上已吃过编译坑） |
| 令牌 | **JWT HS256**（`jose`）+ 不透明刷新令牌 | 纯会话表、PASETO | 访问令牌验签无状态；会话状态回查共享 PG（SV-002），多实例仍可横向扩展；刷新令牌落库以便吊销；`jose` 为纯 ESM、无原生依赖 |
| 校验 | **Zod** | ajv、joi | 与主工程一致（根依赖已含 zod），错误可映射为字段路径 |
| 迁移 | 自研 SQL 迁移器（60 行） | Prisma、Knex、Flyway | 纯 SQL 可审计、无额外运行时；checksum 漂移检测满足 S3 |
| 限流 | **双实现**：内存滑动窗口（dev/test 默认）+ **PostgreSQL 固定窗口共享计数**（生产默认） | Redis、`@fastify/rate-limit` | 自托管单实例够用且**零外部依赖**（PG 已是必需依赖，共享计数不必引入 Redis）；由 `RATE_LIMIT_STORE=memory|postgres` 切换（`config.ts`），实现同一 `RateLimiter.consume` 接口。PG 实现用单条原子 UPSERT 计数（`http/rateLimit.ts` 的 `createPostgresRateLimiter`，`rate_limit_buckets` 表见迁移 004），DB 抖动时**回退进程内计数**兜底。**2026-10-03 校准（S01-D09）**：本行原写"进程内滑动窗口 / 零外部依赖"，未随 L1（SV-003，2026-10-03）落地更新，且 PG 实现是**固定窗口**而非滑动窗口（跨窗口边界可能多放行一小段，属固定窗口固有特性，已在源码注释声明） |

| 事件 | 影响 |
|---|---|
| 用户注销账号（`DELETE /v1/me`） | 审计 `user_id` 置 NULL → 删除 `users` 行 → **级联删除** `refresh_tokens`/`user_settings`/`usage_events`/`memories`/`user_devices`/`user_tasks`（均带 FK CASCADE）。**现状记录（2026-10-03 校准）**：`verification_codes`（按 `email_lower` 关联）与 `rate_limit_buckets`（全局计数）**无 FK、不随级联删除**，注销后残留 |

| 记忆删除（`?hard=true`） | 物理删除 |
| 刷新令牌轮换 | 旧行保留并标记 `revoked_at='rotated'` + `rotated_to`，供审计追溯 |
| 过期/吊销令牌 | 由 `purgeInactive(db, 60)` 清理：**入口启动即扫一次，此后每 6 小时一次**（`index.ts`，SV-004 已接线，定时器 `unref()`，退出时 `clearInterval`），详见 §9.5 |

| 任务元数据上行 | `upsertTask()` 按 `(user_id, client_session_id)` 覆盖：`title`/`updated_at`/`archived_at` 直接取新值，`created_at` 取 `LEAST(旧, 新)`，`synced_at` 刷新为 `now()`；重复上行不产生新行（幂等） |
| 验证码生命周期 | 签发即"单活"（同邮箱同用途旧码置 `used_at`）；`expires_at` 到期或失败次数达上限即不可用。⚠️ **未接线/目标态**：`repositories/verificationCodes.ts` 的 `cleanupExpiredCodes()` 已有实现，但**无调用方**（`index.ts` 的定期维护只清刷新令牌），过期码行会留在表内 |

## 4. 接口设计

### 4.1 通用约定

| 项 | 约定 |
|---|---|
| 基地址 | `http(s)://<host>:<port>`（默认 `http://127.0.0.1:8787`） |
| 版本前缀 | `/v1/...`（业务接口）；`/healthz`、`/readyz` 无前缀 |
| 成功响应 | `{ "ok": true, "data": <payload> }` |
| 失败响应 | `{ "ok": false, "error": { "code", "message", "details"? } }` |
| 鉴权 | `Authorization: Bearer <accessToken>`；免鉴权仅 `/healthz`、`/readyz`、`/v1/auth/register|login|refresh` **+ `/v1/auth/send-code` + `/v1/auth/login-with-code`**（`routes/auth.ts` 未挂 `guard` 的 POST 路由）。**2026-10-03 校准（S01-D04）**：后两条此前只出现在 §10.5，本行清单未收录 |
| 请求体 | `application/json`；上限 `BODY_LIMIT_BYTES`（默认 1 MiB），非 JSON → `400`，超限 → `413` |
| 时间 | 入参 ISO 8601 **含时区**；出参一律 UTC ISO（`Z`） |
| 分页 | 键集（keyset）分页：`limit`（1–200，默认 50）+ `cursor`（不透明串） |
| 并发 | 设置写入可带 `expectedRevision`；不匹配 → `409 REVISION_MISMATCH`（带 `currentRevision`） |
| 幂等 | 记忆 `clientMemoryId`、统计 `clientEventId` |
| 限流 | 超限 → `429` + `Retry-After`，并始终返回 `X-RateLimit-Limit` / `X-RateLimit-Remaining` |
| 安全头 | `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`、`Cache-Control: no-store` |

### 4.2 错误码

| code | HTTP | 触发场景 | 客户端建议动作 |
|---|---|---|---|
| `VALIDATION_ERROR` | 400 | 入参不符合 schema（`details.issues` 含字段路径） | 修正入参；不要重试 |
| `UNAUTHENTICATED` | 401 | 缺少/伪造访问令牌 | 用刷新令牌换取新访问令牌；失败则重新登录 |
| `INVALID_CREDENTIALS` | 401 | 邮箱或密码不正确（统一文案） | 提示用户；不可区分账号是否存在 |
| `TOKEN_EXPIRED` | 401 | 访问/刷新令牌过期 | 走刷新流程或重新登录 |
| `TOKEN_REUSED` | 401 | 已轮换的刷新令牌被再次使用 | **清空本地令牌并重新登录**（整个家族已失效） |
| `FORBIDDEN` | 403 | 账号停用 / 无权操作该会话 | 提示并停止操作 |
| `NOT_FOUND` | 404 | 资源不存在或不属于当前用户 | 从本地缓存移除 |
| `CONFLICT` | 409 | 邮箱已被注册 / 新密码与旧密码相同 | 提示用户 |
| `REVISION_MISMATCH` | 409 | 设置 `expectedRevision` 不匹配 | 拉最新 `revision` 后重试 |
| `PAYLOAD_TOO_LARGE` | 413 | 设置体积 / 批量条数 / 请求体超限 | 分批上报 |
| `RATE_LIMITED` | 429 | 触发限流 | 依据 `Retry-After` 退避 |
| `UNSUPPORTED` | 415 | 非 `application/json` | 修正 Content-Type |
| `UNAVAILABLE` | 503 | 服务暂不可用（当前用于 `/readyz` 的数据库探测失败，`errors.ts` 的 `unavailable()`；SV-008） | 探活摘流量；退避重试；运维检查数据库连通 |
| `INTERNAL` | 500 | 服务端异常（**文案不外泄细节**） | 退避重试；持续失败上报 |

### 4.3 账户与鉴权

## 5. 鉴权与安全设计

### 5.1 威胁模型（简版 STRIDE）

| 威胁 | 场景 | 对策 | 落地位置 |
|---|---|---|---|
| **欺骗** | 伪造/窃取令牌 | 短时 JWT + 守卫按 `sid` 回查会话状态（SV-002）；刷新令牌只存哈希；刷新轮换；重用即吊销整族 | `http/authGuard.ts`、`security/tokens.ts`、`services/authService.ts` |
| **篡改** | 改他人数据 | 所有查询带 `user_id` 条件；跨用户访问 → 404 | `repositories/*` |
| **抵赖** | 否认操作 | 审计日志（登录/改密/令牌重用/登出） | `repositories/audit.ts` |
| **信息泄露** | 撞库、枚举邮箱、日志泄漏 | 统一失败文案 + 等价耗时假校验；密码/令牌字段日志脱敏；5xx 不回细节 | `security/password.ts`、`app.ts` redact |
| **拒绝服务** | 暴力破解、洪泛 | 鉴权接口按 IP 严限流；写操作按用户限流；请求体/批量大小上限 | `http/rateLimit.ts`、`limits.*` |
| **权限提升** | 越权吊销他人会话、注入 | 会话归属校验；全参数化 SQL；Zod 白名单字段 | `authService.revokeSession`、`repositories/*` |

### 5.2 密码存储

- 算法 **Argon2id**：`memoryCost=19456`(19 MiB)、`timeCost=2`、`parallelism=1`、`outputLen=32`
  （`Server/src/security/password.ts`，OWASP 推荐配置）。
- 每用户独立随机盐（由算法内置），同一密码两次哈希结果不同（单测断言）。
- 校验失败（哈希损坏/算法不支持）返回 `false` 而非抛错，避免错误细节外泄。
- 邮箱不存在时执行 `fakeVerify()` 做等价耗时运算，抹平"账号是否存在"的时间差。

### 5.3 令牌生命周期

```
注册/登录
  │  ① 生成 refreshToken（32 字节随机）→ 存 sha256 入库（family_id 新建）
  │  ② 签发 accessToken（JWT HS256，含 sub=userId, sid=refreshToken.id，TTL 900s）
  ▼
使用 accessToken 调业务接口（守卫验签 + 按 `sid` 回查会话状态）
  │
  ├─ 访问令牌过期 ──▶ POST /v1/auth/refresh
  │                      │  ③ 校验 sha256(入参) 命中且未吊销、未过期
  │                      │  ④ 同 family 签发新 refreshToken
  │                      │  ⑤ 旧令牌 revoke(reason=rotated) 并记 rotated_to
  │                      └─▶ 旧令牌**再次**出现 ──▶ 判定泄漏
  │                                                 ⑥ revokeFamily() 吊销整族
  │                                                 ⑦ 审计 outcome=failure/reason=token_reuse
  │                                                 ⑧ 返回 401 TOKEN_REUSED
  │
  ├─ 改密 ──▶ 校验当前密码 → 更新哈希 → revokeAllForUser(password_changed)
  │             → 为当前设备换发新令牌（其他设备需重新登录）
  └─ 登出 ──▶ 单设备 revoke(logout) / 全部设备 revokeAllForUser(logout_all)
```

配置开关 `ALLOW_REFRESH_REUSE`（默认 `false`）：置 `true` 时刷新**不吊销**旧令牌（兼容性场景），
生产环境会打印告警（`config.ts`）。

**访问令牌即时吊销（SV-002，2026-10-03）**：访问令牌自身无状态，但 `sid` 即会话行
（`refresh_tokens.id`）——鉴权守卫（`http/authGuard.ts`）验签后按 `sid` 回查该行（PK 查询），
已吊销/不存在/已过期即返回 401 `UNAUTHENTICATED`（“会话已失效，请重新登录”）。
改密/登出（单设备或全部）/单会话吊销后，旧访问令牌**在下一个请求内即失效**，不再等 TTL 窗口；
客户端收到该 401 会先尝试刷新，刷新失败即清空登录态（`serverApi.ts`）。

### 5.4 防暴力破解与枚举

- 限流：`/v1/auth/*` 按 IP（`RATE_LIMIT_AUTH_PER_MIN` 默认 20/min）；其他接口按 IP（240/min）；
  写操作按用户（120/min）。窗口语义**取决于 `RATE_LIMIT_STORE`**（`Server/src/http/rateLimit.ts` 双实现，见 §2.4）：
  `memory` = **滑动窗口** 60s（按时间戳精确计数，dev/test 默认）；`postgres` = **固定窗口** 60s
  （单条原子 UPSERT、多实例共享计数，生产默认；跨窗口边界可能多放行一小段）。超限一律 `429` + `Retry-After`。
  **2026-10-03 校准（S01-D09）**：本条原写"滑动窗口 60s"，未随 SV-003 落地的 PG 实现更新。
- **写限流桶（`write:<userId>`）只对已鉴权的写请求生效**（`app.ts` 的 `preHandler` 钩子在 `request.auth` 缺失时直接跳过）：
  因此 `register` / `login` / `refresh` / `send-code` / `login-with-code` 这些免鉴权 POST 只受 `auth:<ip>` 约束，
  不受 120/min 的用户级写限流约束。
- 登录失败/成功均写审计（含 IP/UA），便于事后分析。
- 账号停用（`status=disabled`）登录返回 `403 FORBIDDEN` 并记审计（不泄露给未认证观察者）。

### 5.6 配置与密钥安全

- 密钥来源：环境变量（生产）或 `Server/.env`（开发）；**真实环境变量优先于文件**（容器/CI 注入不可被文件覆盖）。
- **生产 fail-closed**：`NODE_ENV=production` 时 `JWT_SECRET` 缺失、短于 32 字符或仍是示例值 →
  **拒绝启动**（`Server/src/config.ts` 中的 errors 分支）。
- 生成密钥：`node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"`。
- 日志脱敏：`req.headers.authorization|cookie`、`req.body.password|currentPassword|newPassword|refreshToken` → `[REDACTED]`。

### 5.7 传输与部署安全

| 项 | 说明 |
|---|---|
| HTTPS | 服务端自身只监听 HTTP；**对外必须置于 TLS 终止（Nginx/Caddy/云 LB）之后** ⚠️ 未内置 TLS |
| `TRUST_PROXY` | 默认 `false`。置于可信反代后才可开启，否则客户端可伪造 `X-Forwarded-For` 绕过按 IP 限流 |
| CORS | 默认关闭（Electron 直连不涉及 CORS）；配置 `CORS_ORIGINS` 才启用（浏览器客户端场景） |
| 监听地址 | 默认 `127.0.0.1`（仅本机）；对外需显式改 `HOST=0.0.0.0` 并配合防火墙 |
| 数据库凭据 | 通过 `DATABASE_URL` 注入；避免使用超级用户；建议专用库+最小权限角色 |

### 5.8 隐私边界

| 数据 | 是否上传 | 理由 |
|---|---|---|
| 邮箱、显示名、密码哈希 | 是（账户必需） | 登录与识别 |
| 用户设置 | 是 | 跨设备一致是核心诉求 |
| 统计事件（`kind`/`value`/`meta`） | 是（客户端决定内容） | 服务端不解析 `meta` 语义 |
| 记忆（`title`/`content`） | 是 | 重建诉求 |
| **任务元数据**（`clientSessionId` + `title` + 归档状态 + 本机时间戳） | **是**（**2026-10-03 校准 / S01-D03**） | 会话列表与归档态属"重装后要回来"的个人数据：存 `user_tasks`（§4.10、§3.2）。**只有元数据**——服务端不持有、也无法还原任何一条消息 |
| 会话消息正文 / Loop 轨迹 / 工具输出 / 本地事件流 | **否** | 体量大、含敏感上下文，且不属"重装重建"范围 |
| 审计记录 | 是（保留 IP/UA） | 安全追溯；注销账号时业务数据级联删除，审计保留但 `user_id` 置 NULL |

⚠️ 未实现：字段级加密（E2EE）、数据导出后的本地加密、审计保留期策略。

## 6. 同步语义（服务端权威）

### 6.1 权威源原则

```
读：登录/启动 ──▶ GET /v1/settings, /v1/memories ──▶ 覆盖本地缓存
写：本地变更   ──▶ PUT/PATCH/POST（上行）──▶ 服务端接受即为准
冲突：以服务端为准；设置用 revision 拒绝静默覆盖
```

选择"服务端权威"而非"双向增量"的原因：语义可预期、实现可验证，且**直接满足核心诉求**
（重装后数据回来）。双向增量的成本（版本向量/墓碑/合并策略）留待确有离线编辑需求时再引入。

### 6.2 设置的乐观并发

```
设备 A: GET /v1/settings            → revision=2
设备 B: PATCH {data, expectedRevision:2} → 200, revision=3
设备 A: PATCH {data, expectedRevision:2} → 409 REVISION_MISMATCH {currentRevision:3}
设备 A: GET（拿到 3）→ 合并本地改动 → PATCH {…, expectedRevision:3} → 200, revision=4
```

### 6.3 记忆的幂等对齐

- 上行必须携带端侧 `memory_id` 作为 `clientMemoryId`；服务端按
  `(user_id, client_memory_id)` 部分唯一索引 upsert。
- 结果：**重装后全量重传不会翻倍**，且同一条逻辑记忆在服务端只有一行；批量接口额外返回
  `created/updated` 便于客户端对账。
- 批量上传在同一事务内完成，避免"一半成功"的中间态。

### 6.4 删除的传播

默认**软删除**（`status='deleted'`）：墓碑保留，列表默认过滤。这样将来引入双向同步时，
"删除"也可以像其他变更一样传播；当前阶段客户端只需按列表结果清理本地。

### 6.5 离线与冲突

| 场景 | 当前行为 | 目标态 |
|---|---|---|
| 服务端不可达 | 客户端应缓存写入意图并退避重试 ⚠️ 客户端接入时实现 | 本地队列 + 自动重放 |
| 两端同时改设置 | `revision` 冲突 → 409，客户端拉取后再写 | 三路合并提示 |
| 两端同时改同一记忆 | 后写覆盖（`updatedAt` 较新者胜） | 字段级合并 / 冲突标记 |

## 7. 备份与恢复设计

### 7.1 备份包格式

```jsonc
{
  "format": "civitas.backup",     // 固定字面量（Zod literal 校验）
  "version": 1,                   // 服务端拒绝高于自身支持版本
  "exportedAt": "2026-10-02T10:29:10.000Z",
  "account": { "email": "…", "displayName": "…" },   // 仅供提示，恢复时以当前登录账号为准
  "settings": { "revision": 2, "data": { … },
                "updatedAt": "2026-10-02T10:20:00.000Z" } | null,   // = SettingsDto（含 updatedAt，见 settingsService.toSettingsDto()）
  "memories": [ { "id", "clientMemoryId", "title", "content", "category",
                  "assertion", "status", "sourceTraceIds", "sourceArbitrationIds",
                  "accessCount", "createdAt", "lastAccessedAt", "updatedAt" } ],
  "tasks": [ { "clientSessionId", "title",
               "createdAt", "updatedAt", "archivedAt" } ],  // 2026-10-03 校准（S01-D06）：**导出总是写入本字段**（可为空数组）；三个时间字段是 **epoch ms 数字**，`archivedAt=null` 即未归档
  "stats": { "events": [ { "kind", "value", "occurredAt", "clientEventId", "meta" } ] } | null,
  "truncated": { "stats": { "limit": 1000, "reason": "统计事件超过调用方设定的 statsLimit…" } }
                                   // 可选完整性标记：**字段缺省 = 导出完整**（SV-001）；当前只可能标 stats
}
```

要点：
- **自包含**：一个文件即可重建，不依赖外部存储。
- 账号字段**不作为身份判定**（防止把 A 的包恢复进 B 的账号时越权）。
- `includeStats` 默认关闭：统计体积可能较大，由调用方决定是否包含。`statsLimit`（可选，1..100000）为统计事件的**显式**上限：缺省即键集分页**全量**导出（无静默上限），传入则只导出前 N 条并在包内 `truncated.stats` 如实标注（SV-001）。
- **导出不设静默条数上限**（**2026-10-03 校准 / S01-D07**，本条原写"导出上限：记忆 10 000 条、事件 10 000 条……⚠️ 超限当前静默截断，目标态见 §12"，与同节上一条及附录 D 的 L6「已解决」自相矛盾）：记忆走 `repositories/memories.ts` 的 `listAllMemories()`、任务走 `repositories/tasks.ts` 的 `listAllTasks()`、统计走 `backupService.ts` 的 `exportStatEvents()`，**均为键集分页循环取全量**——分页大小（1 000）只影响每次查询的行数，不影响结果完整性；仅当调用方显式传 `statsLimit` 才可能截断，且包内 `truncated` 如实标注。
- `tasks` 与 `memories` 一样**无条件导出**（不受 `includeStats` 影响）：任务元数据是"重装后任务列表还在"的关键，体积仅标题 + 时间戳，默认可忽略。

### 7.2 两种恢复模式

| 模式 | 语义 | 适用 |
|---|---|---|
| `merge`（默认） | 按 `clientMemoryId` upsert 记忆；**任务元数据按 `clientSessionId` upsert（不清空既有其他任务）**；设置覆盖；统计按 `clientEventId` 去重追加；**不删除**既有数据 | 日常合并、多设备并行使用 |
| `replace` | 清空该用户 `settings`/`memories`/`usage_events`/`user_tasks` 后写入 | **重装重建**（镜像式恢复） |

实现要点（`Server/src/services/backupService.ts` 的 `restore()`）：
- 全流程在**单事务**内执行（`db.tx`），任一步失败整体回滚，不留半恢复状态。
- 恢复前后不修改账号本身（邮箱/密码/令牌不受影响）。
- `replace` 的删除**限定在 `user_id` 范围内**，不会影响其他用户（集成测试断言"恢复进 B 账号只在 B 名下"）。
- 重复执行 `replace` 结果幂等（集成测试断言：二次恢复记忆数不翻倍）。
- **任务元数据（2026-10-03 校准 / S01-D06）**：`replace` 模式先 `DELETE FROM user_tasks WHERE user_id = $1`
  再按包内 `tasks` 重建，但**仅当包内 `tasks` 非空时才执行删除**——因此导入**不含 `tasks` 字段的旧备份包**
  不会误删该用户已有的任务元数据（向后兼容）；恢复报告始终带 `tasks:{created,updated,total}`（旧包时为 `{0,0,0}`）。
  断言见 `test/integration/tasks.spec.ts` 的"★ 备份包含任务元数据；replace 恢复后归档状态完整回来"。

### 7.3 失败与回滚

| 失败点 | 行为 |
|---|---|
| 包格式/版本不合法 | 400 `VALIDATION_ERROR`（Zod 校验，含字段路径），不触碰数据库 |
| 记忆条数超上限 | 413 `PAYLOAD_TOO_LARGE` |
| 事务中途失败 | 整体回滚（`ROLLBACK`），数据保持恢复前状态 |
| 数据库不可用 | 500 `INTERNAL`（细节入日志），不返回半成品结果 |

### 7.4 "卸载重装重建"完整序列

```
【用户首次使用】                          【卸载 / 换机 / 重装】
  注册/登录                                 重新安装客户端
      │                                          │
      ├─ 设置/记忆/统计 上行 ──▶ 服务端 PG        ├─ 登录（账号在服务端，密码仍有效）
      │                                          │      │
      └─（可选）导出备份包保存到本地/U盘          │      ├─ 拉取：GET settings / memories / stats
                                                 │      │        └──▶ 客户端恢复完成（无需备份包）
                 │                               │
                 └───────── 若服务端数据也丢失 ──┴─▶ 导入备份包：POST /v1/restore
                                                          mode=replace ──▶ 全量重建
```

两条恢复路径互为兜底：**账号仍在服务端** → 登录即恢复；**服务端数据也丢** → 备份包重建。

### 7.5 容量与限流影响

- **导出不受条数上限约束**（**2026-10-03 校准 / S01-D07**，本条原写"单用户记忆导出上限 10 000 条"）：
  记忆 / 任务元数据 / 统计均为键集分页**全量**导出（见 §7.1）。约束只在**写入侧**的批量上限：
  记忆批量 1 000 条（`MAX_MEMORIES_PER_BULK`）、任务批量 500 条（`taskBulkSchema`）、
  统计批量 500 条（`MAX_STATS_EVENTS_PER_BATCH`，`statsIngestSchema` 另有 5 000 条硬顶，见 §4.5）。
- 备份包体积受请求体上限（默认 1 MiB）约束——**恢复大包需提高 `BODY_LIMIT_BYTES`**
  （例如 10 万条记忆建议 16 MiB），这是部署时必须注意的联动项。

## 8. 个人数据统计设计

### 8.1 事件模型

| 字段 | 语义 | 谁定义 |
|---|---|---|
| `kind` | 事件类型（`chat.turn` / `tool.call` / `app.launch` …） | 客户端 |
| `value` | 数值（token 数、耗时 ms、计数…） | 客户端 |
| `occurredAt` | **发生时间**（非入库时间） | 客户端 |
| `meta` | 自定义负载（服务端不解析） | 客户端 |
| `clientEventId` | 幂等键（可空） | 客户端 |

### 8.2 幂等与批量

- 单次上限 `MAX_STATS_EVENTS_PER_BATCH`（默认 500），超限 413。
- 幂等由部分唯一索引承担：`ON CONFLICT (user_id, client_event_id) WHERE client_event_id IS NOT NULL DO NOTHING`；
  返回 `{accepted, submitted}` 让客户端知道实际入库条数。
- 未提供 `clientEventId` 时允许重复写入（适合"每次启动都记一条"这类无需幂等的场景）。

### 8.3 聚合与扩展

当前为**实时聚合**（`COUNT/SUM` + `GROUP BY`），索引 `(user_id, occurred_at DESC)`、`(user_id, kind)`；
`overview` 额外返回终身统计（`MIN/MAX(occurred_at)`、去重活跃天数）。

⚠️ 目标态：当单用户事件量达到百万级时引入 `usage_daily` 物化日汇总表（按 `(user_id, day, kind)`），
接口保持不变，只替换 `statsService` 的读取实现。

### 8.4 时区与分日边界

- 存储一律 UTC；**分桶**由 `STATS_TIMEZONE` 决定（默认 `UTC`，国内部署建议 `Asia/Shanghai`）。
- 边界语义：`occurred_at AT TIME ZONE tz` 得到本地时间再 `date_trunc('day')`；
  查询区间 `[from, to)` 为 UTC。
- 变更时区会使历史日曲线重新分桶（同一份原始事件），不建议频繁调整。

### 8.5 隐私

`meta` 内容完全由客户端掌控；服务端不解析、不用于分析，仅在 `includeStats` 时随包导出。
若客户端不上报敏感内容，服务端无从获知。

- 位置：`Server/migrations/NNN_name.sql`，按文件名升序执行；**当前 001–005**（**2026-10-03 校准 / S01-D13**，
  本行原写"当前 `001_init.sql`"）：

- 单个迁移在**独立事务**中执行；失败回滚且不写记录（不留半应用状态）。
- **漂移检测**：已应用迁移的内容被改动 → 迁移/启动时直接报错（要求新增迁移文件而非改历史）。

### 9.4 备份策略（两层）

| 层次 | 手段 | 责任人 | 恢复粒度 |
|---|---|---|---|
| 数据库层 | `pg_dump` 全库 + 定期快照 | 运维 | 整库（含所有用户） |
| 用户层 | `GET /v1/backup/download` | 用户自助 | 单用户数据（设置/记忆/统计） |

两者互补：用户层满足"我的数据我带走"，数据库层满足"服务器崩了也能回来"。

### 9.5 监控与健康检查

- `/healthz`（进程存活，不限流）、`/readyz`（数据库连通，异常返回 503 + `UNAVAILABLE` 统一错误体）——供容器编排/负载均衡探活。
- 日志：Fastify 结构化 JSON（pino），含 `reqId`；敏感字段脱敏。
- 审计表可作安全观测数据源（登录失败激增、`token_reuse` 出现即需告警）。
- 定期维护：进程启动即清理一次历史刷新令牌，此后每 6 小时执行 `purgeInactive`（删除已吊销/已过期且签发超 60 天的记录，SV-004）；失败仅告警、不阻断服务。
- ⚠️ 未实现：Prometheus 指标端点、trace 上报、告警规则模板。

### 9.6 多实例与扩展

- 应用**无状态**（会话/数据都在 PG），可多实例水平扩展，前置负载均衡即可。
- **限流计数存储随 `RATE_LIMIT_STORE` 决定多实例准确性**（**2026-10-03 校准 / S01-D09**，本条原写
  "⚠️ 限流为进程内计数 → 多实例阈值 = N × 配置值"，与附录 D 的 L1「已解决（SV-003）」矛盾）：
  - `postgres`（**生产默认**）：计数在 `rate_limit_buckets` 表（原子 UPSERT），多实例**共享**、阈值与配置一致；
    窗口为**固定窗口**（跨边界可能多放行一小段）。
  - `memory`（dev/test 默认）：计数在进程内 `Map`，多实例**各算一份** → 实际阈值 = `N ×` 配置值（防护被稀释）；
    窗口为滑动窗口。
  接口 `RateLimiter.consume(key, limitPerMin, now?)` 保持不变；PG 抖动时**回退进程内计数**兜底
  （宁可短时放宽也不误伤正常请求）。若将来改用 Redis，实现同一接口替换即可。
- 数据库侧扩展顺序建议：连接池调优 → 只读副本（统计查询）→ 物化汇总表。

### 9.7 容量与性能预算

| 维度 | 估算 | 依据 |
|---|---|---|
| 单用户设置 | ≤256 KiB | `MAX_SETTINGS_BYTES` |
| 单用户记忆 | 1 万条内舒适（10 万条需提高批量/请求体上限，并考虑分词检索） | 索引 + 写入侧批量/请求体上限（**导出为全量键集分页，已无静默条数上限**，见 §7.1、§7.5；2026-10-03 校准 / S01-D07，本行原写"索引与导出上限"） |

## 11. 失败模式与处置

| 失败 | 现象 | 服务端行为 | 客户端/运维应做 |
|---|---|---|---|
| 数据库不可用 | 所有业务接口 500；`/readyz` 503 | 启动时拒绝启动；运行期返回 `INTERNAL`（细节入日志） | 探活摘流量；恢复数据库后重启 |
| 迁移失败/漂移 | 启动或 `migrate` 报错退出 | 事务回滚，不写 `schema_migrations` | 修复迁移（新增文件），勿改历史 |
| 配置非法 | 进程立即退出并打印 errors | fail-closed | 按提示修 `.env`（尤其 `JWT_SECRET`/`DATABASE_URL`） |
| 刷新令牌泄漏 | 攻击者与用户先后刷新 | 检测到重用 → 吊销整族 → 双方都需重新登录 | 客户端收到 `TOKEN_REUSED` 应清空令牌并提示重新登录 |
| 访问令牌泄漏 | 改密/登出/吊销会话后，泄漏令牌**下一请求即失效**（SV-002） | 守卫按 `sid` 回查 `refresh_tokens`（PK 查询） | 仍建议缩短 TTL；敏感操作二次校验（目标态） |
| 触发限流 | 429 + `Retry-After` | 按 `RATE_LIMIT_STORE` 的窗口策略拒绝（`memory` = 滑动窗口 / `postgres` = 固定窗口，见 §5.4、§9.6） | 依据 `Retry-After` 退避；批量接口分批 |
| 请求体/批量超限 | 413 | 直接拒绝 | 调大上限或分批（恢复大包见 §7.5） |
| 备份包版本过高 | 400 | 拒绝导入 | 升级服务端 |
| 迁移到新 PG 大版本 | — | — | 先 `pg_dump` 再升级，回滚用快照（§9.3 ⚠️ 无自动 down） |
