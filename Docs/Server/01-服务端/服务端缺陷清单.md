## 详细条目

### SV-001 备份导出静默截断（P1，✅ 已修复（2026-10-03 复核））

- **现象**：记忆 >10 000 条、或统计事件 >10 000 条时，`GET /v1/backup` 只导出前 10 000 条，
  **备份包内没有任何"被截断"的标记**；用户/客户端据此认为备份完整，重装后用 `mode=replace` 恢复会**丢数据**。
- **根因**：导出路径写死上限且无溢出检测（2026-10-03 校准：以下行号引用改为符号定位，描述**修复前**形态）——
  - `Server/src/repositories/memories.ts` 的 `listAllMemories()`（修复前）：`limit = 10_000` 缺省 + 单条 `LIMIT $2` 查询
  - `Server/src/services/backupService.ts` 的统计导出（修复前内联 `ORDER BY occurred_at ASC LIMIT $2`，即现 `exportStatEvents()` 前身），`options.statsLimit ?? 10_000`
  - `BackupBundle` 结构（`Server/src/services/backupService.ts`）当时**无 `truncated`/`complete` 之类字段**
- **影响面**：重度用户（长期使用、记忆累计上万条）的备份**静默不完整**；`mode=replace` 恢复是破坏性的，
  会造成"恢复后比备份前更少"的错觉（实际是备份时就少了）。
- **建议修法**（任一，推荐 ①+②）：
  1. 导出改为**分页/流式**（按 `created_at,id` 键集分页循环），彻底消除上限；
  2. 无法分页时在包内显式标注（`"truncated": {"memories": true, "limit": 10000}`）并在
     `GET /v1/backup` 响应头或 `data` 内给出告警，绝不静默；
  3. 或超限直接返回 `413 PAYLOAD_TOO_LARGE` + 引导用户分批导出。
- **复现**：向单用户写入 >10 000 条记忆（或把上限临时调小，如 `listAllMemories(db, uid, 2)` 配合 3 条数据），
  导出后比对条数 → 只见 10 000（或 2）条且无任何提示。
- **验收标准**：备份包与导出接口必须能表达"是否完整"；恢复后条数与备份时一致（或明确告知差异）。
- **注意**：此项在 [设计文档附录 D](服务端设计文档.md) 记为 **L6**，并明确标注为"实现缺陷"而非设计取舍。
- **修复（2026-10-03）**：按建议 ①+② 双管齐下——记忆与统计导出均改为**键集分页循环全量导出**（无 10 000 上限）；`BackupBundle` 新增 `truncated` 字段：仅当调用方**显式**传入 `statsLimit` 且超限时才标注（`{stats: {limit, reason}}`），缺省即完整、绝不静默。
- **验证（2026-10-03）**：`Server/test/integration/backup.spec.ts` 新增 2 项（★ SV-001：记忆导出键集分页取全量不受单页上限截断；统计默认全量导出、显式 statsLimit 超限时包内 truncated 如实标注）；服务端 105/105 全绿（当日快照）。
- **2026-10-03 复核（代码实态确认）**：`memories.ts` `listAllMemories()` 已为键集 `for(;;)` 循环（`EXPORT_PAGE_SIZE = 1_000` 仅影响每次行数）；`backupService.ts` `exportStatEvents()` 未指定 limit 时全量、指定时多取 1 条探测溢出并回传 `truncated`；`BackupBundle.truncated` 与 `tasks` 字段在位。修复**属实**。

### SV-002 改密/登出后旧访问令牌仍可用（P2，✅ 已修复（2026-10-03 复核））

- **现象**：用户 A 在设备 1 改密或"登出全部设备"后，设备 2 上**已经签发**的访问令牌在有效期内
  （默认 `ACCESS_TOKEN_TTL_SEC=900`，即 15 分钟）**仍可正常调用所有业务接口**（读设置、读写记忆、导出备份）。
  用户预期是"改密即让其他设备立刻失效"。
- **根因**：访问令牌是无状态 JWT，业务接口只验签不查库（2026-10-03 校准：行号改符号定位，描述**修复前**形态）——
  - `Server/src/http/authGuard.ts` 的 `createAuthGuard()`（修复前）：仅 `verifyAccessToken(cfg.auth, token)`，**没有任何数据库查询**
  - `Server/src/services/authService.ts` 的 `changePassword()`（修复前）：只 `revokeAllForUser(..., 'password_changed')` 吊销**刷新令牌**家族，
    访问令牌不受影响（登出同理，`logout()`）
- **影响面**：安全语义缺口（被盗设备在 TTL 窗口内仍可操作）；`users.password_changed_at` 字段已预留，可用于收敛。
- **建议修法**（按成本递增）：
  1. 缩短 `ACCESS_TOKEN_TTL_SEC`（如 300s），把窗口压到可接受范围（**推荐先做**）；
  2. `authGuard` 增加轻量校验：查一次会话状态（`refresh_tokens.revoked_at IS NULL AND expires_at > now()`），
     或在 JWT 内带 `iat`，与 `users.password_changed_at` 比对，早于则拒绝（需 `users` 查询，可加内存缓存 TTL）；
  3. 引入令牌黑名单（Redis/内存 LRU），登出/改密时登记 `sid`。
- **复现**：注册 → 记录 `accessToken` → `POST /v1/auth/change-password` → 用旧 `accessToken` 调 `GET /v1/settings` → 仍 200。
- **验收标准**：改密/登出后，旧访问令牌在 ≤1 个请求周期内失效（或至少在文档与 UI 中如实告知 TTL 窗口）。
- **修复（2026-10-03）**：按建议 ② 实施——`authGuard` 验签后按 JWT 的 `sid` 声明**回查会话行**（`SELECT revoked_at, expires_at FROM refresh_tokens WHERE id = $1`）；已吊销/不存在/已过期 → 401 `UNAUTHENTICATED`（"会话已失效，请重新登录"）。改密（`revokeAllForUser password_changed`）、登出（单设备/全部设备）、单会话吊销后，旧访问令牌 ≤1 个请求周期失效；6 个业务路由全部接线 `createAuthGuard(ctx.cfg, ctx.db)`。
- **验证（2026-10-03）**：`Server/test/integration/auth.spec.ts` 新增 2 项（改密后旧令牌立即 401 + fresh 令牌 200；登出后本设备立即 401、其他设备 200、logout allDevices 后全部 401）；auth.spec.ts 14/14、服务端 105/105 全绿（当日快照）。
- **2026-10-03 复核（代码实态确认）**：`authGuard.ts` `createAuthGuard()` 现已按 `claims.sid` 执行 `SELECT revoked_at, expires_at FROM refresh_tokens WHERE id = $1` 回查，会话缺失/已吊销/已过期 → `unauthenticated('会话已失效，请重新登录')`；auth.spec.ts 含 ★ SV-002 两项。修复**属实**。

### SV-003 限流为进程内计数（P2，✅ 已修复（2026-10-03 复核））

- **现象 / 风险**：单实例自托管完全有效；**多实例部署时**每个实例各自计数，实际阈值 ≈ `配置值 × 实例数`，
  使针对登录接口的暴力破解防护、以及写操作防滥用被等比弱化。
- **根因**：`Server/src/http/rateLimit.ts` 使用进程内 `Map`，无共享存储。
- **修复（2026-10-03）**：不引入 Redis，改用**本服务已有的 PostgreSQL** 做共享计数：
  - 新增迁移 `Server/migrations/004_rate_limit_buckets.sql`（`rate_limit_buckets(bucket_key PK, window_start, used)`）；
  - `rateLimit.ts` 新增 `createPostgresRateLimiter()`：单条**原子 UPSERT** 实现固定窗口计数（并发安全、多实例一致），
    并保留进程内实现为默认；配置 `RATE_LIMIT_STORE=memory|postgres`（**生产默认 postgres**，dev/test 默认 memory）；
  - 接口统一为**异步**（`consume(): Promise<RateLimitDecision>`），调用点（`app.ts` 两处 hook）`await`；
  - **可用性兜底**：PG 查询失败时回退到进程内限流（仍然限流，只是退回单实例口径）+ 错误日志，
    避免"存储抖动导致全员被拒"或"完全不限流"；
  - 过期桶由 `unref` 定时器清理（默认 10 分钟，保留 3 个窗口）。
- **验证（2026-10-03）**：
  - `Server/test/integration/rateLimitStore.spec.ts`（6 项）：**两个 limiter 实例共享计数**、
    超限拒绝与 `retryAfterSec`、窗口滚动重置、`peek` 共享、存储故障回退仍限流、
    应用级 `RATE_LIMIT_STORE=postgres` 下 429 由共享计数决定且写入桶表；
  - **双实例实机对比**（同库、`RATE_LIMIT_AUTH_PER_MIN=5`）：
    `memory` 模式 → A 第 6 次 429，但 **B 第 1 次仍 401（未被限流 → 阈值实际 ×2）**；
    `postgres` 模式 → A 第 6 次 429，**B 第 1 次直接 429（共享生效）**，桶表 `auth:127.0.0.1 → used=7`。
- **说明**：语义为**固定窗口**（与内存实现的滑动窗口略有差异，已在代码注释与文档标注）；
  若将来上 Redis，实现同一 `RateLimiter` 接口替换即可。
- **2026-10-03 复核（代码实态确认）**：`rateLimit.ts` `createPostgresRateLimiter()`（原子 UPSERT 固定窗口 + 故障回退进程内）与 `app.ts` 中 `cfg.rateLimitStore === 'postgres' ? createPostgresRateLimiter({ db }) : createRateLimiter()` 接线在位；`config.ts` 缺省组装 `rateLimitStore: e.RATE_LIMIT_STORE ?? (production ? 'postgres' : 'memory')`。修复**属实**（迁移 004 与 rateLimitStore.spec.ts 6 项亦在位）。

### SV-004 过期令牌清理未接线（P3，✅ 已修复（2026-10-03 复核））

- **现象**：`refresh_tokens` 表只增不减（每次登录/刷新新增一行），长期运行后表持续膨胀；
  过期与已吊销记录永久保留。
- **根因（修复前）**：`Server/src/repositories/refreshTokens.ts` 的 `purgeInactive(db, olderThanDays = 60)` 仅有定义、
  **全仓无任何调用者**（2026-10-03 校准：原行号引用改符号定位；现状已有调用者，见下）。
- **影响面**：数据库容量与索引效率（当前量级无感；多用户长期运行后会显现）。
- **建议修法**：启动期挂定时任务（如每 6 小时）或在 `index.ts` 注册 `setInterval` + `unref()`，
  调用 `purgeInactive(db, 60)`；并加一条集成测试断言"过期超 60 天的记录被清理、未过期的保留"。
- **注意**：清理**不得**影响审计追溯——审计信息在 `audit_log`，与本表解耦。
- **修复（2026-10-03）**：`Server/src/index.ts` 接线——启动即扫一次 + `setInterval` 每 6 小时执行 `purgeInactive(db, 60)`；定时器 `unref()`（不阻止进程退出），shutdown 时 `clearInterval`；失败仅 warn 不阻断服务。

  3. **无尝试次数限制**：`verification_codes` 表无 `attempts` 字段，`findValidCode()` 只按"最新 + 未用 + 未过期"取一条，

  2. 用 `crypto.randomInt(0, 1_000_000)` 生成；
  3. 加 `attempts int default 0` + 超过 5 次即 `used_at = now()`（作废）并审计；

  5. 明文比较逻辑统一走常量时间函数。

  `verifyCodeHash()` 走 `timingSafeEqual`；`generateCode()` 改用 `crypto.randomInt`；
  `attempts` 列 + `registerFailedAttempt()` 达 `CODE_MAX_ATTEMPTS`（默认 5）即作废；

  （如 `ALLOW_DEV_CODE=true` 且 `NODE_ENV !== 'production'` 双条件），启动时若为生产且未配置邮件通道则**拒绝启动**（fail-closed）。
- **修复（2026-10-02）**：按建议落地——新增 `Server/src/services/mailTransport.ts`（`webhook` 投递通道 + `console` 降级通道，控制台仅开发）；
  `config.ts` 校验：生产未配置 `MAIL_WEBHOOK_URL` → **拒绝启动**（fail-closed）；`ALLOW_DEV_CODE=true` 且生产 → 拒绝启动，
  且配置组装层再兜一层 `allowDevCode: ALLOW_DEV_CODE && NODE_ENV !== 'production'`；`authService.sendVerificationCode()` 仅在 `cfg.auth.allowDevCode` 时回传 `devCode`。

  **注**：投递通道已落地，但"`reset_password` 用途码的消费端点"（邮箱验证/找回密码功能）**仍未实现**——见下方对应关系表 L4【需人工裁定】。

### SV-014 绑定指纹取自易变硬件信息（P0，✅ 已修复（2026-10-03 复核），与 FE-033 合并处理）

- **现象（修复前）**：`Src/Infra/Security/deviceFingerprint.ts` 的 `getDeviceFingerprint()` 以 `MAC 列表 + hostname + 磁盘序列号` 生成 SHA-256 作为设备标识，
  服务端据此做**硬绑定**（`users.bound_device_id`）：指纹变化即 `403`，且无自助解绑。（2026-10-03 校准：行号引用改符号定位）
- **易变性**：切换 Wi-Fi/有线、VPN/虚拟网卡增删、主机名修改、换盘/换主板、Windows 11 无 `wmic`（序列号为空）都会改变指纹。
- **建议**：改为"安装期生成的随机设备凭据"（存 `safeStorage`，服务端按设备凭据 + 会话识别），
  并把"新设备登录"变成**需确认的事件**而非硬拒绝；同时提供设备管理与自助解绑端点。
- **修复（2026-10-02）**：按建议落地（服务端侧）——迁移 `003_auth_hardening.sql` 为 `user_devices` 增
  `credential_hash`（服务端只存安装期设备凭据的 sha256，见 `users.ts` `registerDevice()`）、`device_kind`（install/legacy/manual）、`last_seen_at`；
  `DEVICE_BINDING_MODE` 默认 **warn**（不再硬拒）；新增自助设备管理端点 `GET /v1/me/devices` 与 `DELETE /v1/me/devices/:deviceId`
  （`Server/src/routes/auth.ts`，服务层 `authService.listDevices()` / `revokeDevice()`，解绑记审计 `auth.revoke_device`）；
  `users.bound_device_id` 降级为仅展示用。客户端侧（safeStorage 凭据生成）见 FE-033。
- **2026-10-03 复核（代码实态确认）**：上述列、端点与服务层函数均在位。修复**属实**。
