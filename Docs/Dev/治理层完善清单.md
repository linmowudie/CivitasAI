## 0. 规则（红线）

| 层级 | 角色 | 职责 | 可否执行治理动作 |
|------|------|------|-----------------|
| **所有者** | `user` | 最终权威 | ✅ 可（等同治理层） |
| **L0** | `auditor` / `regulatory_authority`(=`regulator`) / `arbitrator` | **裁决、审计、监管、立法、冻结** | ✅ **仅此层** |
| **L1** | `prime_director` / `partner` | 编排、拆解、招募、汇总 | ❌ 只做事（可在 L2 自治域内参与决策，见下） |
| **L2** | `worker` / `reviewer` / `assembly_node` | 执行、产出、初步评审 | ❌ 只做事 |

**层级相对规则（审批已验证）**：
- **L2 请求**（L2 是 L1 自治域）→ 用户 / L1 / L0 **任意两方**决策；
- **L1 自身请求** → 用户 + L0（L1 不得自审）；
- **治理动作（L0 域）** → 仅 L0 / 用户；
- **系统角色** → 只能自动**拒绝**，永不自动通过；
- **请求方角色永不进入决策池**（配置也改不掉）。

### 0.2 监管理念（借鉴 `MongoTerminalAgent v2.0` 的 supervisor 系统）

来源：`F:\ProjectCode\MongoTerminalAgent\v2.0`（`Core/Middlewares/__init__.py`、`LogicContinuity.py` 等）。

| 理念 | 该项目的做法 | 本项目对应落地 |
|------|-------------|---------------|
| 监管 = **干预**，不是阻断 | 监管中间件注入"纠偏消息"/改写结果，不硬停主循环 | 监管动作区分**自动干预**与**裁量执法**；自动干预不设角色门 |
| **监管失效绝不阻断主流程** | 监管层所有生命周期方法 try-except 包裹 | 监管判据/记录失败不影响主循环；但**执法被拒必须显式返回拒绝**（不静默） |
| **全局开关 + 逐项开关** | `supervisor.enabled` × `middleware_enabled` | 对应 `Configs/supervision.json`（已有 `approvalTimeoutSec` 等） |
| **阈值化可配置** | `stagnation_threshold`、micro/heavy compact ratio | 规则与阈值走配置，不硬编码布尔权限 |
| **分层各管一类行为** | loop_detection / logic_continuity / path_error / read_dedup / tool_intent / reflection | 审计（副作用）/ 监管（行为）/ 仲裁（冲突）/ 内容审查（产出）四者分离 |
| **避免误伤** | 压缩感知、纠偏注入去重 | 复核类判定须带依据（规则 ID / 事件），不靠模糊启发式 |

**关键推论（本项目采纳）**：
- **判据查询**（`checkViolation` / `validateBehavior`）＝ 监管的"检测"面，**可自动运行、不限角色**；
- **裁量执法**（紧急干预 / 僵局升级 / 终局裁决 / 规则增删）＝ 监管的"动作"面，**必须 L0**；
- 二者不可混淆：把检测也锁到 L0 会让监管失去自动化能力，把执法放开则治理失效。
### 0.1 职能边界（用户 2026-10-04 裁定，**三者不可混淆**）

| 职能 | 审什么 | 归属层级 | 是否治理动作 | 实现归属 |
|------|--------|---------|-------------|---------|
| **reviewer 内容审查** | **生成内容**（产出质量/正确性） | L2（L1 编排域内） | ❌ **不是治理** | `Services/ReviewerAgent`（**不加 L0 门**） |
| **audit 副作用审计** | **副作用行为**（写了什么/改了什么/花了多少） | L0 `auditor` | ✅ 是 | `Services/Audit`（G-01 已实现） |
| **regulation 行为监管** | **行为正确性**（是否守规范、违规判定与执法） | L0 `regulatory_authority` | ✅ 是 | `Services/Regulation`（G-03/04/05） |
| **arbitration 冲突裁决** | **冲突事实与责任** | L0 `arbitrator` | ✅ 是 | `Services/Arbitration`（G-02 已实现） |

> 已核实：`Services/ReviewerAgent` 中**不存在** `freeze / penalt* / behaviorCode / violation / audit / budget / sideEffect` 等治理动作引用
> —— reviewer 确实只做内容审查，未越界；因此 G-06 裁定为"非治理，不加 L0 门"。

## 2. 实现约定（统一模式）

1. **入口加显式 actor**：`fn(input, actorRole: string)`；内部同域调用传自身治理角色（如审计局传 `'auditor'`）。
2. **守卫调用**：`const g = requireGovernanceRole(actorRole, '<动作名>'); if (!g.ok) return err(g.error);`
3. **失败语义**：一律 `fail-closed`（拒绝并留日志），不做"未提供则不校验"的宽松降级。
4. **测试**：每个条目至少 2 个用例——非治理角色被拒 + 治理角色通过。
5. **不破坏既有测试**：若既有测试以非治理角色调用，**先判断是测试写错还是产品规则**（写错则改测试，产品规则则改代码），不得为过测试而放宽红线。
