## 3. 为什么 `systemPromptCache` 可以共享（不是"可变"就该赶走）

判据三条**全中**才可共享：

1. **值由输入唯一决定**（key = `toolNames` + `rolePrompt`）⇒ 不同实例命中同一 key 必得同一字符串
2. **有界**（`SYSTEM_PROMPT_CACHE_MAX = 64`）⇒ 不会无界增长
3. **有显式 reset**（`resetSystemPromptCache()`）⇒ 测试可控

**反例（若共享会出错）**：缓存值依赖"当前实例的会话状态" ⇒ 两实例会互相读到对方的内容。本缓存**不满足**这一点，故安全。

## 4. 核心结论（**修正了我在 [15](15-ReActLoop原语.md) §7 的悲观假设**）

我在 15 §7 写的是：

> "**逐行盘点** `runIteration.ts` 的模块级可变状态……我**没有**逐行审计过这个文件，**不能声称它现在就是可重入的**。"

**盘点的实际结果**：

```
✅ runIteration.ts 的可变状态 = 0（唯一容器是"值由输入决定 + 有界 + 有 reset"的纯缓存）
❗ 真正的地雷不在十步循环，而在 contextCompression.ts 的 _lowGain / _metrics
```

**⇒ S2 的范围应当收窄**：不是"把十步循环改成可重入"（它本来就接近可重入，
因为 `loopState` / `control` / `IterationContext` 都是**显式参数**），而是：

| # | S2 真正要做的事 |
|---|---|
| 1 | **把 `contextCompression` 的 `_lowGain` / `_metrics` 从模块全局移出**（改为实例/参数持有） |
| 2 | 确认 `config` / `deps` 的注入语义**显式化**（谁是全局、谁按实例） |
| 3 | 保持 `middlewares` / `systemPromptCache` 为**共享**（并在文档里写明理由，避免后人误改） |

## 5. 为什么 `_lowGain` / `_metrics` 是真 hazard（不是"看着像"）

| 状态 | 语义 | 嵌套/并发时的后果 |
|---|---|---|
| `_lowGain` | 连续低增益压缩的**计数**（达阈值换策略） | **内层循环的压缩会推进外层的计数器** ⇒ 外层被误判"策略失效"而切换 |
| `_metrics` | 压缩计量**累加器** | 两层的计量混在一起 ⇒ **成本归因错**（正是 §17 归属要求"计量必须可归因"） |

而且 `resetContextCompression()` 是**唯一的重置手段**（测试用），
说明这两个量**没有"每次运行一份"的概念** —— 这正是必须修的。

## 6. 验收方式（S2 的负向用例）

| # | 反例 | 期望 |
|---|---|---|
| 1 | 两层循环各自压缩，内层的低增益计数**不应**推进外层 | 不出现（否则外层误换策略） |
| 2 | 两层循环的压缩计量应**分别归因**，不混合 | 不出现 |
| 3 | 两个并行实例的 `systemPromptCache` 命中**同一 key** | **允许**（值由输入决定；这是设计） |
| 4 | 两实例共享 `middlewares` 后，一实例注册的插件对另一实例可见 | **允许**（目录类 by design）→ 但**归属过滤**（P0-2）必须按 `loopId` 生效 |

**第 3、4 条特意写成"允许"** —— 盘点纪律不只是"找出要改的"，
也要**把"本来就该共享的"写死**，否则后人会把目录类也一并实例化，反而破坏全局注册语义。
