# 29 · 融合方案：L1 编排内核优先（Kernel-First Fusion）

> **状态**：2026-10-17 立项。设计依据 [00-索引](00-索引.md) · [01-双层循环总览](01-双层循环总览.md) · [15-ReActLoop原语](15-ReActLoop原语.md) · [25-实现顺序与最小落地切分](25-实现顺序与最小落地切分.md) §7 · [28-设计实现覆盖清点](28-设计实现覆盖清点.md) §6。
> **一句话**：内核（`Core/Orchestration` + `Core/Patterns` + `Core/Assembly` + `Core/Supervision` + `Core/Durable` + `Core/Lifecycle` + `Core/Context` + `Core/Ledger`）是**编排所有者**；legacy `Core/Loop/runIteration` 是**内层十步执行器**，被内核包住而不是被替换。

---

## 0. 为什么"融合"而不是"重写"

L1 设计从第一天起就是"内核包住既有十步循环"：

- `Core/Loop/reactLoop.ts`（`ReActLoop` 原语）**不重写十步**，默认直接调用真实 `runIteration`（`createReActLoop` → `deps.runIteration ?? realRunIteration`）；
- `Core/Orchestration/reactCore.ts`（内核内层组件）构造 `LoopState` + `IterationContext`，再经 `ReActLoop.runOnce` 落到 `runIteration`；
- [01-双层循环总览](01-双层循环总览.md)：「外层决定跑哪个组件，内层负责把它跑完；`I6 → O1` 是内层回到外层的唯一出口」。

因此融合不是二选一，而是**把所有者从 legacy 移到内核**，legacy 保留为叶子执行器。这也解释了为什么 `runIteration` 上调过的东西（trace 埋点、错误传播、工具门顺序）不必推倒：它们是**内层执行器的正确行为**。

## 1. 所有权矩阵（融合后唯一事实源）

| 能力 | 融合后所有者 | legacy 角色 | 备注 |
|---|---|---|---|
| 任务分解 / 选下一个执行件 | `OuterLoop.selectExecutable` | — | 选件策略由外部注入 |
| 组装（增删节点/校验/落盘/审计） | `Assembly` + `Orchestration/assemblyPorts` | — | 落盘/撤销/审计三端口必须实现 |
| 收敛判定（域静默 + goal + 子代静默） | `OuterLoop` + `Goal` | — | 先于选件判定 |
| L1 域账本 / 下级账本 | `Core/Ledger` + **LedgerHub** | — | 分裂/合并/外层/监管共用同一 registry |
| 上下文装配（可见面/分区边界） | `ContextAssembler` | 内层仍用既有分区装配 | 双写期：外层可见面来自内核 |
| 生命周期 / 监管指令 | `LifecycleController` + `componentSnapshot` | — | 每组件一份控制器 |
| 持久化（组件/对话） | `Core/Durable` checkpointRouter | 轮次级 `iterationCheckpoint` 保留 | 双写期后收敛（P3） |
| 十步 ReAct 执行 | **legacy `runIteration`** | 唯一实现 | 由 `ReActLoop` 原语包裹 |
| 工具面：组装器 | `OrchestratorCompose`/`OrchestratorSelect` + `orchestration` 端口 | — | 当前 `NOT_ENABLED`，P1 接线 |
| 工具面：分裂/合并 | `AgentSplit`/`AgentMerge` + `splitMergeFor` | — | 已接线，P0 复用 LedgerHub |
| 观测 | 外层 `emit` + 内层 span | 内层 span 保留 | 两层各带自己的 scope |

## 2. 四个融合 seam（都要有唯一实现）

1. **InnerExecutor**：`ReActLoop`（已有）。内核只依赖 `ReActLoop` 接口；默认实现 = `createReActLoop` → legacy `runIteration`。禁止在编排组件里直接调 `executeLoop`/`iterate`。
2. **L1ExecutionEntry**：`runL1Dialogue(agentId, task, opts)`。L1 角色（prime_director/partner）的任务走**外层循环**；worker 的指派任务仍走 `executeAssignedTask`（纯内层）。两者最终都落到 `runIteration`。
3. **LedgerHub**：进程内唯一 `L1HostRegistry`。外层循环、分裂/合并、监管快照从同一个 hub 取账本；禁止各自 `createL1HostRegistry()`。
4. **OrchestrationPort**：`createOrchestrationToolPort({registry,validator,assembler,current,adopt})` 注入 `toolServicePorts.orchestration`，让 `OrchestratorCompose`/`OrchestratorSelect` 从 `NOT_ENABLED` 变为真实可用。

## 4. 我 10-17 改动的归位（避免"为了实验改产品"的混淆）

| 改动 | 归位判断 |
|---|---|
| `runIteration` 的 trace span（runInTrace/runInSpan） | 保留：内层执行器的观测职责（融合后仍在内层） |
| 错误传播 / 假成功拦截 / 分区预算 / 死锁检查 | 保留：内层十步的正确性，属叶子执行器 |
| `splitSemantics`（13 项语义） | P1/P2 迁入 `Core/Orchestration`（拓扑语义归编排域）；迁移时同步基准探针路径 |
| `splitAgent` + `splitMergeComposition` | 保留：P0 改从 LedgerHub 取账本；Agent 本体在 `splitAgent` |
| `main.ts` 自动恢复续跑 | 保留（与内核持久化不冲突；P3 统一为 `checkpointRouter` 口径） |

## 5. 风险与约束

1. **两本账风险**（最高）：任何新代码自建 `L1HostRegistry` 都视为违规——P0 的 hub 是唯一入口，之后加静态守卫。
2. **双持久化风险**：P3 前 kernel checkpoint 与 legacy checkpoint 并存，必须以"谁恢复谁"写清，避免恢复出两份状态。
3. **外层选件策略质量**：`selectExecutable` 目前没有生产策略实现，P2 先用"单组件 DIRECT 预设 + 收敛即返回"的最小策略，再迭代。
4. **不改判据**：融合过程中禁止为了让实验变绿而改 oracle/探针；实验仅作为"没打坏"的回归证据。
