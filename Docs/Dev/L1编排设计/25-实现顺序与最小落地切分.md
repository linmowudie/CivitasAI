## 1. 切分原则（四条）

| # | 原则 | 理由 |
|---|---|---|
| 1 | **先修两个既有缺陷** | 多个组件依赖它们（落盘 / 拒写），不修则后续全是空壳 |

## 3. 每步的通用验收清单

```bash
npm run typecheck     # 0 error
npm run lint          # 0 error
npx vitest run        # 全绿
npm run bench         # 自测 + 守门 + 审计
```

**外加（这是本页的重点）**：每步必须新增**至少一条负向测试**，形态照抄本仓已跑通的两个先例：

```
registerTool(非法) → 断言 ok === false          ← "非法即拒"的形态（已跑通）
validateToolSpec(非法 spec) → 断言 errors 非空   ← 纯函数式校验的形态（已跑通）
```

**禁止**用"静态匹配"充当负向验证：

| 不算通过 | 因为 |
|---|---|
| 断言源码里含 `if (violations.length)` | 只证明**写了**检查，不证明**检查会拒** |
| 断言注释/文档里提到该判据 | 本仓已有"审计把注释当代码"的教训 |
| 断言函数存在 | 存在 ≠ 被调用 ≠ 生效 |

## 4. 与 Benchmark 的关系（不要另起一套）

- 每步落地后，**对应 cell 的 `attestation` 从 `static` 升级为 `executed`** 需要**真实调用探针**（形态照抄 `Benchmarks/runner/assertProbes.ts` 的 6 个探针）
- **不要**为了让数字好看而把 `static` 改写成 `executed` —— 本仓已抓到过"锚点存在被当成锚点通过"的假绿

## 6. 建议的第一枪

**S0**（修两个既有缺陷）—— 理由：① 它**不依赖任何新组件**；② 它是多个组件的**前置**；③ 它能立刻给出一条**真实调用**的负向测试，
把"负向用例必须真实调用"这条纪律**在本项目里先立起来**。

S0 的两条验收都可当场证伪：

```
① 挂一个 afterAgent 插件 → 断言 runIteration 后它被调用（当前必然失败，修后才通过）
② 造乐观锁版本冲突 → 断言写入被拒（当前必然失败：会返回 ok）
```

**这两条现在就能跑，且现在应该是"红的"** —— 先让它们红，再让它们绿。

### 7.1 修前的重要发现（比修复本身更值钱）

**缺陷同时写进了实现与测试** —— `Tests/EventBus/eventBus.spec.ts` 的两条 G8-1 用例
原本**断言 `expect(r2.ok).toBe(true)`**（即"版本冲突时 Result 是 ok"），
与实现 `ok({success:false})` 互相印证，**两边都是绿的**。

⇒ 这就是本仓反复出现的假绿形态：**契约错了，测试照着错契约写，于是没人发现**。
修后按契约（`writeGuard.ts:34`「拒写」）改正断言，并把结构化冲突信息的校验移到
`VERSION_CONFLICT` 事件的 payload（信息不丢，覆盖不减）。

### 7.2 修后的连带效应（必须如实记录）

`afterAgent` 一旦派发，**两个原本是死代码的中间件开始真的执行**：
`checkpointWriter`（挂起态落盘）与 `stopRuleEvaluator`（停止规则）。
这是行为变化，不是纯重构 —— 由全量回归覆盖验证（**174 文件 / 2061 用例全绿**）。

### 7.5 本步的方法论要点：**用变异检验证明测试有牙**

本步做不到"干净的先红"——**会话 API 原本不存在，测试无从编译**，
所以实现与测试是同一步完成的。为了不让"5/5 绿"变成自我印证，补做了一次**变异检验**：

```
变异：把 `const metrics = session?.metrics ?? _metrics;` 改成 `const metrics = _metrics;`
结果：3 条隔离断言【转红】· 2 条（兼容路径 + 结构相异）仍绿
还原：5/5 回绿
```

⇒ 证明这些断言**真的能检出"隔离不存在"**，而非结构性同义反复。
（这也回答了"金标准"问题：**变异能被测出**才叫有牙。）
