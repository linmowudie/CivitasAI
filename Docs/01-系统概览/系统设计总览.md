## 1. 系统定位

### 1.1 产品愿景

Civitas-AI 是一个**社会驱动型自治智能体系统**。系统打破传统固定流水线模式，以 Prime Director（老板 Agent）为中枢，根据任务复杂度自主决定组织形态，并内置司法、行政、税务等监管机制，实现自我纠错、资源管控与生态平衡。

### 1.2 核心隐喻

| 现实隐喻 | 系统映射 | 核心职责 |
|---------|---------|---------|
| 市长 | Prime Director | 需求解析、模式决策、全局编排 |
| 合伙人 | Partner | 联合攻坚高难度任务 |
| 员工 | Worker | 执行细分任务 |
| 流水线工人 | Assembly Line | 按 SOP 执行标准化任务 |
| 法院 | Arbitration Tribunal | 处理 Agent 间纠纷 |
| 政府 | Regulatory Authority | 跨域协调、全局规则维护 |
| 税务局 | Resource Audit Bureau | Token 监控、异常稽查、征税 |

### 1.3 技术选型摘要

| 决策项 | 选择 | ADR 编号 |
|--------|------|---------|
| 主语言 | TypeScript (Node.js) | 待定 |
| 运行形态 | 后端服务 | 待定 |
| 前端 | React（城邦大屏 + 用户交互） | 待定 |
| 持久化 | SQLite | 待定 |
| 前后端通信 | WebSocket（流式）+ REST（管理） | 待定 |
| LLM | 混合模型路由（多 Provider） | 待定 |
| 配置格式 | JSON / TS 原生对象 | 待定 |

## 2. Agent 类型定向（ADR-0000）

### 2.1 五元组

```
[A2 | B3 | C1 | N4 | R2]
```

| 轴 | 取值 | 含义 |
|----|------|------|
| D1 自主度 | A2 | 自由循环 — Prime Director 多步规划（评估→决策→招募→追踪→汇总） |
| D2 副作用面 | B3 | 执行命令/写外部系统 — Agent 写代码文件、执行命令、调用外部 LLM API |
| D3 上下文主导源 | C1 | 用户即时输入 — 主上下文来自用户需求，Agent 间通信是衍生上下文 |
| D4 交互拓扑 | N4 | 多 Agent 编排 — 动态组织、多角色协作 |
| D5 时效要求 | R2 | 交互流式 — 用户等待 Agent 工作，期望流式反馈 |

### 2.2 判定路径

决策树：Q1(输出非纯文本) → Q2(非 GUI 操作) → Q3(步骤不可预穷举，动态路由) → Q4(需要多专精角色分工 + 互相审查) → **T6 多 Agent 协作型**

### 2.3 T6 升级信号验证

| # | 信号 | 命中情况 |
|---|------|---------|
| 1 | 上下文不可容纳 | 多角色独立上下文（Director/Partner/Worker/Tribunal/Audit 各自私有） |
| 2 | 需要互相审查 | 仲裁庭 3-LLM 多数决 + 资源审计局独立稽查 |
| 3 | 工具集互斥 | Worker 最小工具集 vs Director 全局权限 vs Audit 只读稽查 |
| 4 | 时效量级不同 | 主任务交互流式(R2) vs 稽查/审计可离线(R1) |

### 2.4 与默认画像（T3）的差异

| 配置项 | T3 默认值 | T6 定向值 | 理由 |
|--------|----------|----------|------|
| 主循环形态 | 10 步自由循环 | 编排层循环 + Worker 内层循环 | 需要 Director 全局调度 |
| `max_iterations` | 30（`loopDefaults.max_iterations`） | 仍按角色单层限定（`roleOverrides[role].max_iterations`），但**另叠加全局墙钟与 Token 预算**（`stopRules.limits.*`） | 多 Agent 协作需全局视角，但单层上限不得取消 |
| 工具面 | 四级全开 | Worker 各自持最小工具集，禁止共享全量工具 | 安全隔离 |
| 安全信任模型 | 三级 | 每个 Worker 独立信任边界；跨 Agent 调用记为操作历史 | 沙箱隔离 |
| 分区预算上限 | S15% / L15% / M15% / H45%（`context.partitionCeilingRatio`） | **Phase 0–2 仍用同一默认值**；“Director L 大 / Worker H 大”为待实现目标，需先登记 `context.partitionCeilingByRole[role]`（Docs/11 §2.8） | 角色职责不同，但无键不得实现 |
| 历史与记忆 | 三类历史全量 | `trace_id` 跨 Agent 传播，Worker 各自 `operation_id` | 审计追溯 |
| 评测主指标 | 六维全量 | 端到端完成率 + 成本/任务 + 错误恢复率 | 协作效率优先 |

## 4. 核心机制摘要

### 4.1 六种路由模式

| 模式 | 代号 | 触发条件 | 参与角色 | 产出物 |
|------|------|---------|---------|--------|
| 高难攻坚 | `CONSORTIUM` | 预估 Token > 50K 或需 ≥ 2 个不同专业域 | PD + 1~N 个 PT | 《联合开发契约》 |
| 并行委派 | `DELEGATION` | 任务可拆解为低耦合子任务 | PD + 1~N 个 WK | 《任务分配书》 |
| 流水线 | `ASSEMBLY_LINE` | 任务流程高度确定性、可预定义 SOP | AL 节点序列 | SOP 执行结果 |
| 司法仲裁 | `LITIGATION` | Agent 间不可调和冲突 | AR (3-LLM) | 《裁决书》 |
| 行政协调 | `REGULATION` | 跨域重大事件或全局规则更新 | RG | 广播通知 / 规则更新 |
| 税务稽查 | `AUDIT` | Token 消耗异常触发 | AU | 稽查报告 / 冻结令 |

### 4.2 路由判定规则（已精确定义）

**Director 评估流程：**
1. 接收用户需求 → 1 次 LLM 调用生成结构化评估报告
2. 评估报告包含：预估 Token 消耗、所需专业域列表、任务耦合度评分
3. 按规则路由：

| 条件 | 路由 |
|------|------|
| 预估 Token > 50K **或** 专业域 ≥ 2 | `CONSORTIUM` |
| 任务可拆解为低耦合子任务（耦合度 < 0.3） | `DELEGATION` |
| 任务匹配已有 SOP 模板 | `ASSEMBLY_LINE` |
| 其他（简单任务） | PD 直接执行 |

> 阈值全部写入 `Configs/routingRules.json`，可热更新。

### 4.3 交付判定标准

| 失败类型 | 判定条件 |
|---------|---------|
| 格式不符 | 输出不符合任务分配书定义的输出 Schema |
| 质量不达标 | Director 评估输出质量评分 < 60/100 |
| 执行超时 | 超过任务分配书约定的 `maxIterations` 或时间上限 |
| 显式放弃 | Worker 返回 `UNABLE_TO_COMPLETE` 标记 |

**容错规则：** 连续 3 次失败 → 开除并重新招募。阈值可配。

### 4.4 Token 分润模型

```
Agent_i 分润 = 总Token池 × (Wq×质量分 + Wn×数量分 + We×效率分) / Σ(所有Agent综合分)

默认权重：Wq = 0.5, Wn = 0.3, We = 0.2
```

| 维度 | 度量方式 | 默认权重 |
|------|---------|---------|
| 产出质量 | 交付物被最终采纳的比例（Director 判定） | 0.5 |
| 产出量 | 有效输出 Token 数 | 0.3 |
| 效率 | 实际耗时倒数 | 0.2 |

### 4.5 异常消耗检测

| 判定规则 | 默认阈值 | 说明 |
|---------|---------|------|
| 滚动窗口超限 | 5 分钟内消耗 > 单 Agent 预算的 80% | 预算默认 10K tokens/5min |
| 偏离均值 | 当前轮消耗 > 该 Agent 近 10 轮均值的 3 倍 | 防止缓慢泄漏 |
| 循环检测 | 连续 3 次输出相似度 > 0.85 | 疑似死循环/幻觉重复 |

**处置流程：** 触发 → 警告（日志）→ 二次触发 → 冻结 Agent + 通知 Director

### 4.6 仲裁死锁定义与处理

| 死锁条件 | 定义 |
|---------|------|
| 判定死锁 | 3 个仲裁 LLM 给出 3 种不同裁决（无法达成多数决） |
| 超时死锁 | 仲裁流程超过 120 秒仍未出结果 |

**死锁处理：** 自动升级至 Regulatory Authority → 单 LLM 强制裁决 + 记录为"监管干预" → 通知用户

### 4.7 动态仲裁者数量控制（来自思考1）

冲突频率与 Agent 数量的关系：$f = k \cdot n^{m}$（$m > 1$，超线性增长）

**动态调整策略：**
- 核心层仲裁者：固定 1 个，处理常规冲突
- 辅助层仲裁者：按冲突监测指标动态增减
- 调整触发：连续 3 个时间窗口冲突频率超阈值 → 增加辅助仲裁者
- 资源约束：仲裁者总数 ≤ min(C/c_i, B/b_i)，受计算资源和通信资源双重约束

### 4.8 治理型共享记忆（来自思考2）

**六步治理闭环：**
1. 写入拦截 → 2. 胶囊调阅 → 3. 裁决推理 → 4. 律师函挂起 → 5. 现场恢复 → 6. 知识沉淀

**裁决优先级协议（由高到低）：**
1. 时间戳优先（LWW）
2. 任务权威性优先
3. 证据链完整性优先
4. LLM 语义推理兜底

## 7. 全局 ID 定义

三个核心 ID 的语义在全部分系统中必须一致，禁止混用：

| ID | 粒度 | 生成时机 | 格式 |
|----|------|---------|------|
| `session_key` | 一个逻辑会话（用户维度） | 会话首次创建时 | SHA-256 前 16 位十六进制 |
| `trace_id` | 一次 Agent 运行会话（运行维度） | 运行启动时 | UUID v4 |
| `operation_id` | 单次工具调用/文件操作 | 操作发起时 | `{timestamp_ms}-{4位随机hex}` |

**T6 扩展：** 跨 Agent 传播时复用同一 `trace_id`，新增 `parent_agent_id` 字段登记父子关系，禁止新造第三类追踪 ID。

## 8. 跨类型不可让渡的红线

以下规则与类型无关，任何实现都必须遵守：

| 红线 | 说明 |
|------|------|
| 安全默认拒绝 | 未明确允许的操作一律拒绝 |
| 危险确认不可绕过 | 危险级动作的确认流程不提供跳过开关 |
| ID 语义不可变 | `session_key` / `trace_id` / `operation_id` 不可混用 |
| 历史数据不可丢失 | 写入失败重试一次，仍失败则上报 FATAL |
| 日志不阻塞主流程 | 写入失败静默丢弃 |
| 所有配置项有默认值 | 空配置下系统可直接启动 |

### 8.1 v2 补充红线（对齐 Loop/Harness 工程）

| 红线 | 说明 | 来源 |
|------|------|------|
| **Verifier 四级不可跨越** | L1 硬验证未通过时禁止直接调用 L3 LLM Judge | Docs/12 §3 |
| **Maker ≠ Checker** | 产出与验证必须使用不同模型 + 不同提示 + 不共享上下文 | Docs/12 §3 §Docs/03 §7.1 |
| **LoopState 不可被压缩触及** | goal 与 immutableConstraints 不在任何上下文压缩机制的可写集 | Docs/12 §4.1 |
| **失败反馈必可行动** | 禁止 "retry" 式无证据反馈，必须写 FailureFeedback 具体证据 | Docs/12 §7 |
| **每个 Loop 至少 4 类退出** | 成功 + 上限 + 预算 + 无进展 + 风险，缺一拒发 | Docs/12 §2 |
| **不可逆副作用先写 INTENT 后执行** | 任何 `idempotency='NO'` 或 `reversibility='IRREVERSIBLE'` 工具 | Docs/13 §4 |
| **审批超时默认拒绝** | 禁止任何"无应答自动通过"机制 | Docs/12 §6.3 |
| **trace_id 跨 Agent 不可变** | 子 Agent 继承父 trace_id + 新增 parent_agent_id | Docs/02 §3.2 |
| **主循环 10 步不可调换** | 任何重序需写 ADR | skill source-code.md + Docs/02 §3 |
| **中间件与监管共存** | 不得将监管折叠回中间件，不得省略中间件只留监管 | skill + Docs/02 §4.3 |
