## 2. 前置修复：长时记忆原本不落库

接入过程中发现（新登记 `FE-026`）：`Src/Services/SharedMemory/longTermMemory.ts` 只用进程内 `Map`，
而 SQLite 表 `long_term_memory`（迁移 v17）**没有任何读写方**，实测 0 行。后果有两个：

1. **重启即丢**：记忆完全依赖进程存活，"跨任务持久化"名不副实；
2. **ID 重用**：`memoryId = ltm-${++memoryCounter}`，每次启动计数器归零 →
   重启后新建的记忆会复用 `ltm-1`，而云端按 `clientMemoryId` 幂等 upsert，
   会把**另一条记忆的内容**写进同一条云端记录（串号）。

修复（`Src/Services/SharedMemory/longTermMemoryStore.ts` + `longTermMemory.ts`）：

| 能力 | 说明 |
|---|---|
| 写穿落库 | `writeMemory` 后 `INSERT ... ON CONFLICT(memory_id) DO UPDATE`（fail-safe：失败仅告警，不中断 Agent 循环） |
| 启动回灌 | `hydrateLongTermMemory()`（`Src/main.ts` 步骤 ⑦.2）把库中记忆载入内存 |
| **计数器恢复** | 回灌时把计数器推进到 `max(ltm-N)+1`，**杜绝重启后 ID 重用** |
| 访问/状态落库 | `persistAccess`（读路径，失败静默）、`persistStatus`（deprecated/contradicted） |
| 批量导入 | `importMemories()` 供云端恢复使用（幂等 upsert + 计数器同步推进） |

**注意**：`resetLongTermMemory()` 只清内存（测试用），库中记录保留。

### 3.1 为什么服务端请求由主进程转发

渲染进程是**浏览器上下文**：直接 `fetch('http://127.0.0.1:8787/...')` 属跨源请求，
必须服务端配置 CORS；打包后页面来源为 `file://`（`Origin: null`）更麻烦。
因此桌面端统一走 **主进程 IPC 转发**（`ipcMain.handle('server-fetch')` → Node `fetch`），
不受 CORS 约束，且**服务端无需为桌面端开放 CORS**（安全面更小）。

- Electron（含打包后）：`electronAPI.serverFetch` 存在 → 走主进程；
- 浏览器（`npm run dev` 调试）：降级为原生 `fetch`，此时**必须**配置服务端
  `CORS_ORIGINS=http://localhost:5173`（否则报连接失败，错误文案已提示该原因）。

## 4. 令牌存储与登录态

| 环境 | 存储 | 说明 |
|---|---|---|
| Electron | 主进程 **`safeStorage`** 加密后写入 `userData/secure-store.json` | Windows DPAPI / macOS Keychain / Linux libsecret；渲染进程只经 IPC 读写（通道 `secure-store-available` / `secure-store-get` / `secure-store-set` / `secure-store-remove`，主进程注册见 `electron/main.ts` 同名 `ipcMain.handle`；渲染侧封装见 `Client/src/services/secureStore.ts` 的 `probeSecureStorage` / `getSecureStore`） |
| 浏览器 | `sessionStorage` | 仅本会话；面板明确提示"令牌未加密存储，关闭窗口需重新登录"（`secureStore.ts` 的 `fallbackStore`） |

- 令牌**只存在于内存 + 安全存储**：不进 `localStorage`、不进 zustand 持久化、不进日志。
  键名 `civitas.account.tokens`（`secureStore.ts` 的 `TOKENS_STORAGE_KEY`）；
  设备凭据 `civitas.device.id` / `civitas.device.credential` 同样落 safeStorage
  （`accountStore.ts` 的 `getDevice()`）。
- `init()`（**2026-10-03 校准**：由 `Client/src/App.tsx` 根组件与左栏
  `Client/src/components/Layout/LeftPanel/FeatureList.tsx` 各调用一次，store 内部幂等，
  不阻塞其他功能）：
  1. 读本地服务器地址（`localStorage`，明文本地配置）+ 异步探测 safeStorage 可用性；
  2. 尝试从安全存储恢复令牌 → `GET /v1/me` 校验 → 成功则进入已登录态；
  3. 失败（令牌过期/被重用）→ 回落匿名态并清理令牌。
- **401 自动续期**：`serverApi.authedRequest` 遇到 `TOKEN_EXPIRED`/`UNAUTHENTICATED` 时
  用刷新令牌换新令牌并**重试一次**；并发请求通过**单飞**（single-flight）只刷新一次。
- `TOKEN_REUSED`：判定为凭证泄漏（服务端已吊销整族）→ 立即清空登录态并提示重新登录。
- 鉴权钩子在 **store 创建时注入一次**（不依赖 `init()` 先被调用），避免调用顺序导致的静默 `NOT_LOGGED_IN`。

## 5. 同步语义

### 5.1 上行（push，手动触发）

| 数据 | 客户端来源 | 服务端接口 | 幂等键 | 备注 |
|---|---|---|---|---|
| 应用偏好 | `prefsStore.prefs` + `gatherLocalPrefs()` 并入 `chatStore` 运行时选中项 | `PUT /v1/settings`（`data.app`） | 带 `expectedRevision` | 冲突返回 `409`，由用户选择以哪端为准 |
| **配置 overrides**（2026-10-03 校准新增） | `configStore.getOverridesForSync()`（仅用户显式改过的键） | `PUT /v1/settings`（`data.config`） | 同上（与偏好**同一个 revision**） | 成功后 `configStore.markSynced()` 清 `dirty` |
| 长时记忆 | IPC `ipcGetLongTermMemory({limit:5000})` 优先，降级 `GET /api/memory/long-term?limit=5000` | `POST /v1/memories/bulk` | `clientMemoryId = memoryId` | 每批 ≤500（服务端上限 1000） |
| 个人统计 | IPC `ipcGetStatsEvents({since,limit:500})` 优先，降级 `GET /api/sync/stats-events?since=` | `POST /v1/stats/events` | `clientEventId` | 最多 10 轮续拉，每轮成功后推进 `statsSyncSince` |
| **任务元数据**（2026-10-03 校准新增） | `fetchLocalSessionsForSync()`：IPC `ipcListSessions({archived:'all'})` 优先，降级 `GET /api/sessions?archived=all` | `POST /v1/tasks/bulk` | `clientSessionId = session_id` | 每批 ≤500；**只上行 `title`/`createdAt`/`updatedAt`/`archivedAt`，正文不上行**；失败降级为 `warnings` |

### 5.2 下行（pull，登录后自动 + 手动）

| 数据 | 服务端来源 | 客户端落点 |
|---|---|---|
| 应用偏好 | `GET /v1/settings` → `data.app` | `prefsStore.applyFromServer()` + `applyPrefsToRuntime()` 写回 `chatStore`（模型/工作方式） |
| **配置 overrides**（2026-10-03 校准新增） | `GET /v1/settings` → `data.config` | `configStore.applyFromCloud()`（服务端权威覆盖本地 overrides，并清 `dirty`） |
| 长时记忆 | `GET /v1/memories`（键集分页，最多 50 页 × 200） | `importLocalMemories()`：IPC `ipdBulkLongTermMemory` 优先，降级 `POST /api/memory/long-term/bulk` 批量导入（幂等） |
| **任务归档状态**（2026-10-03 校准新增） | `GET /v1/tasks?archived=all&limit=2000` | `applyServerTaskStates()`：IPC `ipcArchiveSession` 优先，降级 `POST /api/sessions/:id/archive`。**只对齐本机已存在的任务**；云端有而本机无正文的任务**不创建空会话**（避免"幽灵任务"） |
| 统计概览 | `GET /v1/stats/overview` | 面板展示（累计事件/数值/活跃天数/云端记忆/活跃设备） |

### 5.3 冲突与失败

| 场景 | 行为 |
|---|---|
| 设置 revision 冲突 | `pushAll` 返回 `REVISION_MISMATCH` → 面板显示"云端版本 N"，提供 **以云端为准**（`pull()`）/ **以本机为准**（`push(true)`，`force=true` 不带 expectedRevision） |
| 网络类失败（`NETWORK`/`TIMEOUT`） | 入**重试队列**（同类型去重），面板显示"重试 N 项"，`scheduleRetry()` 30s 后自动重试一次（测试环境 `isTestEnv()` 不启用定时器） |
| 4xx（校验/权限等） | 原则上不入队（重试无意义），直接显示错误 |
| ⚠️【需人工裁定】`SESSION_EXPIRED` 的归类 | 代码真源：`accountStore.ts` 的 `enqueueIfTransient()` 判定式为 `code === 'NETWORK' \|\| code === 'TIMEOUT' \|\| code === 'SESSION_EXPIRED'`；而 `SESSION_EXPIRED` 由 `serverApi.authedRequest` 刷新失败产生（HTTP 语义即 401），**与上一行"4xx 不入队"矛盾**，且未登录状态下重试必然再次失败。2026-10-03 校准仅登记现状：**待裁定**二选一——文档补"会话过期除外"，或代码剔除 `SESSION_EXPIRED`（倾向后者：登录成功后已有自动 `pull()`）。本轮不裁决、不改代码 |
| 记忆/统计/任务子步骤失败 | 记入 `warnings` 并展示，**不阻断**其他子步骤（部分成功可见）；**例外**：`PUT/GET /v1/settings` 失败即整体失败（不静默） |

### 5.4 本地数据来源（统计派生）

`GET /api/sync/stats-events?since&limit`（`Src/Interface/RestApi/syncApi.ts`；Electron 下由 IPC

## 6. 字段映射（本地 ↔ 服务端）

| 本地（`long_term_memory`） | 服务端（`memories`） | 转换 |
|---|---|---|
| `memory_id` | `client_memory_id` | 直传（幂等键） |
| `title` / `content` / `category` | 同名 | 直传（服务端 `category` 为自由文本） |
| `assertion` | `assertion` | **2026-10-03 校准（原"故恒为 `observed`"表述过宽，已按代码拆分）**：① **本地写入路径**——`Src/Services/SharedMemory/longTermMemory.ts` 的 `writeMemory()` 经 `isEligibleForLongTerm()` 只接受 `observed`，其余一律拒绝；② **上行映射**——`Client/src/services/syncService.ts` 的 `toServerMemoryItem()` 放行 `observed`/`inferred`/`verified`/`disputed`，非枚举值回落 `observed`；③ **云端导入路径**——`importMemories()` 只做必要字段兜底校验，**不做 `observed` 过滤**，原样落库 ⇒ 一旦云端存在非 `observed` 断言，本地即会出现非 `observed` 记录，"恒为 `observed`"不成立。⚠️【需人工裁定】：现状记录如上，**待裁定**二选一——文档把不变式限定为"仅 Agent 写入路径"，或在 `importMemories()` 统一回落 `observed`。本轮不裁决、不改代码 |
| `status`：`active`/`deprecated`/`contradicted` | `active`/`archived`/`deleted` | **有损映射**：`deprecated`/`contradicted` → `archived`；反向 `archived` → `deprecated`（有 `contradictedBy` 时为 `contradicted`） |
| `sourceTraceIds` / `sourceArbitrationIds` | 同名（jsonb） | 数组 ↔ jsonb |
| `created_at` / `last_accessed_at`(ms) | `createdAt` / `lastAccessedAt`(ISO) | 时间戳 ↔ ISO |
| `access_count` | `accessCount` | 直传 |

> 状态枚举有损是**有意为之**：服务端墓碑语义只需 `active/archived/deleted`；
> 本地更细的 `deprecated`/`contradicted` 在往返后会归一为 `deprecated`（不丢记忆本身，仅丢细分）。

## 12. 登录系统安全审计与加固（2026-10-02）

> 本节由一次「参照业界标准审计现有登录系统」的工作沉淀。
> 结论先讲：**服务端的数据隔离是对的（10/10 实测通过），但客户端把"机器级数据"当成了"账号级数据"，
> 且设备绑定策略会让用户换机后永久失去账号**。
> **2026-10-03 校准（限定"均已修复"的范围）**：跨账号隔离（FE-032）与"新设备被硬拒"（FE-033，`warn` 默认放行）
> 确已修复；但设备策略链路上仍有两项残留——**设备/会话吊销的 HTTP 方法不匹配**（【需人工裁定】）与
> **密码路径完全绕过设备策略**（⚠️ 未实现/目标态），详见 §12.3 与 §11 C9/C10。

### 12.1 与业界标准做法的对照

| 标准做法 | 出处 | 审计前状态 | 现状 |
|---|---|---|---|
| 原生客户端用授权码 + PKCE（或 RFC 8628 设备授权），不绑硬件 | [NIST SP 1800-13](https://www.nccoe.nist.gov/sites/default/files/legacy-files/psfr-mobile-sso-nist-sp1800-13-draft-v2.pdf#29#7) | ❌ 邮箱+验证码 + 硬件指纹硬绑定 | 🟨 验证码登录保留（自托管合理），硬绑定取消 |
| 新设备 = **需确认的事件**，而非硬拒绝 | [ZITADEL · Identity Patterns for AI](https://help.zitadel.com/identity-patterns-for-ai-securing-agents-with-zitadel) | ❌ 新设备直接 403，无解绑入口 | 🟨 默认 `warn` 记录 + 审计已生效；`strict` 可选，但**自助解绑端到端不可用**（客户端发 POST、服务端只注册 DELETE）——见 §12.3 / §11 C9（2026-10-03 校准，原记 ✅ 覆盖过宽） |
| 短时效访问令牌 + 刷新轮换 + 重用检测 | [OAuth 2.0/OIDC 流程](https://github.com/sujeet-pro/sujeet.pro/blob/main/content/articles/oauth-oidc-flow-guide/README.md#1) | ✅ 已实现 | ✅ 保持 |
| 一次性凭证**哈希存储**、CSPRNG、失败锁定 | [Microsoft · AI Agent 身份](https://learn.microsoft.com/en-us/startups/build/identity-management/identity-fundamentals-ai-agents#1) | ❌ 明文落库 + `Math.random()` + 无锁定 | ✅ 哈希 + `randomInt` + 5 次锁定 + 配额/冷却 |
| 令牌可撤销（短 TTL 兜底） | [Microsoft 身份平台](https://learn.microsoft.com/zh-hk/entra/identity-platform/v2-oauth2-auth-code-flow#3) | 🟥 访问令牌无状态（TTL 15 分钟） | ✅ **已修（2026-10-03 校准，原记"🟥 保持 `SV-002`"已过时）**：`Server/src/http/authGuard.ts` 按令牌 `sid` 回查 `refresh_tokens` 的 `revoked_at`/`expires_at`，命中吊销即 401 ⇒ 改密/登出/吊销会话后**旧访问令牌立刻失效**，不再只靠短 TTL 兜底 |
| 生产必须能真实投递验证码 | — | ❌ 只有 `console.log` + TODO | ✅ webhook 通道，未配置则**拒绝启动** |

### 12.2 审计发现（均以实测为准）

| # | 问题 | 证据 | 处置 |
|---|---|---|---|
| A1 | **设备绑定 = 换机/重装永久锁死**：指纹取自 MAC 列表 + 主机名 + 磁盘序列号，切换 Wi-Fi/插拔 VPN/改主机名/换盘/Win11 缺 `wmic` 都会变；且无解绑 API（仓储里 `revokeDevice` 是死代码） | 新设备登录 `403`；`/v1/auth/unbind-device`、`/v1/me/device(s)`、`/v1/auth/unbind` 全 404 | 见 §12.3 |
| A2 | **跨账号数据不隔离**：本地记忆无属主列，上行取全部本地记忆 + 当前令牌 | A 写入的记忆在 B 登录后可见，并已写入 B 的云端账号 | 见 §12.4 |
| A3 | 验证码**明文落库**、`Math.random()` 生成、无失败锁定 | 库中 `code` 与接口返回一致；连错 5 次后正确码仍可登录 | 哈希 + CSPRNG + 计数作废 + 配额/冷却 |
| A4 | **生产环境发不出验证码**（唯一登录入口） | `authService` 生产分支只有 TODO | webhook 通道 + 生产 fail-closed |

### 12.3 设备策略（修复后）

| 模式 | 行为 | 适用 |
|---|---|---|
| `off` | 不记录设备 | 单机自用 |
| **`warn`（默认）** | 记录设备、审计 `auth.new_device`、**允许登录** | 个人自托管（换机/换网不再被锁死） |
| `strict` | 拒绝未登记设备；**首个设备放行**；提供自助解绑 | 企业/共享设备 |

> ⚠️ **2026-10-03 校准（适用范围）**：上表的 off/warn/strict 分支**只存在于**
> `Server/src/services/authService.ts` 的 `loginWithCode()`（其"⑤ 设备处理"块，含 strict 的
> `device_not_registered` 拒绝与 `auth.new_device` 审计）。`authService.register()` 与
> `authService.login()`（密码路径）**没有任何设备处理代码** ⇒ 密码登录完全绕过设备策略，
> `user_devices` 也不会因密码登录而增长。表所述"策略"目前**不等于全量生效**。

- **设备身份 = 安装期凭据**：客户端首次运行生成随机串（`crypto.randomUUID`）存 `safeStorage`
  （键 `civitas.device.id` / `civitas.device.credential`，见 `accountStore.ts` 的 `getDevice()`）；服务端只存 `sha256(credential)`
  （`Server/src/repositories/users.ts` 的 `upsertDevice()`，`credential` 传入时 `kind='install'`）。
  硬件指纹只作为设备列表里的可读标签（`accountStore.ts` 的 `deviceLabel()`，经 IPC `ipc-get-device-fingerprint` 取值）。
  - ⚠️ **2026-10-03 校准（原"登录时随请求发送"表述过宽）**：实际**只有 `accountStore.loginWithCode()`**

### 12.4 如何保证"登录后拉取/上传的都是当前用户的数据"

**三道闸**，缺一不可：

1. **服务端（权威）**：所有仓储查询都以令牌中的 `sub` 作为 `user_id` 过滤；
   按 ID 访问他人资源一律 **404**（不泄露存在性）；请求体无法指定 `user_id`。
   实测（A/B 双账号）：设置、记忆列表、按 ID 读/改/删、统计汇总、备份包、吊销他人会话 —— **10/10 全部拒绝或为空**。
2. **本地数据带属主**：`long_term_memory` 复合主键 `(owner_user_id, memory_id)`（迁移 v21）；
   登录后属主 = 服务端 `userId`，未登录 = `local`；读写/回灌/导入全部按属主分区
   （`GET/PUT /api/account/active-user` 由客户端 `accountStore.adoptAccount()` 在登录/登出时经
   `services/api.ts` 的 `apiPut()` 切换，路由注册见 `Src/Interface/RestApi/memoryApi.ts`）。
   ⚠️ 2026-10-03 校准：该通道**只有 HTTP、无对应 IPC handler**，不受 §3"IPC 直连优先"影响，
   因此浏览器/无 IPC 环境下依赖本地 REST 仍在跑（:3000）。
   - **2026-10-03 校准（覆盖面已扩大）**：迁移 v22 `add_owner_scope_to_personal_data` 为
     `chat_sessions` / `chat_messages` / `tasks` / `subtasks` / `global_workspace` / `pending_approvals` /
     `loops` / `effect_journal` / `token_wallets` / `token_transactions` 统一加上 `owner_user_id`
     （迁移 v26 再为 `chat_sessions` 加 `archived_at`，支撑 §5.1/§5.2 的任务元数据同步）。
     因此本道闸现在同时覆盖**统计派生**（§5.4 的 `WHERE owner_user_id = ?`）与
     **任务元数据**（`fetchLocalSessionsForSync` 取的会话列表本身即属主内数据）。
3. **同步元数据绑定账号**：`civitas.sync.meta.userId`；
   账号变化即丢弃 `serverRevision`/`statsSyncSince`（旧数据无此字段 → 一律按换账号处理）。

实机验证（修复后）：A 登录写入本地记忆 → 登出（命名空间回 `local`）→ B 登录（命名空间 = B 的 userId）→
**B 的本地记忆列表为空**，且 A 的云端数据不受影响。

### 12.5 验证码加固清单

| 项 | 实现 |
|---|---|
| 存储 | 只存 `sha256(code)`（迁移 003 移除明文列 `code`） |
| 生成 | `crypto.randomInt(100_000, 1_000_000)` |
| 比较 | `timingSafeEqual`（常量时间） |
| 一次性 | 成功后 `used_at = now()`；签发新码即作废旧码 |
| 失败锁定 | `attempts` 累加，达 `CODE_MAX_ATTEMPTS`（默认 5）即作废并提示"次数过多" |
| 发送配额 | `CODE_MAX_PER_WINDOW`（默认 3）/`CODE_WINDOW_SEC`（默认 600s） |
| 冷却 | `CODE_RESEND_COOLDOWN_SEC`（默认 60s，0 = 关闭） |
| devCode | 仅 `ALLOW_DEV_CODE=true` 且非生产；生产开启 → **拒绝启动** |
| 投递 | `MAIL_WEBHOOK_URL`（webhook POST JSON）；生产未配置 → **拒绝启动** |
