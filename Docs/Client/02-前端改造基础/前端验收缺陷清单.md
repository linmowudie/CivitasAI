# 前端验收缺陷清单

> **用途**：记录前端（含 Electron 壳与相关后端链路）验收过程中发现、**尚未修复**的缺陷与未实现功能。
> **配套**：修复完成后写入根目录 [`CHANGELOG.md`](../../../CHANGELOG.md)（代码与工程变更记录），本清单只做索引。
> **分工**：本清单 = 待办/未修复；`CHANGELOG.md` = 已修复的代码变更；`Docs/CHANGELOG.md` = 设计文档演进。

## 工作流

1. **手动测试发现问题** → 提问/描述现象 → 我复现定位 → 分配 ID 记入本清单「未修复」区（含根因文件行号与建议修法）
2. **修复完成** → 本清单状态改为「已修复」并附验证证据（测试名/CDP 实测数据）
3. **写入 [`CHANGELOG.md`](../../../CHANGELOG.md)** 对应日期小节 → 该项从「未修复」区移到文末「已修复归档」

## 状态约定

| 状态 | 含义 |
|---|---|
| 🟥 未修复 | 已确认，代码未改 |
| 🟨 修复中 | 正在改，未验证 |
| 🟩 已修复 | 已验证（附证据），待写入 CHANGELOG |
| ⬜ 已知限制 | 有意保留的取舍/未实现功能，不算缺陷 |

## 严重度约定

| 级别 | 含义 |
|---|---|
| P0 | 阻断主流程（无法对话/无法启动） |
| P1 | 功能不可用或数据错误 |
| P2 | 体验/一致性问题，有绕行方案 |
| P3 | 工程卫生（死代码/命名/文档不一致） |

### FE-032 跨账号数据不隔离（P0，🟩 已修复 2026-10-02 · 2026-10-03 复核 ✅）

- **现象（实测）**：同一台机器上，账号 A 登出、账号 B（全新）登录后，
  **B 能看到 A 的全部本地记忆**；B 点击「上传到云端」后，A 的记忆被写入 **B 的云端账号**。
- **实测证据**（真实 Electron + 真实服务端）：
  ```
  ② 以 A 身份写入本地记忆（含标记 LEAK-MARKER-…）→ 本地 3 条
  ④ 登出 A → ⑤ 用全新账号 B 登录 → ⑥ B 的本机记忆列表仍是 A 的 3 条（含 LEAK-MARKER）
  ⑦ B 点击上传 → 服务端核对：B 的云端记忆 = [ltm-cli-1 端到端验证记忆 A, ltm-cli-2 端到端验证记忆 B]
     —— 这两条原本由另一个账号（cli-…@example.com）上传 ⇒ 跨账号污染已发生
  ```
- **根因（客户端数据模型缺"属主"维度）**：
  1. 本地 `long_term_memory` 表**没有用户列**（`Src/Infra/Db/migrations.ts` v17），是"机器级"而非"账号级"；
  2. 上行入口不做过滤：`Client/src/services/syncService.ts` 的 `fetchLocalMemories()` → 直接
     `GET /api/memory/long-term`（返回**全部**本地记忆）再 `POST /v1/memories/bulk`（带上**当前**账号令牌）；
  3. 登出/切换账号**不清本地数据**：`accountStore.logout()`/`authStore.logout()` 只清令牌与内存状态；
  4. 偏好同样机器级：`localStorage['civitas.prefs']` / `['civitas.sync.meta']` 未按账号分区
     （`serverRevision`/`statsSyncSince` 会被下一个账号继承 → 误判"已同步"）；
  5. 会话与消息（`chat_sessions`/`chat_messages`）也机器级 → 同机换账号可见他人对话（未上行，属本地隐私泄露）。
- **影响面**：**隐私泄露 + 数据污染**（A 的记忆进入 B 的云端账号，且 A 的本地数据被 B 任意增删）。
  共享电脑/多账号场景 100% 命中；这也是"每个用户只应看到自己的数据"这一基本原则的破坏。
- **修复方案（建议按序）**：
  1. **本地数据加属主**：新增迁移给 `long_term_memory` 加 `owner_user_id text`（或 `account_key`），
     本地 REST 读写带上当前账号键（未登录时用 `local`），上行只取本账号的行；

### FE-033 设备绑定导致换机/重装永久锁死（P0，🟩 已修复 2026-10-02 · 2026-10-03 复核 ✅）

- **现象（实测）**：同一账号在"新设备"（指纹变化）上登录 → `403 FORBIDDEN 该账号已绑定其他设备，请联系管理员解绑`，
  且**没有任何自助解绑端点**（实测 `POST /v1/auth/unbind-device`、`DELETE /v1/me/device`、
  `DELETE /v1/me/devices`、`DELETE /v1/auth/unbind`、`DELETE /v1/me/devices/current` 全部 404）。
- **更严重的是指纹本身易变**：`Src/Infra/Security/deviceFingerprint.ts` → `getDeviceFingerprint()` 用
  **MAC 列表 + 主机名 + 磁盘序列号** 生成 SHA-256：
  - 切换 Wi-Fi/有线、插拔 VPN/虚拟网卡 → `getMacAddresses()` 结果变化 ⇒ 指纹变化；
  - 主机名修改、换硬盘/主板、Windows 11 无 `wmic`（`getDiskSerial()` 返回空串）⇒ 指纹变化；
  - 也就是说：**用户什么都没换，只要网络环境变一下就可能被自己的账号拒之门外**。
- **影响面**：与产品核心目标（"卸载重装后用同一账号登录即恢复数据"）**直接冲突**；
  且当前唯一"解绑"手段是**手工改数据库**（`users.bound_device_id`）。
- **附带风险**：绑定发生在**验证码登录**路径上，且是"首次登录即绑定"——
  任何先完成登录的人（知道邮箱 + 拿到/猜到验证码）会**抢绑**该账号，把真正的主人永久挡在外面（实测中我的测试脚本
  用 `attacker-device` 登录一次，该账号随后对所有新设备返回 403）。
- **修复方案（建议）**：
  1. **去掉硬绑定**，改为"新设备登录 = 一次可确认的事件"：向已验证邮箱发"新设备登录确认"，
     或允许在**已登录设备**上批准新设备（RFC 8628 设备授权思路）；
  2. 若必须保留绑定：必须提供**自助解绑/设备管理**（把仓储里已有的 `users.revokeDevice` 暴露为
     `GET /v1/me/devices` + `DELETE /v1/me/devices/:deviceId`，并用**当前有效会话**鉴权）；
  3. 指纹改为**稳定标识**（安装时生成随机 `device_secret` 存 `safeStorage`，服务端按"设备凭据"识别），
     而不是随网络/主机变化的硬件指纹；
  4. 至少在 UI 明确提示"换机会被拒绝"，并在服务端错误文案中给出可行路径（当前"请联系管理员"无任何入口）。
- **验证方式（修复后）**：账号在设备 1 登录 → 用设备 2（不同 deviceId）登录 → 可自助完成授权/解绑并进入；
  网络环境变化（增删 MAC）不影响已登录设备的继续使用。
- **2026-10-03 复核（现状）**：已按建议 2 + 3 落地——`Server/src/routes/auth.ts` 提供 `GET /v1/me/devices` 与
  `DELETE /v1/me/devices/:deviceId` 自助设备管理；客户端设备标识改为 `Client/src/stores/accountStore.ts` → `getDevice()`
  的稳定「安装 ID + 设备凭据」（safeStorage 持久），`deviceFingerprint.ts` → `getDeviceFingerprint()` 降级为**展示标签**
  （`fingerprintLabel`），不再参与身份判定。本条的建议清单按原样保留为决策过程。

### FE-041 方案 B 身份验真在 HTTP 链路上永不生效（P1，🟩 已修复 2026-10-04）

- **现象**：`POST /api/approvals/:id/decide` 声称"携带服务端令牌 → 向服务端 `/v1/me` 验真身份"（G-09 方案 B），但真实 HTTP 请求进入后 `req.headers` 恒为 `undefined` → `extractBearerToken` 恒返回 `null` → **永远回退方案 A**（本地活动账号绑定）。
- **根因（三段链路断在"构造点"）**：
  - 定义：`Src/Interface/Contracts/…` → `ApiRequest.headers?: Record<string, string>` 已定义；消费：`Src/Interface/RestApi/approvalApi.ts` → `extractBearerToken(req.headers)` → `resolveServerIdentity()`（`Src/Services/Governance/serverIdentity.ts`）已实现；
  - **断点**：`Src/Interface/WebServer/httpServer.ts` → `handleApiRequest()` 构造 `handleRequest({ method, url, body })` 时**未透传 `headers: req.headers`**——真头永远进不了 API 层。
  - 附带：同文件 CORS 响应 `Access-Control-Allow-Headers: 'Content-Type'` **未含 `Authorization`/`X-Account-Token`**——浏览器模式下预检即被拦。
- **影响面**：G-09 声称的"身份不可伪造（服务端验真）"加固**在端到端链路上不存在**；当前单机本地场景由方案 A（活动账号绑定）兼底，掩盖了断链；治理清单中"方案 B 实测"实为**函数级直调**（`resolveServerIdentity("fake-token")` 单测），未走 HTTP。
- **建议修法**：①`handleApiRequest` 构造时加 `headers: req.headers as Record<string, string>`；②CORS `Allow-Headers` 补 `Authorization, X-Account-Token`；③补一条走真实 HTTP 的集成用例（携伪造令牌 → 403，拒绝后落 `identity_unverified` 留痕）。
- **修复（2026-10-04）**：① `Src/Interface/WebServer/httpServer.ts` → `handleApiRequest` 构造 `handleRequest` 时透传
  `headers: normalizeRequestHeaders(req.headers)`（新增归一化函数：`IncomingMessage.headers`（值可为 `string | string[] | undefined`）
  → `Record<string, string>`，重复头以 `, ` 合并，符合 RFC 9110 §5.2 的 HTTP 语义）；
  ② CORS `Access-Control-Allow-Headers` 由 `Content-Type` 补全为 `Content-Type, Authorization, X-Account-Token`（浏览器预检放行）。
- **验证（2026-10-04）**：新增 `Tests/Interface/httpServerHeaderPassthrough.spec.ts`（5 项）：处理器层透传、
  未提供 headers 向后兼容、**真实 httpServer 往返**（`Authorization` 与 `X-Account-Token` 到达处理器）、CORS 预检放行。
