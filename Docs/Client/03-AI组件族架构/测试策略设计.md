## 0. 测试目标与原则

### 0.1 核心目标

确保 AI 组件族架构在演进过程中：
1. **视觉无回归**：MessageBubble 拆分前后，用户看到的界面完全一致
2. **动态加载可靠**：懒加载组件不会因网络延迟或 chunk 加载失败导致白屏
3. **性能可量化**：首屏加载时间、FCP、LCP 等指标有明确基线和验收阈值
4. **类型安全**：TypeScript 泛型约束能捕获 payload 结构不匹配错误

**四条目标的落地现状（2026-10-03 校准）**

| 目标 | 现状 | 承载物 / 缺口 |
|------|------|--------------|
| 1 视觉无回归 | ⚠️ **未实现/目标态**：无像素级快照件（全仓无 `*.snap`/`__snapshots__`，无 `jest-image-snapshot`） | 过渡替代为**结构断言**：`Tests/Client/message-list-turn.spec.tsx`、`Tests/Client/message-segments.spec.tsx`、`Tests/Client/tool-segment-order.spec.ts` 断言气泡内"思考/工具/正文"顺序与折叠形态，见 §2 顶部注记（TEST-07） |
| 2 动态加载可靠 | **部分实现**：注册表用例 21 条（`Tests/AIComponents/registry.spec.ts`），其中直接覆盖懒加载协议与族推断的 8 条（`registerFamily() + 懒加载` 3 + `inferFamilyFromEventType()` 5）；⚠️ 但运行期装配容器 `AIBubbleContainer` 不存在、`Subscribe` 生产零调用，故"加载失败不白屏"无任何端到端验证 | 见 §3 顶部注记（TEST-08）与 `AI组件族架构设计.md` ARCH-01/ARCH-04 |

### 0.2 测试金字塔

```
        ┌─────────────┐
        │   E2E 测试   │  ← 10%（关键用户旅程）
        ├─────────────┤
        │  集成测试    │  ← 20%（组件间交互）
        ├─────────────┤
        │  单元测试    │  ← 70%（单个组件逻辑）
        └─────────────┘
```

**理由**：AI 组件的核心价值是"可独立测试",因此单元测试占比应高于传统前端项目。

> **2026-10-03 校准（实际分布与金字塔的偏差）**：金字塔目前是"两层"而非三层。
> - 单元/组件层：`Tests/AIComponents/` 6 个 spec 文件 / 118 条用例（RTL + vitest）；
> - 集成层：全部为 **vitest 进程内**用例——`Tests/Client/`（14 文件 / 93 条，store + React 组件）、`Tests/Interface/`（含 `frontendIntegration.spec.ts` 的 REST 路由契约 25 条）、`Tests/AIComponents/eventBusBridge.spec.ts`（IPC 桥接 10 条）；
> - **UI E2E 层 = 0**：`@playwright/test` 未安装、无 `playwright.config.*`。注意 `Tests/E2E/` 下 9 个 `*.spec.ts`（如 `loopConvergence.spec.ts`）是**后端进程内**用例，只 import `vitest` 与 `Src/...`，不驱动浏览器，与本节的 UI E2E 不是同一层。

#### 测试 1：Harness.ToolGroup 渲染多轮工具调用（真实 props）

/**

const mockToolCalls: ToolCallEntry[] = [
  { id: 'tc-1', name: 'read_file', arguments: { path: '/test.txt' }, status: 'success', content: 'file content here' },
  { id: 'tc-2', name: 'exec_run', arguments: { cmd: 'ls -la' }, status: 'error', error: { code: 'EXEC_FAIL', message: 'Command failed' } },
  { id: 'tc-3', name: 'write_output', arguments: {}, status: 'pending' },

it('有工具调用时显示工具数量', () => {

  expect(screen.getByText('3 次')).toBeTruthy();

#### 测试 3：ComponentRegistry 懒加载触发（真实可运行）

```ts
// Tests/AIComponents/registry.spec.ts —— describe('registerFamily() + 懒加载')
import { beforeEach, vi, it, expect } from 'vitest';

beforeEach(() => { vi.resetModules(); });          // registry 是单例，靠 resetModules + 动态 import 隔离
async function createFreshRegistry() {
  const mod = await import('../../Client/src/ai-components/registry');
  return mod.registry;
}

it('注册族后，匹配该族事件时触发懒加载', async () => {
  const registry = await createFreshRegistry();
  const registerAllSpy = vi.fn();
  const loader = vi.fn().mockResolvedValue({ registerAll: registerAllSpy });

  registry.registerFamily('loop', loader);
  await registry.getComponent('loop:iteration');   // 前缀推断 → loop 族 → 触发 loader

  expect(loader).toHaveBeenCalledTimes(1);
  expect(registerAllSpy).toHaveBeenCalledTimes(1); // 懒加载回调协议：module.registerAll(registry)
});

it('族只加载一次（重复触发不重复加载）', async () => {
  const registry = await createFreshRegistry();
  const loader = vi.fn().mockResolvedValue({ registerAll: vi.fn() });
  registry.registerFamily('memory', loader);
  await registry.getComponent('memory:first');
  await registry.getComponent('memory:second');
  expect(loader).toHaveBeenCalledTimes(1);
});
```

## 附录 B：常见问题解答

### Q1：为什么不用 Cypress 而用 Playwright？

**A**：Playwright 对 Electron IPC / 网络模拟的支持更完善（原 WebSocket 时代 `page.route('ws://')` 已随架构简化而移除），且微软维护，更新频率高。

> **2026-10-03 校准（TEST-08）**：选型未变，但 ⚠️ **Playwright 尚未引入**（未安装、无 config、无 spec）。
> 另需修正本条理由的适用范围：迁移到 IPC 后，**渲染进程事件流不再经过任何可被 `page.route()` 拦截的网络面**
> （`window.electronAPI.onBackendEvent` 是 preload contextBridge 暴露的函数，不是网络请求），
> 因此"Playwright 支持 Electron IPC"这一说法**不成立**——真 E2E 要么注入 `window.electronAPI` stub，要么用 `@playwright/test` 的 Electron 驱动，
> 要么只测浏览器面（mock `GET /api/sessions/:id/ai-events`）。此结论影响 §3 的落地成本评估。

### Q2：快照测试会因字体渲染差异误报吗？

**A**：会。解决方案：
1. CI 使用固定字体（Google Fonts 离线包）
2. 设置 `failureThresholdType: 'percent'` 容差 0.1%
3. 使用 Chromatic 的智能 diff（忽略抗锯齿差异）

> **2026-10-03 校准（TEST-07）**：⚠️ 本问答**暂无适用对象**——快照体系（`jest-image-snapshot` + Chromatic + workflow）整体未启动，
> 三条对策均无执行件。待 §2 落地时一并生效。

### Q3：契约测试会增加多少 CI 时间？

**A**：约 2-3 分钟（Pact Mock Server 启动 + 验证）。可通过并行执行优化。

> **2026-10-03 校准（TEST-11 / TEST-13）**：当前 `ci.yml` 只有 `lint → test → build`，**Pact 未引入 → 增量时间为 0**。
> 同时提醒：现有 `test` job 需等 `lint` 完成、`build` 需等 `test`，**四 job 并行**的原设计（含 unit/snapshot/e2e/perf）尚未实现，
> 若引入契约/E2E，先考虑把串行链改为并行，否则 CI 时长为叠加而非取最大。
