# 共享记忆与上下文系统设计

> 本文档定义 Civitas-AI 的共享记忆系统（Shared Memory）与上下文管理，包括事件总线、共享/隔离双层存储、写入守卫、上下文胶囊和知识沉淀机制。

---

## 1. 职责边界

| 职责 | 说明 |
|------|------|
| 全局工作区管理 | 维护所有 Agent 可读写的共享状态 |
| 私有上下文隔离 | 每个 Agent 的中间推理过程物理隔离 |
| 写入守卫 | 拦截异常写入，检测语义冲突 |
| 上下文胶囊 | 按需为 Agent 组装轻量级上下文片段 |
| 知识沉淀 | 将临时事实提炼为长期知识 |
| 事件溯源 | 所有状态变更转化为不可变事件 |

**不负责：** 仲裁裁决（由 Arbitration 负责）、Token 扣减（由 TokenEconomy 负责）。

### 2.1 各层定义

| 层 | 数据范围 | 生命周期 | 存储位置 |
|----|---------|---------|---------|
| 共享层 | `messages`, `task_context`, `verdicts`, `contracts` | 全局持久/会话级 | SQLite + 内存缓存 |

### 3.1 全局工作区（GlobalWorkspace）

interface GlobalWorkspace {

### 3.2 写入守卫（WriteGuard）

```typescript
class WriteGuard {
  // 拦截写入请求
  async intercept(entry: WorkspaceEntry): Promise<InterceptResult> {
    // [1] 生成/验证语义向量
    const vector = entry.semanticVector ?? await this.generateVector(entry.content);
    
    // [2] 相似度碰撞检测
    const similarEntries = await this.workspace.searchByVector(vector, 5);
    
    // [3] 冲突判定
    for (const existing of similarEntries) {
      const similarity = cosineSimilarity(vector, existing.semanticVector);
      
      if (similarity > 0.85) {
        // 高相似度 → 检查是否语义相反
        const isOpposite = await this.checkSemanticOpposition(entry.content, existing.content);
        
        if (isOpposite) {
          // 语义冲突 → 阻断并上报
          return {
            allowed: false,
            conflict: {
              conflictId: generateId(),
              newMemoryId: entry.entryId,
              oldMemoryId: existing.entryId,
              similarity,
              conflictType: 'semantic_opposition',
            }
          };
        }
        
        // 高相似 + 非相反 → 可能是重复 → 警告但放行
        return { allowed: true, warning: 'potential_duplicate' };
      }
    }
    
    // 无冲突 → 放行
    return { allowed: true };
  }
}
```

### 3.3 上下文胶囊构建器（CapsuleBuilder）

```typescript
class CapsuleBuilder {
  // 为指定 Agent 构建上下文胶囊
  async buildForAgent(agentId: string, taskContext: TaskContext): Promise<Capsule> {
    const capsule: Capsule = {
      capsuleId: generateId(),
      agentId,
      sections: [],
      totalTokens: 0,
    };
    
    // [1] 任务描述（必选）
    capsule.sections.push({
      type: 'task_description',
      content: taskContext.description,
      tokenCount: await this.countTokens(taskContext.description),
    });
    
    // [2] 相关共享记忆（语义检索 Top-K）
    const relevantMemories = await this.workspace.searchBySemantic(
      taskContext.description,
      taskContext.memoryTopK ?? 5
    );
    capsule.sections.push({
      type: 'relevant_memories',
      content: relevantMemories.map(m => m.content).join('\n---\n'),
      tokenCount: await this.countTokens(relevantMemories.map(m => m.content).join('\n')),
    });
    
    // [3] 最近对话历史（按时间倒序，直到预算用尽）
    const recentMessages = await this.getRecentMessages(taskContext.traceId, taskContext.messageBudget);
    capsule.sections.push({
      type: 'recent_messages',
      content: recentMessages.map(m => formatMessage(m)).join('\n'),
      tokenCount: await this.countTokens(recentMessages.map(m => formatMessage(m)).join('\n')),
    });
    
    // [4] 约束条件
    if (taskContext.constraints?.length) {
      capsule.sections.push({
        type: 'constraints',
        content: taskContext.constraints.join('\n'),
        tokenCount: await this.countTokens(taskContext.constraints.join('\n')),
      });
    }
    
    // [5] 预算检查
    const totalTokens = capsule.sections.reduce((sum, s) => sum + s.tokenCount, 0);
    if (totalTokens > taskContext.capsuleBudget) {
      // 超预算 → 按优先级裁剪（constraints > task > memories > messages）
      await this.trimToBudget(capsule, taskContext.capsuleBudget);
    }
    
    return capsule;
  }
}
```

## 4. 事件总线（EventBus）

### 4.1 设计原则

| 原则 | 说明 |
|------|------|
| 事件溯源 | 所有状态变更转化为不可变事件 |
| 发布-订阅 | 组件仅订阅关心的事件类型，极致解耦 |
| 异步通信 | 事件处理不阻塞发布者 |
| 有序性 | 同一 trace 下的事件保证顺序 |

### 4.2 实现方案

**Phase 0-2：** 内存事件总线（进程内 EventEmitter 模式）

```typescript
interface EventBus {
  // 发布事件
  publish(event: DomainEvent): void;
  
  // 订阅事件
  subscribe(eventType: EventType, handler: EventHandler): Subscription;
  
  // 订阅多个事件
  subscribeMany(eventTypes: EventType[], handler: EventHandler): Subscription;
  
  // 等待特定事件（Promise 化）
  waitFor(eventType: EventType, filter?: (event: DomainEvent) => boolean, timeoutMs?: number): Promise<DomainEvent>;
}

interface DomainEvent {
  eventId: string;                     // UUID
  eventType: EventType;                // 🔴 必须是 §4.3 注册表成员，禁止自由字符串
  traceId?: string;                    // 关联 trace
  loopId?: string;                     // v2.1 补：Loop 级事件必填（供 §8.5 与 Docs/12 回放对齐）
  timestamp: number;                   // epoch **毫秒**（与 Docs/10 §1.1 时间列统一）
  priority: 'low' | 'normal' | 'high' | 'critical';
  payload: Record<string, unknown>;     // 事件数据
  source: string;                      // 发布者标识（组件名，如 'SharedMemory/WriteGuard'）
}
```

> **v2.1 修正**：① `eventType` 由 `string` 改为 `EventType`（否则§4.3 的"禁止自由字符串"红线在类型层不可执行）；
> ② `subscribe` / `subscribeMany` 的参数同步改为 `EventType` / `EventType[]`；
> ③ `timestamp` 由 ISO 字符串改为 epoch ms（全系统时间统一为整数毫秒，见 Docs/10 §1.1）；
> ④ `timeout` → `timeoutMs`（强制单位后缀）；⑤ 新增 `loopId`，原来 Loop 事件只能塞在 `payload` 里，导致索引与回放无法按 Loop 检索。

**Phase 3 升级路径：** 内存事件总线 → Redis Pub/Sub（接口不变，仅替换实现）

## 5. 数据流图

```
Agent-A 写入新记忆
    │
    ▼
WriteGuard.intercept()
    │
    ├── 无冲突 → GlobalWorkspace.write() → 广播 MEMORY_WRITTEN
    └── 有冲突 → 生成 CONFLICT_DETECTED
                    │
                    ▼
              Arbitration 六步闭环
                    │
                    ├── 胶囊调阅 → 裁决推理 → 律师函挂起
                    │
                    ▼
              裁决完成
                    │
                    ├── 胜者记忆写入 → MEMORY_WRITTEN
                    ├── 败者记忆标记 → MEMORY_SUPERSEDED
                    ├── 恢复确认 → RESTORATION_ACK
                    └── 知识沉淀 → KNOWLEDGE_CONSOLIDATION
                                    │
                                    ▼
                              LongTermMemory.write()
```

## 8. v2 补丁：Context ≠ State 拆分与并行隔离

> **修订依据**：`Docs/99-审查记录/设计审查报告-Loop与Harness工程.md` §3 失效三、§4.3、§4.4。

### 8.1 SharedMemory 职责边界重新定义（红线）

旧版中 `GlobalWorkspace` 同时充当了【跨 Agent 共享上下文】与【任务事实】两个角色，导致：
- 上下文压缩会意外修改任务事实；
- 不同 Agent 看到不同时间点的 workspace 无版本号；
- 一个 Agent 错误写入会污染其他 Agent 下一轮上下文。

**v2 红线**：

| 存放 | 内容 | 写入时机 | 允许丢失 |
|------|------|---------|---------|
| **LoopState**（Docs/12 §4） | 任务事实 | 每轮末尾强一致 | ❌ |
| **GlobalWorkspace** | 跨 Agent 可共享的观察 | 事件到达 | ⚠️ 可从 Event 重建 |
| **LongTermMemory** | 知识沉淀 | 任务完成后 | ⚠️ |
| **Context（本轮装配）** | 从上面三者临时拼装 | ⑥ 之前 | 不适用 |

**禁止**：任何将 `goal / immutable_constraints / successCriteria` 写入 GlobalWorkspace 的行为——必须写入 LoopState。

### 8.2 版本号与乐观锁（新增）

`WorkspaceEntry` 必须包含：

```typescript
interface WorkspaceEntry {
  // ... 旧字段保留
  version: number;                // 🔴 新增：单调递增
  lastModifiedBy: string;         // 🔴 新增：agentId
  conflictStrategy: 'lww' | 'authority' | 'arbitrate';  // 🔴 新增
  causalTokens: string[];         // 🔴 新增：因果一致性向量
}
```

**写入约束**：
- `GlobalWorkspace.write(key, value, expectedVersion)` —— expectedVersion 不匹配 → 拒写 → 产生 `VERSION_CONFLICT`；
- `causalTokens` 记录本次写前看到过的其他 Agent 写入事件 id；用于仲裁时重建 happens-before 关系。

### 8.3 WorkspaceLock（并行隔离）

对齐审查报告 §4.3：“并行 Agent 必须隔离工作区”。

```typescript
// Services/SharedMemory/WorkspaceLock.ts
interface LockRequest {
  key: string;                 // 文件路径或 entryKey
  agentId: string;
  mode: 'READ' | 'WRITE' | 'EXCLUSIVE';
  ttlMs: number;                // 默认 60_000
}

// 语义
acquire(req): Promise<Grant | Rejected | Queued>
release(grantId): Promise<void>
```

**策略**：
| 目录/资源 | 默认锁 | 适用 |
|---------|-------|------|
| `Data/Workspace/{session}/{taskId}/{agentId}/**` | 无锁（天然隔离） | 代码任务个人目录 |
| `Data/Workspace/{session}/shared/**` | 乐观锁 | 需合并的产物 |
| 同一仓库 | Git worktree | Consortium 代码任务 |
| `GlobalWorkspace.entries` | 版本号 + LWW/仲裁 | 共享上下文 |

### 8.4 Self-Reinforcing 防御（错误传播）

针对“Agent 上一轮错误结论被下一轮当事实前提”，新增：

- 写入 GlobalWorkspace 时区分 `assertion: 'observed' | 'inferred' | 'assumed'`；
- 只有 `observed` （工具返回值/硬验证结果）可直接入 L 低频分区；
- `inferred` 与 `assumed` 必须进入 M/H，不会进入长期记忆；
- GoalReanchor 从原始数据源重新推导时丢弃 `inferred/assumed`。

### 8.5 与 Docs/12 Docs/13 的接口契约

| 交互 | 方式 |
|------|------|

| GlobalWorkspace.read | 不写日志；但携带 LoopState.lastCheckpointId 作为快照时间戳 |
