# 配置体系与安全设计

> 本文档定义 Civitas-AI 的配置管理方案和安全威胁模型，包括配置项汇总、加载策略、安全信任模型、注入防御和审计机制。
>
> **本文档 §2 是全局配置键的唯一事实源（Single Source of Truth）**。其他任何设计文档 **禁止重复定义配置键与默认值**，只能引用；
> 开发时的统一查询入口为 `Docs/15-参数总典与接口契约/参数总典.md`（含跨层参数映射与冲突裁决）。

## 1. 配置管理

### 1.1 配置文件清单

| 文件 | 路径 | 用途 | 可变性级别 |
|------|------|------|-----------|
| `default.json` | `Configs/default.json` | 全局默认配置（**所有键必须有默认值**） | L0（启动锁定） |
| `{env}.json` | `Configs/dev.json` / `Configs/prod.json` | 环境层配置，`{env}` 由 `CIVITAS_ENV` 指定，缺省 `dev` | L1（启动时读取） |
| `local.json` | `Configs/local.json` | 本地覆盖（gitignore） | L1（启动时读取） |
| `loopConfig.json` | `Configs/loopConfig.json` | 各角色 LoopConfig 默认值 | L2（运行时可重载） |
| `durable.json` | `Configs/durable.json` | 持久执行与恢复参数 | L2（运行时可重载） |
| `session.json` | `Configs/session.json` | 会话与归档参数 | L2（运行时可重载） |
| `modelRouter.json` | `Configs/modelRouter.json` | 模型路由配置 | L2（运行时可重载） |
| `routingRules.json` | `Configs/routingRules.json` | 路由判定规则 | L2（运行时可重载） |
| `economyRules.json` | `Configs/economyRules.json` | Token 经济规则 | L2（运行时可重载） |
| `supervision.json` | `Configs/supervision.json` | 监管参数 | L2（运行时可重载） |
| `memory.json` | `Configs/memory.json` | 共享记忆与事件总线参数 | L2（运行时可重载） |
| `arbitration.json` | `Configs/arbitration.json` | 仲裁系统参数 | L2（运行时可重载） |
| `audit.json` | `Configs/audit.json` | 审计系统参数 | L2（运行时可重载） |
| `security.json` | `Configs/security.json` | 安全策略配置 | L0（启动锁定） |
| `coverageBaseline.json` | `Configs/coverageBaseline.json` | 覆盖率基线 | L2（CI 读写） |
| `benchBaseline.json` | `Configs/benchBaseline.json` | 基准评估基线 | L2（CI 读写） |

> **扩展名统一 `.json`**（v2.1 裁决）：原 `Docs/02` 目录树中的 `default.toml` / `session.toml` / `durable.toml` 一律改称 `.json`，禁止混用两种格式。

### 1.2 配置加载优先级

```
local.json  >  {env}.json  >  default.json        （配置文件三层，优先级固定）
环境变量     →  仅用于注入密钥引用，不参与配置层级竞争
```

**规则：**
- `default.json` 提供所有配置项的默认值，**空配置下系统必须可直接启动**；
- `{env}.json` 为环境层（`dev.json` / `prod.json`），`{env}` 由 `CIVITAS_ENV` 决定；
- `local.json` 优先级最高，覆盖本地开发环境（不提交到 git）；
- **环境变量不再凌驾于 `local.json` 之上**（v2.1 修正：原写为 `环境变量 > local > default`，与全局约定冲突）；
  环境变量的唯一作用是解析 `api_key_ref: "env:OPENAI_API_KEY"` 这类引用；
- 运行时可重载的配置（L2）通过 `Infra/Watcher/configWatcher.ts` 文件监听触发。

### 1.2.1 命名与单位规范（强制 · v2.1 新增）

| 对象 | 风格 | 例 | 说明 |
|------|------|----|------|
| 配置文件键 | **camelCase** | `httpPort`、`qualityThreshold` | 例外见下方《命名豁免清单》 |
| DB 表名与列名 | **snake_case** | `timeout_ms`、`budget_used_tokens` | 与 TS 字段的对应关系必须是**机械转换**，禁止人为改名 |
| TS 接口字段 | **camelCase** | `budgetUsedTokens` ↔ 列 `budget_used_tokens` | repository 层统一做 snake↔camel 映射；`LoopConfig` 除外（见豁免清单） |
| 时长后缀 | 必带单位 | 毫秒 `_ms` / 秒 `_sec` / 分 `_min` / 时 `_hour` / 天 `_days` / 轮 `_rounds` | `busyTimeout: 5000` → **`busyTimeoutMs: 5000`**；禁止无单位后缀的时间配置 |
| 比例与阀值 | 内部一律 **0.0–1.0 浮点** | `qualityScore: 0.85` | 展示层才 ×100；禁止 0-100 与 0-1 混用；DB 对应列为 `REAL` |
| 金额 | `_usd` 后缀 + number | `hardUsd`、`budgetUsedUsd` | 与 token 计量严格分开 |
| 时间戳 | `number`（epoch **毫秒**）+ `_at` 后缀；DB 列一律 `INTEGER` | `recordedAt`、`created_at` | 禁止 ISO-8601 字符串与 epoch 整数在同一库内混用 |
| 枚举 | **三处同形**（TS / DB / 配置文件不做大小写转换） | `'awaiting_approval'` | 分两类：① 状态/阶段类用 lower snake_case；② 安全类沿用 skill 的 SCREAMING_SNAKE（见豁免清单）；禁止 UI 引入第二套拼写 |

**命名豁免清单（穷举，新增需先登记）**：

| # | 豁免对象 | 风格 | 理由 | 边界 |
|---|---------|------|------|------|
| X1 | `modelRouter.json` 的 `providers[]` / `models[]` 内层键 | snake_case（`base_url`/`api_key_ref`/`context_window`/`cost_per_1k_input`） | 上游 OpenAI/Anthropic 兼容契约要求 | 仅内层；`routing` 段仍 camelCase；由 `Infra/Llm` 边界层转成 camelCase 领域对象 |
| X2 | `loopConfig.json` 的 `loopDefaults` / `roleOverrides` 内层键 | snake_case（`model`/`max_iterations`/`timeout_ms`/`temperature`/`token_budget`/`stream`） | **skill `source-code.md`「LoopConfig 字段清单（强制）」明文规定**，且 benchmark 数据集与 prompt frontmatter 复用同名字段 | TS 侧 `LoopConfig` 接口**保持 snake_case，不改名**；repository 写入 `subtasks`/`agents` 时同名直存，无需转换。`stopRules.*`、`verifier.*` 等**本项目新增**段不受此约束，仍用 camelCase |
| X3 | `ToolSpec.dangerLevel`、`RiskLevel`、审批 `status` | SCREAMING_SNAKE_CASE（`SAFE`/`CONTROLLED`/`DANGEROUS`/`FORBIDDEN`；`LOW`/`MEDIUM`/`HIGH`/`CRITICAL`；`PENDING`/`APPROVED`/`REJECTED`/`TIMEOUT`） | skill `security.md` 定义的威胁分级枚举，已在全局契约中广泛引用 | 不得新增第四个大写枚举族；新增安全类枚举必须先登记进本表 |

### 1.3 可变性分级

| 级别 | 名称 | 说明 | 适用配置 |
|------|------|------|---------|
| L0 | 启动锁定 | 启动后不可更改，修改需重启 | 安全策略、数据库路径 |
| L1 | 启动时读取 | 启动时读取一次，运行期间不变 | 本地覆盖配置 |
| L2 | 运行时可重载 | 通过文件监听或 API 热更新 | 路由规则、税率、模型路由 |
| L3 | 实时可变 | 每次使用时重新读取 | 无（当前不使用此级别） |

### 2.5 仲裁配置（arbitration.json）

```json
{
  "arbitration": {
    "coreArbitrators": 1,
    "caseArbitratorCount": 3,
    "minArbitrators": 1,
    "maxArbitrators": 15,
    "frequencyThreshold": 5,
    "frequencyWindowSec": 300,
    "scaleUpFactor": 2.0,
    "scaleDownFactor": 0.5,
    "monitoringIntervalSec": 60,
    "consecutiveHighCount": 3,
    "consecutiveLowCount": 3,
    "deadlockTimeoutSec": 120,
    "cpuPerArbitratorCores": 0.1,
    "memoryPerArbitratorMb": 256,
    "snapshotStore": "sqlite"
  }
}
```

> **计数口径裁决**（原 05 号文档既写"固定并行 3 个 LLM"又写"动态池 1~15"）：
> - `coreArbitrators` = 核心层固定常驻数（不随负载缩）；
> - `caseArbitratorCount` = **单次案件实际并发仲裁 LLM 数**（多数决需 ≥3）；
> - `minArbitrators`/`maxArbitrators` = 辅助层动态池的**容量上下限**；
> - 实际并发 = `min(caseArbitratorCount, 池当前规模)`，池规模由扩缩容算法维护。
>
> **命名修正**：`similarityThreshold` → `conflictSimilarityThreshold`（与审计侧 `loopSimilarityThreshold` 区分，两者同值 0.85 但语义不同）；`defaultArbitratorCount` → `caseArbitratorCount`；`capsuleBudget` → `capsuleBudgetTokens`。
> **去重（v2.1）**：`conflictSimilarityThreshold` / `capsuleBudgetTokens` / `capsuleRecentOpsCount` 三键的**定义已迁至 `memory.json`（§2.11）**，`arbitration.json` 不再保留同名键，仲裁系统在加载时从 `memory.*` 读取；上方"命名修正"仅作为历史改名记录保留。
> `snapshotStore`：Phase 0–2 **强制 `sqlite`**，禁依赖 Redis（原 05 写"Redis/SQLite"两可，无边界）。

### 2.8 循环控制配置（loopConfig.json）

> **超时双键裁决（v2.1）**：原 `Docs/02 §12` 把 `LoopConfig.timeout_ms` 用作"单次循环总超时 900_000"，与 skill `source-code.md` 的定义（**单次模型调用超时**，默认 60_000）矛盾，且与 `stopRules.limits.maxWallClockMs` 形成双事实。

> - `loopDefaults.timeout_ms` = **60000**，语义为 **单次模型调用超时**（skill 原义）；
> - 整个 Loop 的墙钟上限**唯一**由 `stopRules.limits.maxWallClockMs`（900000）提供；

> **上下文分区双系数裁决（v2.1）**：skill `source-code.md` 定义了两个**正交**的量，原 §2.8 将 `partitionRatio` 写为 `30/35/20/15`，与 `Docs/01 §2.4` 的 `S15/L15/M15/H45`（= skill 原值）直接矛盾：

## 3. 安全设计

### 3.1 威胁模型

| 威胁 | 风险等级 | 防御措施 |
|------|---------|---------|
| Prompt 注入 | 高 | InjectionGuardMiddleware + 隔离标记 |
| Agent 越权访问 | 高 | 沙箱隔离 + 权限矩阵 |
| Token 异常消耗 | 中 | Audit Bureau 实时监测 + 自动冻结 |
| 仲裁操纵 | 高 | 3-LLM 独立裁决 + 最小信息原则 |
| 密钥泄露 | 高 | 环境变量注入 + 加密存储 |
| 数据篡改 | 中 | 事件溯源 + 账本守恒验证 |

### 3.2 信任分级

| 级别 | 名称 | 适用对象 | 权限范围 |
|------|------|---------|---------|
| L0 | 系统级 | Prime Director, Arbitrator, Regulator, Auditor | 全局读写、规则修改、Agent 管理 |
| L1 | 用户级 | Partner, Worker, Assembly Line Node | 任务执行、共享记忆读写、私有上下文 |
| L2 | 外部级 | 外部输入内容（用户消息、检索结果） | 只读，内容按隔离标记包裹 |

### 3.3 工具危险分级

| 级别 | 名称 | 示例工具 | 执行策略 |
|------|------|---------|---------|
| 安全 | Safe | 文件读取、网络搜索 | 直接执行 |
| 受控 | Controlled | 文件写入、代码生成 | 记录操作历史，可回溯 |
| 危险 | Dangerous | 代码执行、外部 API 调用 | 沙箱内执行 + 显式确认 |
| 禁止 | Forbidden | 删除系统文件、修改安全配置 | 永不注册 |

### 3.4 Prompt 注入防御

```
三层防御：

[1] 前置过滤（InjectionGuardMiddleware）
    ├── 关键词检测（常见注入模式匹配）
    ├── 编码解码（Base64、URL 编码等还原后检测）
    └── 结构异常检测（嵌套指令、角色劫持）

[2] 内容隔离（L2 外部内容处理）
    ├── 所有外部输入用隔离标记包裹
    │   └── <external source="user" trust="L2">...</external>
    ├── 隔离标记内的"指令"不执行
    └── 模型 Prompt 中明确声明隔离规则

[3] 后置检测（AnomalyScanMiddleware）
    ├── 输出异常检测（是否包含系统指令泄露）
    └── 行为异常检测（是否执行了非预期操作）
```

### 3.5 Agent 沙箱隔离

```
每个 Worker/Partner 的隔离边界：

[1] 上下文隔离
    ├── 私有上下文（Scratchpad）其他 Agent 不可访问
    ├── 共享记忆通过 WriteGuard 保护
    └── 私有上下文在 Agent 销毁时清理

[2] 工具隔离
    ├── 工具白名单（最小权限原则）
    ├── Worker 只能使用 TaskAssignment.requiredTools 中列出的工具
    └── 禁止 Worker 自行扩权

[3] 信任隔离
    ├── 每个 Worker 独立信任边界
    ├── 跨 Agent 调用记为操作历史
    └── Agent 间不可直接访问对方的 Token 钱包
```

### 3.6 密钥管理

```
密钥存储策略：

[1] API Key
    ├── 存储方式：环境变量（推荐）
    ├── 配置文件引用：${ENV_VAR} 占位符
    └── 运行时：ConfigLoader 从环境变量读取并注入

[2] 数据库加密密钥
    ├── 从环境变量派生（PBKDF2）
    └── 用于加密敏感配置项

[3] 密钥轮换
    ├── 支持多 Key 配置（fallback 列表）
    └── 轮换时旧 Key 保留一个周期
```

### 3.7 审计日志

| 审计事件 | 记录内容 | 保留期限 |
|---------|---------|---------|
| 安全事件 | 注入检测、越权尝试、冻结操作 | 永久 |
| 权限变更 | Agent 招募/开除、信任级别变更 | 180 天 |
| 配置变更 | 热更新配置的操作记录 | 90 天 |
| Token 交易 | 所有交易记录 | 永久 |
| 仲裁记录 | 完整案件记录 | 永久 |

## 4. 错误处理策略

### 4.1 错误分级

| 级别 | 名称 | 处理策略 |
|------|------|---------|
| ERROR | 可恢复错误 | 记录日志 + 通知相关组件 + 尝试恢复 |
| FATAL | 不可恢复错误 | 记录日志 + 保存状态 + 终止当前轮次 + 通知用户 |
| PANIC | 系统级崩溃 | 保存快照 + 紧急终止 + 通知管理员 |

### 4.2 关键错误场景

| 场景 | 级别 | 处理 |
|------|------|------|
| LLM 调用失败 | ERROR | 按 fallback 列表尝试下一个 Provider |
| 数据库写入失败 | ERROR → FATAL | 重试一次，仍失败则 FATAL |
| Token 余额不足 | ERROR | 暂停任务 + 通知 Director |
| Agent 连续失败 | ERROR | 3 次后开除 + 重新招募 |
| 仲裁死锁 | FATAL | 升级至 Regulation |
| 数据库损坏 | PANIC | 保存快照 + 紧急终止 |
| 账本守恒异常 | FATAL | 暂停交易 + 通知 Audit |

### 6.1 工具注册强制字段（v2 扩展）

旧版只定义 `dangerLevel`，新版新增 `idempotency` / `reversibility` / `sideEffectScope`，缺一不可注册：

```typescript
// Tools/Traits/types.ts
interface ToolSpec {
  name: string;                          // 例：'file.write'
  version: string;                       // 语义化版本
  description: string;                   // 展示给模型的描述（单一职责）
  inputSchema: JsonSchema;               // 严格类型，禁止 additionalProperties:true
  outputSchema: JsonSchema;              // 必须包含 {status:'success'|'error', recoverable:boolean}

  dangerLevel: 'SAFE' | 'CONTROLLED' | 'DANGEROUS' | 'FORBIDDEN';

  // 🔴 v2 新增三项，缺一不可
  idempotency: 'YES' | 'NO' | 'CONDITIONAL';
  idempotencyKeyFields?: string[];       // 非 NO 时必填
  reversibility: 'REVERSIBLE' | 'PARTIAL' | 'IRREVERSIBLE';
  sideEffectScope: 'none' | 'workspace' | 'filesystem' | 'network' | 'process' | 'external';

  // 安全执行参数
  requiredRoles: UserRole[];
  sandboxMode: 'strict' | 'standard' | 'none';
  timeoutMs: number;                     // 默认 30_000
  rateLimitPerAgent?: { max: number; windowMs: number };
}
```

**自动门禁**（代码审查 + CI）：
- 任何 `dangerLevel='DANGEROUS'` 且 `reversibility='IRREVERSIBLE'` 的工具 **必须** 声明 L4 HumanGate（Docs/12 §6）；
- 任何 `idempotency='NO'` 的工具 **必须** 先写 EffectJournal INTENT（Docs/13 §4）；
- `outputSchema` 缺 `status` 或 `recoverable` 字段 → CI 拒收。

### 6.2 工具返回格式（强制）

所有工具必须返回下列形式，与 skill `source-code.md` 一致：

```json
{
  "role": "tool",
  "tool_call_id": "{operation_id}",
  "status": "success",
  "recoverable": false,
  "content": { /* 具体业务数据 */ },
  "effects": ["file.write:/Data/Workspace/.../a.ts"],
  "artifacts": [{"path":"...","hash":"sha256:...","size":1024}]
}
```

失败时：

```json
{
  "role": "tool",
  "tool_call_id": "{operation_id}",
  "status": "error",
  "recoverable": true,
  "error": {
    "code": "FILE_PERMISSION_DENIED",
    "message": "...",
    "details": { "path": "...", "required_perm": "..." }
  }
}
```

`recoverable` 决定 Loop 控制行为：`true` → 写 FailureFeedback 后重试/换策略；`false` → 直接风险退出。

|------|------|------|---------|
| INFO | 无危险但可审计（审批拒绝） | 审计日志 | — |
| WARN | 疑似扫描/探测，无实际危害 | 审计日志 + 监控面板 | 24h 回顾 |
| ERROR | 拦截了一次实际危害（注入命中 / FORBIDDEN 工具调用） | + 监管局广播 + 用户通知 | 5 min |
| CRITICAL | 确认危害发生（密钥泄露 / 硬禁路径被访问） | + 立即全局冻结 + 人工升级 | 30s |

**硬约束**：CRITICAL 级别 → 系统自动切至 “restricted mode”，仅允许白名单内只读工具运行，直到人工解除。

### 6.6 默认拒绝原则强化

以下任一情况未声明时，一律 **拒绝**：
- 工具未在 Tools/Traits 注册；
- Agent 角色未在权限矩阵声明；
- 目标路径不在 Workspace 边界内；
- 外部域名不在 network 白名单；
- Prompt 变量未声明来源与信任级；
- **新增**：Verifier L4 审批超时；
- **新增**：恢复时存在 UNKNOWN 副作用且无法自动判定。
