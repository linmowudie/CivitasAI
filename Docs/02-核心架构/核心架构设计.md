## 1. 五层架构

系统采用五层架构，**单向依赖**：上层依赖下层，下层不可引用上层。

```
┌─────────────────────────────────────────────────┐
│              Interface（交互层）                   │
│  Web UI (React) · WebSocket Server · REST API    │
├─────────────────────────────────────────────────┤
│              Core（引擎层）                      │
│  Loop · Middleware · Model · Decision            │
│  （含 Agent Runtime / Orchestrator / Route）     │
├─────────────────────────────────────────────────┤
│              Services（服务层）                  │
│  Context · Supervision · Pipeline · Hook         │
│  Cache · Session · Retrieval                     │
│  LoopControl · TokenEconomy · Arbitration        │
│  Regulation · Audit · SharedMemory · EventBus    │
├─────────────────────────────────────────────────┤
│              Tools（工具层）                     │
│  Registry · Factory · Traits · Builtin · Custom  │
│  Builtin: Read / Write / Execute / Search / ...  │
├─────────────────────────────────────────────────┤
│              Infra（基础设施层）                 │
│  Fs · Db · Terminal · Logging · Time · Llm       │
│  Slm · Embedding · Hook · Config · Sandbox       │
│  Security · Watcher · Workspace · Env            │
│  DurableExecution（本 v2 新增）                  │
└─────────────────────────────────────────────────┘
```

> **层名统一**（对齐 skill `source-code.md`）：只允许使用 `Interface / Core / Services / Tools / Infra` 五个名字，禁止"核心层/决策层/业务层"等曾用名。

### 1.1 各层职责

| 层 | 职责 | 可依赖的层 | 禁止依赖 |
|----|------|-----------|---------|
| **Interface** | 用户交互入口：Web UI 渲染、WebSocket 连接管理、REST API 路由 | Core, Services(只读查询) | Tools, Infra |
| **Core** | 系统核心引擎：Agent 运行时、上下文管理、主循环、编排决策 | Services, Tools, Infra | Interface |
| **Services** | 业务服务：Token 经济、仲裁、监管、审计、共享记忆、事件总线 | Tools, Infra | Interface, Core |
| **Tools** | 工具实现：LLM 调用、文件操作、代码执行、外部 API | Infra | Interface, Core, Services |
| **Infra** | 基础设施：数据库、日志、配置、加密、HTTP、向量存储 | 无（最底层） | 所有上层 |

### 1.2 层间通信规则

| 规则 | 说明 |
|------|------|
| 单向依赖 | 上层可调用下层导出的函数/类，下层**绝对不可**引用上层 |
| 跨层调用 | Interface 需要读取 Services 数据时，通过 Core 暴露的查询接口间接获取 |
| 事件通信 | 同层或跨层组件间异步通信统一走事件总线（Services/EventBus） |
| 接口契约 | 每层对外暴露的类型定义必须写在 `Src/{LayerName}/types.ts` |

- 目录一律 **PascalCase**（如 `LoopControl/` `DurableExecution/`）

## 3. 主循环序列（强制 10 步）

> **本小节是 `skill:source-code.md` 强制契约的直接投影，禁止任何顺序调换**。若需适配业务必须写 ADR 并获批。

每个 Agent 的一次迭代严格遵循以下 10 步：

| # | 步骤 | 属于 | 内容 | 实现位置 |
|---|------|------|------|---------|
| ① | **输入接收** InputReceived | 内部 | 从接口/编排/事件取入。触发 Hook `UserInputReceived`，可拦截 | Core/Loop |
| ② | **前置监管** PreSupervision | 监管 | 安全注入检测、权限验证、频率限制 | Services/Supervision/preSupervision |
| ③ | **中间件管线** Middleware | 中间件 | `beforeModel` 钩子链（包括 GoalReanchor / FingerprintDetector / …） | Core/Middleware |
| ④ | **上下文装配** ContextAssembly | 服务 | 按 S/L/M/H 分件系数装配；处理 Cache 命中 | Services/Context/assembler |
| ⑤ | **监管懒监听** LazySupervision | 监管 | 对已装配上下文运行压缩/摘要/推理/循环四项监管（只读） | Services/Supervision/* |
| ⑥ | **模型调用** ModelCall | 工具 | 走 §10 契约（超时 60s / 流首字节 10s / 401·403 FATAL）；包裹在 `wrapModelCall` 中 | Tools/Registry → Infra/Llm |
| ⑦ | **输出解析** OutputParse | 内部 | 包含“工具选择”：区分 tool_use / 文本 / 推理块 | Core/Loop |
| ⑧ | **工具执行** ToolExecute | 工具 | 触发 Hook `PreToolExecute`（可拦截）；包裹在 `wrapToolCall`（幂等 + 审批 + 限流） | Tools/ |
| ⑨ | **后置监管** PostSupervision | 监管 | 结果归档、异常扫描、Token 扣减、Loop 控制五类退出判定 | Services/Supervision/postSupervision |
| ⑩ | **迭代判定** IterationDecision | 循环 | 成功/上限/预算/无进展/风险 5 类退出判定 → 继续或终止 | Services/LoopControl/stopRules |

### 3.1 关键约束

1. **②与③不可合并**：监管是内置安全机制，中间件是可扩展插件，两者共存时**中间件在外层、监管在内层**，禁止互相替代（对齐 skill）。
2. **⑤不可省略**：监管对上下文的检查在装配之后、调用之前，避免修改已装配的上下文造成缓存命中失效。
3. **⑧必须包裹 `wrapToolCall`**：幂等、审批门、限流、日志都挂在此，确保任何副作用先写意图日志（Docs/13 §4）。
4. **⑩不可交给模型自判**：“完成”判定必须由验证器确定，防止失效一。

### 3.2 T6 双层循环（内层仍遵循上述 10 步）

```
┌────────────────────────────────────────────┐
│  编排层循环（Prime Director）                 │
│  LoopConfig.max_iterations = 全局预算         │
│  内部依旧遵循 ①→⑩ 10 步；⑧ 工具时包含       │
│  dispatch_task / review_deliverable /        │
│  recruit_agent 等编排级工具                   │
│                                              │
│  ┌──────────────────────────────────┐       │
│  │  Worker 内层循环                    │       │
│  │  拥有独立的 LoopState + Checkpoint   │       │
│  │  trace_id 与 Director 相同；新增     │       │
│  │  parent_agent_id 关联上级           │       │
│  │  内部依旧遵循 ①→⑩ 10 步            │       │
│  └──────────────────────────────────┘       │
└────────────────────────────────────────────┘
```

**T6 特有约束**（对齐 skill 中 T6 默认值映射）：
- `trace_id` 跨 Agent 复用，新增 `parent_agent_id` 写入日志与事件；
- Token 预算上移为**编排层全局预算**，`LoopConfig.token_budget` 在 Director 侧为总量、Worker 侧为分配额度；
- **⑩ 需额外检测**：互相回传死锁（A 等 B 的结果，B 等 A 的结果），命中时直接触发风险退出。

## 4. 中间件管线（六钩子 + 与监管的关系）

> **v2 修订**：对齐业界事实标准 LangChain `AgentMiddleware` 六钩子，与 skill 定义的中间件机制兼容。本小节与 §3 中②/⑨ 监管模块 **共存不互相替代**。

### 4.1 六钩子定义

| # | 钩子 | 触发时机 | 可否短路 | 典型用途 |
|---|------|---------|---------|---------|
| 1 | `beforeAgent` | Loop 开始，① 之前 | ✓ | 会话初始化、环境快照 |
| 2 | `beforeModel` | ③ 中，上下文装配之前 | ✓ | **GoalReanchor**、注入预检测、动态提示修改 |
| 3 | **`wrapModelCall`** | 环绕 ⑥ | 完全控制 | 重试、降级、多模型 fallback、Reasoning Sandwich、预算 Sentinel |
| 4 | **`wrapToolCall`** | 环绕 ⑧ | 完全控制 | **幂等包裹**、**审批门**、**限流**、**EffectJournal** |
| 5 | `afterModel` | ⑦ 之后 | ✓ | 输出解析后修正、内容安全过滤 |
| 6 | `afterAgent` | ⑩ 完成之后 | ✗ | 归档、Trace 上报、指标采集 |

### 4.2 接口定义

```typescript
// Core/Middleware/types.ts
type MiddlewareHook =
  | 'beforeAgent' | 'beforeModel' | 'wrapModelCall'
  | 'wrapToolCall' | 'afterModel' | 'afterAgent';

interface AgentMiddleware {
  name: string;
  hook: MiddlewareHook;
  priority: number;                       // 同钩子内排序，小的先执行
  canShortCircuit: boolean;

  // 非 wrap 型：前置/后置钩子
  run?(ctx: LoopContext, next: NextFn): Promise<void>;

  // wrap 型：完全包裹后续链路（参考 koa/onion）
  wrap?<T>(ctx: LoopContext, call: () => Promise<T>): Promise<T>;
}
```

### 4.3 与监管模块的关系（红线）

```
中间件（外层）─ 面向扩展，允许项目自定义
    ↓
监管模块（内层）─ 固定 6 件，安全与约束不可插拔
```

**约束**：
- 禁止实现为“只有中间件、没有监管”——监管必须在 Services/Supervision 下实例化；
- 禁止实现为“只有监管、没有中间件”——中间件提供项目可插拔能力（如 Docs/12 的 5 个循环级守卫）；
- 两层阈值参数均写入 `Configs/supervision.json`，同名项**监管优先**。

| 钩子 | 中间件 | 优先级 | 来源 |
|------|---------|-------|------|
| beforeAgent | SessionBootstrap | 10 | 会话初始化 |
| beforeModel | **GoalReanchorMiddleware** | 20 | Docs/12 §4.3 |

## 5. 上下文分区（缓存感知四级）

> **v2 修订**：严格对齐 skill `source-code.md` §上下文分区。旧版描述的 S=系统约束/L=长期记忆/M=对话历史 + "预留" 分区均不合规。

**核心原则**：**不变的内容在前，变化的内容在后**，以最大化 Prompt Cache 命中。

### 5.1 四级分区与两个正交系数

| 分区 | 含义 | 内容 | **预算上限**（`partitionCeilingRatio`） | **分件系数**（`tokenCoefficient`） | 变动频率 |
|------|------|------|------|------|---------|
| **S** Static | 静态区 | 系统提示词、不可变约束、角色定义 | **≤ 15%** | **0.05**（极低） | 极低（会话内不变） |
| **L** Low-freq | 低频区 | 工具 Schema、长期记忆、Skills | **≤ 15%** | **0.5** | 低（小时级） |
| **M** Mid-freq | 中频区 | 用户对话历史、LoopState 摘要 | **≤ 15%** | **0.3** | 中（轮次级） |
| **H** High-freq | 高频区 | Agent 输出、工具结果、本轮检索片段 | **≤ 45%** | **1.0** | 高（每轮） |

两个系数属于 **不同机制、不得混用**（v2.1 澄清，旧版曾将两者当同一个量）：

- **预算上限**（skill `source-code.md` §Token 预算体系）：约束每个分区**能占多少输入预算**，四项和 = 90%，剩 10% 为余量；超限→ 按评分裁剪；
- **分件系数**（skill §评分延迟压缩机制）：进入条目压缩评分的**第四维度成本折算因子**（S 区因 Prompt Cache 命中而实际只付 5% 价格），**不是百分比**。

**预算公式**（仅用于压缩评分）：
```
条目压缩评分 = 时间衰减 + 访问频率（反向加权）+ 语义相关性 + 分件系数
```

### 5.2 追加式写入格式（强制）

任何写入上下文的内容必须使用四段式：

```
类型|元数据|时间戳|内容
```

例子：
```
TOOL_RESULT|{toolName:"file.write",op_id:"1735...-a1b2"}|1735000000|Successfully wrote 512 bytes
MEM_RECALL|{source:"longTermMemory",id:"m-42"}|1735000001|Prior decision: reject inline LLM in Auditor
```

**作用**：实现时间旅行调试、可确定回放、可分类丢弃。

### 5.3 与 LoopState 的关系（红线）

**禁止**使用上下文分区机制存储任务事实。`LoopState` 必须独立持久化到 `Data/Loops/{session_key}/state.json`（见 Docs/12 §4.1），分区仅用于装配上下文，**压缩不会破坏 State**。

### 5.4 评分与延迟压缩

（对齐 skill `source-code.md` §评分延迟压缩机制）

- **不即时压缩**。先评分（重要性 = 新近度 x 相密度 x 默认权重），低分优先丢弃；
- 只在上下文使用率 ≥ 92% 时触发实际截断；
- 压缩后必须触发 `GoalReanchorMiddleware`（下轮开头）。

## 6. Agent 运行时生命周期

> **枚举同形修正（v2.1）**：本节旧版用中文态名（创建/就绪/执行/挂起…）描述状态机，与 DB 列 `agents.status` 的英文枚举不同形（违反 Docs/10 §1.1 “枚举三处同形”）。
> 现以 **`agents.status` 的 6 个规范值为唯一事实源**，中文仅作括号内展示名；并明确区分**两个层级**：`awaiting_approval` 与 `failed` **不是 Agent 态**，而是 Loop 态（`loops.phase` / `loops.stopped_reason`）。

```
creating(创建) → ready(就绪) → running(执行) ⇄ suspended(挂起)
     ↑                        ↓                        ↓
     │                    destroyed(销毁) ← expelled(开除) ←──┐
     └────────── 重新招募（新 agent_id，不复用旧实例）───────────┘

Loop 级（不是 Agent 状态列，存在 loops.phase）：
  running 内嵌：planning → acting → verifying →（awaiting_approval）→ …
  终态：completed | failed（失败原因写 loops.stopped_reason）
```

| 层级 | 合法取值 | 列名 |
|------|---------|------|
| **Agent 生命周期**（6） | `creating` `ready` `running` `suspended` `expelled` `destroyed` | `agents.status` |
| **Loop 阶段**（6） | `planning` `acting` `verifying` `awaiting_approval` `completed` `failed` | `loops.phase` |
| **Loop 退出原因**（7） | `success` `limits` `budget_soft` `budget_hard` `no_progress` `risk` `human_abort` | `loops.stopped_reason` |

### 6.1 状态转换规则

> 表中“状态”列均为 **Agent 层**（`agents.status`）；写“Loop 层”的行不变 Agent 态，只变 `loops.phase`。

| 当前状态 | 触发事件 | 目标状态 | 动作 |
|---------|---------|---------|------|
| `creating` | 初始化完成 | `ready` | 分配 Token 钱包、加载角色 Prompt |
| `ready` | 收到任务指令 | `running` | 进入主循环，创建 LoopState + Checkpoint |
| `running` | 验证器通过 + 风险退出未命中 | `ready` | 结算 Token、写成功 Checkpoint（Loop 层 → `completed`） |
| `running` | **命中审批门** | `running`（不变） | **仅 Loop 层 → `awaiting_approval`**；写 `PendingApproval` 到 DB，Agent 状态不变 |
| Loop `awaiting_approval` | 审批通过 | Loop → `acting` | 从 `PendingApproval.payload` 恢复当前步骤 |
| Loop `awaiting_approval` | 审批超时 / 拒绝 | Loop → `failed` | 写 `FailureFeedback(category='risk')`；Agent 回 `ready` |
| `running` | 收到 `SUSPEND_AND_NOTIFY`（律师函） | `suspended` | 冻结 State，释放资源（**属合法中断来源**，ADR-0002） |
| `suspended` | 收到 `RESTORATION_ACK` | `running` | 恢复 State，从 `last_checkpoint_id` 续接 |
| `running` | 验证器失败 ≥ 上限 | `ready` | Loop 层 → `failed` + 写 `DiagnosticSummary`；Agent 本体不死亡 |
| `expelled` | Director 发起重新招募 | `creating` | **新建 Agent 实例**（`agent_id` 不同，旧实例入 `destroyed`） |
| 任意 | 任务结束 + 无后续任务 | `destroyed` | 清理资源、归档 Trace |
| `running` | `supervision.agentConsecutiveFailuresToExpel` 命中（默认 3） | `expelled` | 跨任务累计失败开除（≠ `stopRules.limits.maxConsecutiveErrors`） |

## 10. 模型调用契约（Model Call Contract）

> **v2 新增章**：对齐 skill `source-code.md` §模型调用契约。所有对 LLM 的调用必须满足下列硬性约束；违反任何一条均为代码门禁失败项。

### 10.1 超时

| 项 | 默认 | 可调范围 | 行为 |
|----|------|---------|------|
| 单次调用总超时 | **60_000 ms** | 10s – 300s | 超时→归为网络错误重试 |
| 流式首字节 | **10_000 ms** | 3s – 60s | 超时→中止并降级 |
| 流式相邻包间隔 | **15_000 ms** | 5s – 60s | 超时→中止 |

### 10.2 错误分类与重试

| HTTP / 错误 | 分类 | 重试 | 退避 | 处理 |
|-----------|------|------|------|------|
| **401 / 403** | Auth | ❌ 禁止 | — | **FATAL**，不重试，直接终止当前轮次 |
| **429** | RateLimited | ✅ 1 次 | 5s | 仍失败→降级到备选 Provider |
| **5xx**（非 503） | ServerError | ✅ 2 次 | 1s, 2s | 耗尽→终止本轮 |
| **503** | ServiceUnavailable | ✅ 1 次 | 直接降级 | 备选 Provider |
| **网络错误**（ECONNRESET/ETIMEDOUT） | Network | ✅ 2 次 | 1s, 2s | 耗尽→终止本轮 |
| **Schema 不匹配** | FormatError | ✅ 1 次 | 直接重试 | 仍失败→上报 FATAL |
| **内容安全命中** | ContentBlocked | ❌ 禁止 | — | 直接失败，写入安全事件 |

**重试耗尽后的统一行为**：终止当前轮次，写入 `FailureFeedback(category='external')`，交给 Loop 控制的 **⑩ 迭代判定**，避免默默推进。

### 10.3 流式与非流式

- **默认流式**：`stream: true`；非流式仅用于已知返回极短的内部控制调用；
- 流式必须支持 **中途取消**（AbortSignal），取消时也写 EffectJournal；
- 流式中间不能切换 `thinking/reasoning` 模式（对齐 Anthropic Extended Thinking 约束）。

### 10.4 多 Provider 配置格式

## 12. LoopConfig（每个循环必备 7 字段）

> **v2 新增章**：对齐 skill `source-code.md` §LoopConfig 字段清单（强制）。任何 Agent 启动时 **必须实例化一份 LoopConfig**，不得缺项。
>
> **命名豁免（v2.1）**：本接口字段为 **snake_case**，受 `Docs/11 §1.2.1 豁免 X2` 保护（skill 强制字段，benchmark 数据集与 prompt frontmatter 同名复用），**不得**为了对齐 TS 惯例而改名。
> 字段数：skill 强制 **6** 项（`model` / `max_iterations` / `timeout_ms` / `temperature` / `token_budget` / `stream`）+ 本项目扩展 **1** 项（`pauseSignal`）= 7。

```typescript
// Core/Loop/loopConfig.ts
interface LoopConfig {

   * 单次模型调用超时（ms）；默认 60_000（skill 语义）。

   * 禁止在 LoopConfig 里再设一套总超时。
   */
  timeout_ms: number;

  /** 采样温度；默认 0.2，审计/仲裁/验证 0 */
  temperature: number;

  /** Token 总预算（硬预算基准）；默认 100_000 */
  token_budget: number;

  /** 是否流式；默认 true */
  stream: boolean;

  /** 🔴 v2 强制补充：中止信号（仅供审批门/暂停符使用） */

}

// 默认值来自 Configs/loopConfig.json → loopDefaults（唯一事实源，见 Docs/11 §2.8）
```

| `assembly_node` | ✅ | 同上 |
| `arbitrator` | ✅ | 同上（`temperature` 强制 0） |
