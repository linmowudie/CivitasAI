# 仲裁系统设计

> 本文档定义 Civitas-AI 的仲裁系统（Arbitration Tribunal），融合动态仲裁者数量控制、上下文胶囊、律师函挂起机制和现场恢复机制的完整设计。

---

## 1. 职责边界

| 职责 | 说明 |
|------|------|
| 冲突接收 | 接收 WriteGuard 上报的语义冲突、Agent 间分歧 |
| 上下文胶囊组装 | 按需拉取证据，组装轻量级裁决上下文 |
| 裁决推理 | 3-LLM 多数决，按优先级协议推理 |
| 律师函挂起 | 立即挂起涉事 Agent，释放资源 |
| 现场恢复 | 指定恢复者，执行补偿动作 |
| 动态仲裁者管理 | 按冲突频率动态调整辅助仲裁者数量 |
| 知识沉淀 | 裁决结果提炼为长期知识 |

**不负责：** 冲突检测（由 SharedMemory/WriteGuard 负责）、Token 划扣执行（由 TokenEconomy 执行）、全局规则修改（由 Regulatory Authority 负责）。

## 3. 核心组件

### 3.1 组件定义

| 组件 | 类名 | 职责 |
|------|------|------|
| 冲突接收器 | `ConflictReceiver` | 接收冲突事件，创建仲裁案件 |
| 胶囊组装器 | `CapsuleAssembler` | 按需拉取证据，组装上下文胶囊 |

| 动态扩缩器 | `DynamicArbitratorScaler` | 按冲突监测指标调整仲裁者数量 |

## 4. 六步治理闭环（详细流程）

### Step 1：写入拦截（由 WriteGuard 触发）

```
Agent 向全局工作区写入新记忆
    │
    ▼
WriteGuard.intercept(writeRequest)
    ├── 提取新记忆的语义向量 + 元数据
    ├── 在向量库中检索相似度 > 0.85 的旧记忆
    ├── 检测是否存在语义相反的旧记忆
    │
    ├── 无冲突 → 放行写入
    └── 有冲突 → 生成 CONFLICT_DETECTED 事件
        │
        └── 事件内容：
            {
              conflictId: string,
              newMemoryId: string,
              oldMemoryId: string,
              newMemoryAgentId: string,
              oldMemoryAgentId: string,
              similarity: number,
              conflictType: 'semantic_opposition' | 'contradiction' | 'duplication',
              timestamp: number                  // epoch ms
            }
```

### Step 2：胶囊调阅

```
Arbitrator 收到 CONFLICT_DETECTED 事件
    │
    ▼
CapsuleAssembler.assemble(conflictId)
    │
    ├── [2a] 拉取证据
    │   ├── 新记忆完整内容 + 元数据（时间戳、来源 Agent、任务 ID）
    │   └── 旧记忆完整内容 + 元数据
    │
    ├── [2b] 拉取环境上下文
    │   ├── 两条记忆所属任务的"父级任务描述"
    │   └── 前置约束条件（如有）
    │
    ├── [2c] 拉取 Agent 历史记录
    │   ├── 涉事 Agent 最近 5 条操作记录
    │   └── 相关 trace_id 的决策历史
    │
    └── [2d] 组装胶囊
        │
        └── 输出 ContextCapsule：
            {
              capsuleId: string,
              conflictId: string,
              evidence: {
                newMemory: { content, metadata, agentId },
                oldMemory: { content, metadata, agentId },
              },
              taskContext: {
                parentTaskDescription: string,
                constraints: string[],
              },
              agentHistory: {
                plaintiffOps: OperationRecord[],
                defendantOps: OperationRecord[],
              },
              tokenBudget: number,      // 本次仲裁的 Token 预算
              createdAt: number,                          // epoch ms
            }
```

**最小信息原则：** 仲裁者绝不加载全局上下文，只看到"案卷"。

### Step 3：裁决推理

```
ReasoningEngine.reason(capsule)
    │
    ├── 并行调用 3 个独立 LLM（仲裁者）
    │   ├── 每个 LLM 独立接收 capsule
    │   ├── 使用 arbitrator.md 提示词
    │   └── 输出结构化裁决
    │
    ▼
按优先级协议推理（每个 LLM 内部）：
    │
    ├── 优先级 1：时间戳优先（LWW）
    │   └── 如果新旧记忆描述客观事实，且新记忆时间戳更晚 → 采信新记忆
    │
    ├── 优先级 2：任务权威性优先
    │   └── 检查来源 Agent 的权限等级/任务优先级
    │
    ├── 优先级 3：证据链完整性优先
    │   └── 检查哪条记忆附带更可靠的工具调用结果
    │
    └── 优先级 4：LLM 语义推理兜底
        └── 根据任务环境上下文进行逻辑推演
    │
    ▼
单个 LLM 裁决输出：
    {
      arbitratorId: string,
      verdict: 'new_wins' | 'old_wins' | 'both_invalid' | 'need_more_evidence',
      winnerId: string | null,
      loserId: string | null,
      reasoning: string,                // 裁决理由
      confidence: number,               // 置信度 0-1
      penalty?: {
        type: 'token_deduction' | 'warning' | 'none',
        amount?: number,
      },
    }
    │
    ▼
多数决汇总：
    ├── 3 个裁决中 ≥ 2 个一致 → 形成最终裁决
    ├── 3 个裁决各不相同 → 判定死锁 → 升级至 Regulatory Authority
    └── 超时（120s）→ 判定超时死锁 → 升级至 Regulatory Authority
```

### Step 4：律师函挂起

```
InjunctionPublisher.publish(arbitrationCase)
    │
    ├── 在 Step 3 启动的【同时】立即发布（不等裁决完成）
    │
    ▼
广播 SUSPEND_AND_NOTIFY 事件（最高优先级）：
    {
      eventType: 'SUSPEND_AND_NOTIFY',
      targetAgentIds: string[],        // 涉事 Agent 列表
      conflictSummary: string,         // 冲突摘要
      suspensionReason: string,        // 挂起原因
      arbitrationId: string,           // 关联仲裁案件 ID
      issuedAt: number,                           // epoch ms
    }
    │
    ▼
涉事 Agent 收到律师函后【立即执行】：
    │
    ├── [4a] 状态冻结（State Freeze）
    │   ├── 停止当前任务链执行
    │   ├── 将执行进度、局部变量、中间结论打包
    │   └── 存入 Redis/SQLite（冻结快照）
    │
    ├── [4b] 任务转移（Task Shifting）
    │   ├── 释放当前算力资源
    │   └── 处理任务队列中不依赖冲突上下文的低优先级任务
    │       （如无可用任务，进入空闲等待）
    │
    └── [4c] 进入等待队列
        └── 标记为 WAITING_FOR_ARBITRATION，不再推进原任务
```

**架构价值：**
- **零资源浪费** — Agent 不会因冲突而傻等（Block），而是去干别的活（Yield）
- **数据安全** — 通过"冻结状态"杜绝 Agent 在等待期间基于错误前提继续执行
- **系统韧性** — 冲突不再导致系统崩溃或死锁，而是变成一次常规的异步任务调度

### Step 5：现场恢复

```
RestorationManager.restore(arbitrationResult)
    │
    ├── [5a] 指定恢复者
    │   ├── 策略 1：失败方自愈（Self-Healing）
    │   │   └── 指定产生错误记忆的 Agent 作为恢复者
    │   └── 策略 2：全局接管（Global Takeover）
    │       └── 指定更高权限的 Fallback Agent 强制回滚
    │
    ▼
    ├── [5b] 恢复者执行现场恢复
    │   ├── 撤回错误动作（生成补偿动作 CompensatingAction）
    │   │   └── 如：修改了错误文件 → 回滚文件；发了错误请求 → 发送撤销请求
    │   ├── 重置本地状态
    │   │   ├── 清除基于错误记忆推导的所有中间结论
    │   │   └── 将任务状态回退到冲突发生前的节点
    │   └── 应用裁决结果
    │       └── 将仲裁者给出的"新真相"写入全局工作区
    │
    ▼
    └── [5c] 二次广播
        │
        └── 广播 RESTORATION_ACK 事件：
            {
              eventType: 'RESTORATION_ACK',
              restorerId: string,
              restoredTaskId: string,
              compensationActions: CompensatingAction[],
              restoredAt: number,                         // epoch ms
            }
```

### Step 6：知识沉淀

```
KnowledgeConsolidator.consolidate(arbitrationResult)
    │
    ├── [6a] 滑动窗口检查
    │   └── 检查被裁决替换掉的旧记忆所在的工作区时间窗口
    │
    ├── [6b] 知识提炼
    │   ├── 如果冲突涉及重要业务规则变更 → 触发 KNOWLEDGE_CONSOLIDATION
    │   └── 剥离具体对话过程，只保留核心事实
    │
    └── [6c] 写入长期记忆
        ├── 提炼后的静态知识 → LongTermMemory
        └── 裁决案例 → 仲裁历史库（供未来参考）
```

### Step 7（后续）：解封与恢复

```
涉事 Agent 监听到 RESTORATION_ACK 事件
    │
    ├── 确认"案结事了"
    ├── 从 SQLite 拉取冻结状态快照
    ├── 结合仲裁者给出的"新真相"更新本地上下文
    └── 继续执行之前被挂起的任务
```

## 5. 动态仲裁者数量控制

### 5.1 冲突监测指标

| 指标 | 计算方式 | 用途 |
|------|---------|------|
| 冲突发生频率 | 单位时间内冲突次数（滑动窗口） | 判断是否需要扩容 |
| 冲突持续时间 | 从冲突检测到裁决完成的时长 | 判断仲裁效率 |
| 冲突涉及 Agent 数 | 单次冲突中参与的 Agent 数量（加权平均） | 判断冲突规模 |
| 待处理冲突队列长度 | 排队等待仲裁的案件数 | 判断仲裁压力 |

### 5.2 动态调整算法

```
每 monitoringInterval（默认 60s）执行一次：

// 采集指标
metrics = ConflictMonitor.collect(windowSize=300s)

// 判定是否需要调整
if metrics.conflictFrequency > frequencyThreshold
   AND consecutiveHighCount >= 3:
    // 连续 3 个窗口超阈值 → 扩容
    targetCount = min(currentCount × scaleUpFactor, maxArbitrators)
    
else if metrics.conflictFrequency < frequencyThreshold × 0.5
   AND consecutiveLowCount >= 3:
    // 连续 3 个窗口低于阈值一半 → 缩容
    targetCount = max(currentCount × arbitration.scaleDownFactor, arbitration.minArbitrators)

// 资源约束检查
resourceLimit = min(
  availableCpu / arbitration.cpuPerArbitratorCores,
  availableMemoryMb / arbitration.memoryPerArbitratorMb
)
targetCount = min(targetCount, resourceLimit)

// 执行调整
if targetCount != currentCount:
    ArbitratorPool.resize(targetCount)
    广播 ARBITRATOR_POOL_RESIZED 事件
```

### 5.3 仲裁者分层

| 层级 | 数量 | 职责 | 扩缩策略 |
|------|------|------|---------|
| 核心层 | 1（固定） | 处理常规冲突、维护裁决一致性 | 不扩缩 |
| 辅助层 | 0~N（动态） | 应对突发/大规模冲突 | 按监测指标扩缩 |

### 5.4 配置参数

> **本节不维护默认值**（SSOT 裁决，见 Docs/11 文档头）。唯一事实源为 **Docs/11 §2.5**（`arbitration.json → arbitration.*`）。
> 下表仅列本子系统消费的键、定义位置与 **v2.1 命名/单位修正**：

| 本文使用的键 | 定义位置 | 修正说明 |
|-------------|---------|---------|
| `arbitration.coreArbitrators` / `caseArbitratorCount` | Docs/11 §2.5 | 常驻核心数与**单案并发仲裁 LLM 数**（解开了原"固定 3 个"与"动态池 1~15"两种口径共存） |
| `arbitration.minArbitrators` / `maxArbitrators` | Docs/11 §2.5 | 动态池上下限 |
| `arbitration.frequencyThreshold` + `frequencyWindowSec` | Docs/11 §2.5 | 原 `5/5min` 复合值拆为两键（数值 + 单位后缀） |
| `arbitration.scaleUpFactor` / `scaleDownFactor` | Docs/11 §2.5 | 扩缩倍率 |
| `arbitration.monitoringIntervalSec` | Docs/11 §2.5 | 原 `monitoringInterval: 60s` → 数值去单位 + 键名补后缀 |
| `arbitration.consecutiveHighCount` / `consecutiveLowCount` | Docs/11 §2.5 | 连续高/低负载判定轮数（补充定义，原伪码引用了未登记变量） |
| `arbitration.deadlockTimeoutSec` | Docs/11 §2.5 | 原 `deadlockTimeout: 120s` → 同上 |
| `arbitration.cpuPerArbitratorCores` / `memoryPerArbitratorMb` | Docs/11 §2.5 | 原 `cpuPerArbitrator` / `memoryPerArbitrator: 256MB` 无单位后缀且含非法字符 |
| `arbitration.snapshotStore` | Docs/11 §2.5 | Phase 0–2 强制 `"sqlite"`（禁 Redis） |

## 6. 仲裁案件数据模型

```typescript
interface ArbitrationCase {
  caseId: string;                      // UUID
  conflictId: string;                  // 关联冲突 ID
  
  // 涉事方
  parties: {
    agentId: string;
    role: 'plaintiff' | 'defendant';
    memoryId: string;                  // 相关记忆 ID
  }[];
  
  // 胶囊
  capsule: ContextCapsule;
  
  // 裁决过程
  arbitratorVerdicts: ArbitratorVerdict[];
  finalVerdict?: {
    verdict: 'new_wins' | 'old_wins' | 'both_invalid';
    majorityCount: number;             // 多数决票数
    reasoning: string;
    penalty?: PenaltyAction;
  };
  
  // 恢复
  restorationStatus: 'pending' | 'in_progress' | 'completed' | 'failed';
  restorerId?: string;
  compensationActions?: CompensatingAction[];
  
  // 状态
  status: 'filed' | 'arbitrating' | 'verdict_reached' | 'restoring' | 'closed' | 'deadlocked';
  
  // 时间
  filedAt: number;                            // epoch ms
  verdictAt?: number;                         // epoch ms
  restoredAt?: number;                        // epoch ms
  closedAt?: number;                          // epoch ms
}
```

## 7. 事件清单

| 事件 | 触发时机 | 订阅者 |
|------|---------|--------|
| `CONFLICT_DETECTED` | WriteGuard 检测到语义冲突 | Arbitration |
| `ARBITRATION_FILED` | 仲裁案件立案 | Dashboard |
| `SUSPEND_AND_NOTIFY` | 律师函发布 | 涉事 Agent, Dashboard |
| `ARBITRATION_VERDICT` | 裁决完成 | TokenEconomy, SharedMemory, Restoration |
| `RESTORATION_ACK` | 现场恢复确认 | 涉事 Agent, Dashboard |
| `KNOWLEDGE_CONSOLIDATION` | 触发知识沉淀 | SharedMemory/LongTermMemory |
| `ARBITRATION_DEADLOCK` | 裁决死锁/超时 | Regulation, Dashboard |
| `ARBITRATOR_POOL_RESIZED` | 仲裁者池扩缩 | Dashboard |
