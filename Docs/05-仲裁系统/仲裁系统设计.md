# 仲裁系统设计

> 本文档定义 Civitas-AI 的仲裁系统（Arbitration Tribunal），融合动态仲裁者数量控制、上下文胶囊、律师函挂起机制和现场恢复机制的完整设计。

---

## 1. 职责边界

| 职责 | 说明 |
|------|------|
| 冲突接收 | 接收 WriteGuard 上报的语义冲突、Agent 间分歧 |
| 上下文胶囊组装 | 按需拉取证据，组装轻量级裁决上下文 |
| 裁决推理 | 3-LLM 多数决，按优先级协议推理 |
| 律师函挂起 | 立即挂起涉事 Agent，释放资源 |
| 现场恢复 | 指定恢复者，执行补偿动作 |
| 动态仲裁者管理 | 按冲突频率动态调整辅助仲裁者数量 |
| 知识沉淀 | 裁决结果提炼为长期知识 |

**不负责：** 冲突检测（由 SharedMemory/WriteGuard 负责）、Token 划扣执行（由 TokenEconomy 执行）、全局规则修改（由 Regulatory Authority 负责）。

## 4. 六步治理闭环（详细流程）

### Step 1：写入拦截（由 WriteGuard 触发）

```

    │
    ▼

    │
    ├── 【目标态 · ⚠️ 未实现（2026-09-22 校准）】
    │   ├── 提取新记忆的语义向量 + 元数据
    │   ├── 在向量库中检索相似度 > 0.85 的旧记忆
    │   └── 检测是否存在语义相反的旧记忆
    │
    ├── 【实际实现】interceptWrite 仅做三件事：
```

### Step 3：裁决推理


### Step 4：律师函挂起

```
issueSuspension(caseId)                       // 原写 InjunctionPublisher.publish(arbitrationCase) 不存在；实为 tribunal.ts:195
    │
    ├── 发布时机（2026-09-22 校准，按代码）：**裁决后挂起**，而非"与 Step 3 同时"

    │
    ▼

    {
      eventType: 'SUSPEND_AND_NOTIFY',
      targetAgentIds: string[],        // 涉事 Agent 列表 = [plaintiffAgentId, defendantAgentId]
      suspensionReason: string,        // 挂起原因
      caseId: string,                  // 关联仲裁案件 ID（代码字段名为 caseId，非 arbitrationId）

    │
    ▼

    │                                        // ⚠️ 未实现（2026-09-22 校准）：Src 中无 SUSPEND_AND_NOTIFY 订阅方，
    │                                        //    以下 [4a]-[4c] 为设计目标态（冻结快照落 Redis/SQLite 亦未接线）
    ├── [4a] 状态冻结（State Freeze）
    │   ├── 停止当前任务链执行
    │   ├── 将执行进度、局部变量、中间结论打包
    │   └── 存入 Redis/SQLite（冻结快照）
    │
    ├── [4b] 任务转移（Task Shifting）
    │   ├── 释放当前算力资源
    │   └── 处理任务队列中不依赖冲突上下文的低优先级任务
    │       （如无可用任务，进入空闲等待）
    │
    └── [4c] 进入等待队列
        └── 标记为 WAITING_FOR_ARBITRATION，不再推进原任务
```

**架构价值：**
- **零资源浪费** — Agent 不会因冲突而傻等（Block），而是去干别的活（Yield）
- **数据安全** — 通过"冻结状态"杜绝 Agent 在等待期间基于错误前提继续执行
- **系统韧性** — 冲突不再导致系统崩溃或死锁，而是变成一次常规的异步任务调度

## 5. 动态仲裁者数量控制

### 5.1 冲突监测指标

| 指标 | 计算方式 | 用途 |
|------|---------|------|
| 冲突发生频率 | 单位时间内冲突次数（滑动窗口） | 判断是否需要扩容 |
| 冲突持续时间 | 从冲突检测到裁决完成的时长 | 判断仲裁效率 |
| 冲突涉及 Agent 数 | 单次冲突中参与的 Agent 数量（加权平均） | 判断冲突规模 |
| 待处理冲突队列长度 | 排队等待仲裁的案件数 | 判断仲裁压力 |

> ⚠️ 未实现（2026-09-22 校准）：`dynamicScaling.ts` 只维护 `conflictWindow: number[]`（由 `recordConflict()` 追加的冲突时间戳），
> 即**仅"冲突发生频率"一项有采集代码**（窗口长度硬编码 300 秒，未读 `arbitration.frequencyWindowSec`）；
> 冲突持续时间、涉及 Agent 数、待处理队列长度三项均无实现。

### 5.2 动态调整算法

```
// 原写法 targetCount = currentCount × scaleUpFactor 与 CPU/内存资源约束检查均与代码不符（代码无资源约束逻辑）。

evaluateScaling()                              // dynamicScaling.ts:72；由 startAutoScaling() 每 monitoringIntervalMs 触发（:150）
{
  // [0] 冷却期：距上次扩缩 < cooldownMs（默认 120_000）→ 直接返回 action='none'

  // [1] 采集指标：conflictWindow 过滤到最近 300 秒（窗口长度硬编码，未读 frequencyWindowSec）
  frequency = conflictWindow.length            // 窗口内冲突条数

  // [2] 扩容判定：频率连续 consecutiveHighCount（默认 3）个评估轮 > frequencyThreshold（默认 5）
  //     幂律公式 f = k · n^m
  scalingFactor(=k, 默认 1.5) × Math.pow(frequency, scalingExponent(=m, 默认 0.5))
  targetCount = min(ceil(上式), maxArbitrators /* 默认 15 */)
  if (targetCount > currentAux) resizeAuxiliaryPool(targetCount)      // 仅扩辅助层，核心层不参与扩缩

  // [3] 缩容判定：frequency < frequencyThreshold × 0.5 且连续 consecutiveLowCount（默认 3）轮
  targetCount = max(minArbitrators /* 默认 0 */, floor(currentAux × 0.5))   // ⚠️ 0.5 为硬编码，未读 scaleDownFactor
  if (targetCount < currentAux) resizeAuxiliaryPool(targetCount)

  // [4] 介于两者之间 → consecutiveHigh / consecutiveLow 双双清零
}

// 扩缩成功后广播 ARBITRATOR_POOL_RESIZED（source='Arbitration/dynamicScaling'）
//   payload = { action: 'scale_up' | 'scale_down', targetCount, added | removed }

⚠️ 未接线（2026-09-22 校准）：
  · initDynamicScaling(cfg) 在 Src 中无调用方 → 全部阈值取模块内 DEFAULT_CONFIG，
    Configs/arbitration.json 的 scaleUpFactor / scaleDownFactor / monitoringIntervalSec /
    frequencyWindowSec / cpuPerArbitratorCores / memoryPerArbitratorMb **均未被消费**；
  · recordConflict() 无生产调用方（案件立案/裁决路径未回采频率），故自动扩缩实际处于空转；
  · 无 CPU/内存资源约束（原"resourceLimit"分支为设计目标）。
```

### 5.3 仲裁者分层

| 层级 | 数量 | 职责 | 扩缩策略 |
|------|------|------|---------|
| 核心层 | 1（固定） | 处理常规冲突、维护裁决一致性 | 不扩缩 |
| 辅助层 | 0~N（动态） | 应对突发/大规模冲突 | 按监测指标扩缩 |
